## Part 1 — what happened

### Phase 1 — iterative scoping (feedback-and-wait)

The session opened with idea-pipeline #21 ("Gascity progress tracker" TUI) and an explicit request for impressions only ("don't take action, just give me feedback and wait"). Several rounds of scoping followed, each settling one decision: the TUI is a **toy/v0.1 dogfood** delivered in chunks (chunk 1 = beads browser, chunk 2 = sessions + `tail -30` peek); it is an **operator instrument alongside the backbone**, not a 26th component; repo discipline is **idea-pipeline = issue only / software-factory = plans / software-factory-prototype = code**; and the config is reshaped to serve the goal ("the goal should be the driver, not the current configuration"). The agent honored the feedback-and-wait constraint and only acted once the operator said "go."

### Phase 2 — institutionalize the plan + scaffold the prototype

Authored the durable plan in software-factory (PR #257): a new TUI operator-instrument plan, a "built alongside (not one of the 25)" section in the backbone plan, and a Board 1 Card 8 update. Staged the prototype (PR #12): `python3` + a baked `tui/` + an `sftui` shim in the image, a placeholder `beadview.py`, an opt-in default-inert build-rig credential path, and a stored chunk-1 prompt command. Claimed issue #21 and posted STARTED / PR-OPENED (recognizing cross-repo PRs cannot keyword-close the issue).

### Phase 3 — the Docker correction (the central mishap)

The agent had shipped the prototype changes as "unverified — no Docker host, no token in this environment." The operator pushed back: Docker *is* available, the daemon just is not started — "an incredibly common mistake agents make" — and asked where it was documented. It was documented (HANDOFF.md §3, including a real token and a full CA-injection recipe) but buried in a doc the agent had only skimmed. Fix: a SessionStart hook that auto-starts `dockerd`, new `AGENTS.md`/`CLAUDE.md` in the prototype (which had none), and corrections to the false "can't run here" claims in both PRs.

### Phase 4 — in-sandbox verification (subagent-driven)

With Docker running, a subagent built the CA-trusting image and verified the packaging tokenless (`python3`, `sftui --dump`, baked `beadview.py`), then ran the chunk-1 dogfood with the real token: the prototype built `beadview.py` itself, end-to-end and unattended (~15 min, created → routed → polecat commit → refinery merge). The factory-built viewer (230 lines, stdlib curses, discovered `gc bd list --json` on its own) was cleaner than the placeholder and replaced it (PR #12, `cc7026f`).

### Phase 5 — merge, close, fix the surfaced defects

Merged #257 and #12; closed #21 against the agreed criterion. Verification had surfaced two defects → PR #13: an `entrypoint.sh` crash-loop on reused/partial volumes (pack-install gated on `packs.lock` alone) and HANDOFF §3 gaps (npm needs `NODE_EXTRA_CA_CERTS`; Docker Hub 429s).

### Phase 6 — "always test fixes" + verifying the fix

The agent initially shipped the entrypoint fix "reasoned, not tested." The operator made it an absolute: "Always test fixes. No exceptions. Ever. Put that in agents Md and follow that instruction." Added the rule to both AGENTS.md files (#258 + #13), stored the chunk-1 prompt durably, documented pull+rebuild, then *followed it*: a second subagent reproduced the crash-loop on the old entrypoint (`RestartCount=5`, exact gc error) and confirmed the fix recovers on identical input (`RestartCount=0`). Merged #13 and #258. A dropped turn (responding "No response requested" to "retrospect") was the session's minor process miss.

## Part 3 — agents-file suggestions

Proposed additions to `AGENTS.md`. Each has a per-rule file in the sibling directory; both sections are mirrored inline here. (Two further rules — "the sandbox HAS Docker / start the daemon" and "always test fixes — no exceptions, ever" — were already adopted *during* this session, into the prototype `AGENTS.md` and both `AGENTS.md` files respectively, so they are not re-proposed here.)

### Suggestion 1: Read the full handoff/environment doc before claiming an environment limitation — `AGENTS-MD-aee92aa39e`

- **Per-rule file**: [./2026-06-08-258/AGENTS-MD-aee92aa39e-read-full-handoff-before-claiming-limitation.md](./2026-06-08-258/AGENTS-MD-aee92aa39e-read-full-handoff-before-claiming-limitation.md)

**Proposed agent instruction:**

> **Read the full handoff/environment doc before claiming an environment limitation.** Before reporting that a capability is unavailable (no Docker, no token, no network, "can't verify here"), read the repo's complete handoff / environment / getting-started doc end to end — not just its head — and probe directly (e.g. `which dockerd`, `docker info`). State a limitation only after both the doc and a live probe confirm it.
>
> *Grounded in: claiming "no Docker host / no token" when the daemon merely needed `sudo dockerd` and a token plus a full build recipe were documented in HANDOFF.md §3, which had only been skimmed.*

**Justification:**

This session twice asserted a false environment limitation ("no Docker host," then "no token") and shipped two PRs of work labeled "unverified" on that basis. Both were wrong — Docker was present (daemon unstarted) and a token + full recipe were in HANDOFF.md §3, which had only been skimmed. The correction cost a follow-up pass after operator pushback; the rule costs one full doc read plus a one-line probe.

### Suggestion 2: Store invocation prompts and commands durably in the repo — `AGENTS-MD-6741a48eef`

- **Per-rule file**: [./2026-06-08-258/AGENTS-MD-6741a48eef-store-prompts-durably.md](./2026-06-08-258/AGENTS-MD-6741a48eef-store-prompts-durably.md)

**Proposed agent instruction:**

> **Store invocation prompts and commands durably in the repo.** When a prompt, command, or input drives real work (a `gc bd create` task body, a subagent brief, a generation prompt), commit it to the repo as the durable source of truth — do not leave it only in chat, a subagent brief, or an ephemeral / un-synced store (e.g. a local bead store). If it was worth running, it is worth re-running and reviewing.
>
> *Grounded in: the chunk-1 `gc bd create` prompt existing only in the ephemeral bead and the subagent brief until the operator asked where it was stored.*

**Justification:**

The chunk-1 prompt was the load-bearing input that made the factory build its own TUI, yet it lived only in chat, a subagent brief, and the never-synced local bead store. When the operator asked where it was stored, the honest answer was "nowhere durable" — a silent data-loss risk. The fix was one committed file; the asymmetry against losing the factory's own build recipe is stark.

### Suggestion 3: Cross-repo issue and PR closure is manual — `AGENTS-MD-41fab64fed`

- **Per-rule file**: [./2026-06-08-258/AGENTS-MD-41fab64fed-cross-repo-closure-manual.md](./2026-06-08-258/AGENTS-MD-41fab64fed-cross-repo-closure-manual.md)

**Proposed agent instruction:**

> **Cross-repo issue and PR closure is manual.** GitHub keyword-closing (`Closes #N`) only works when the PR and the issue live in the same repository. When a PR addresses an issue in a different repo, do not claim the merge will auto-close it; close the issue explicitly against a stated criterion and link the PRs in a comment.
>
> *Grounded in: idea-pipeline issue #21 addressed by PRs in software-factory and software-factory-prototype, which cannot keyword-close it across repos.*

**Justification:**

The tracking issue lived in idea-pipeline while every PR landed in two other repos. A naive `Closes #21` would have silently failed and left a done issue open forever. Recognizing the cross-repo limit cost nothing and let the agent set an explicit close criterion and close deliberately. The rule prevents a class of stale-state bugs in any multi-repo workflow.

### Suggestion 4: Prefer verified dogfood output over hand-written placeholders — `AGENTS-MD-ac657067bd`

- **Per-rule file**: [./2026-06-08-258/AGENTS-MD-ac657067bd-prefer-dogfood-over-placeholder.md](./2026-06-08-258/AGENTS-MD-ac657067bd-prefer-dogfood-over-placeholder.md)

**Proposed agent instruction:**

> **Prefer verified dogfood output over hand-written placeholders.** When the system under test can generate the artifact itself (a dogfood / factory build) and that output passes verification, ship the generated artifact with its provenance recorded, rather than a hand-written stub — even if you already wrote the stub.
>
> *Grounded in: the prototype's own build loop producing a cleaner, working `beadview.py` than the placeholder the agent had written, which then replaced it.*

**Justification:**

The agent wrote a placeholder `beadview.py` expecting to keep it, but the dogfood produced an objectively better viewer that met every spec point and carried "the factory built this" provenance — the entire thesis being demonstrated. Shipping the placeholder anyway would have discarded both. The rule costs nothing beyond requiring the generated output to pass verification first.
