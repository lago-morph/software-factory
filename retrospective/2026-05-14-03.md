## Part 1 — what happened

### Phase 1 — Retro-coverage audit

Goal: answer the user's question — what fraction of the repo's PRs are covered by some retrospective, and where are the gaps?

Approach: enumerate the five existing retros (`retrospective/2026-05-11-01.md`, `2026-05-13-01.md`, `2026-05-13-02.md`, `2026-05-14-01.md`, `2026-05-14-02.md`), read each for its **"Commit hashes by PR"** section, then list all PRs via `mcp__github__list_pull_requests` and compute the set difference.

The audit yielded:

- **37 PRs total** (#1–#50 with issue-number gaps).
- **14 PRs explicitly covered** by some retro's "Commit hashes by PR" section.
- **~14 dark PRs** with no retrospective discussion.
- **Two long silence gaps** in the PR stream: ~36 h (2026-05-11 13Z → 2026-05-13 01Z) and ~17 h (2026-05-13 05Z → 2026-05-13 23Z) — likely user time off, not coverage gaps.
- **Dark zone 1**: PRs #11–#25 on 2026-05-11 (12 merged + 1 closed unmerged).
- **Dark zone 2**: PRs #49–#50 on 2026-05-14 (after the day's two retros).

Two operational findings during the audit:

- **GitHub PR numbers and issue numbers share a namespace.** Gaps in the PR sequence (#4, #8, #23, #24, #26–31, #36, #41, #42) are issues, not missing data. I had to recognize that explicitly before computing coverage.
- **`mcp__github__list_pull_requests` returned ~134 KB JSON**, which exceeded the tool-result token cap. The harness saved the raw blob to disk; I read it out-of-band via `python3 -c ...` to extract just the fields I needed (number, state, merged_at, base, head, title). Direct loading would have spent the context budget on JSON formatting.

### Phase 2 — Synthesize the dark-zone-1 retro

Goal: produce a retroactive retrospective for PRs #11–#25, leaning heavily on PR descriptions, dated to the last PR's merge time, in the standard retro format.

Approach: fetch 13 PR descriptions in a single parallel block (`mcp__github__pull_request_read method=get` ×13), then synthesize the narrative from the bodies.

What the PR bodies gave directly:
- The phase decomposition (skill extraction → cache eviction → ADR/retro-skill → PR-lifecycle hardening → PLAN.md consolidations → manual drains → fanout build → 26-subagent fanout).
- Concrete numbers (commit counts, line diffs, wall times).
- The four reconstructed-claim refutations in report 07 (the Dark Factory primary-source unlock).
- The Lenny "video-only" reclassification after three failed retrieval routes.
- The `isolation: "worktree"` mandate in PR #22 and its first real exercise at N=26 in PR #25.

What the PR bodies did **not** give directly, and required inference:
- **Self-reflection** ("what I'd do differently"). PR descriptions are forward-looking artifacts; they describe what was done and why, not what was botched. The PR #13 → #14 fresh-branch redundancy was inferrable because PR #16 was explicitly written to prevent recurrence — the rule-tightening was the evidence.
- **The meta-lesson** that retro 2026-05-11-01 was written mid-session. This came from comparing retro 1's "Commit hashes by PR" (which covered up to #10 + work on the #14 branch) against the PR list's continued activity (11 more PRs after retro 1's commit landed).

The synthesized retro: `retrospective/2026-05-11-02.md`, 323 lines, dated 2026-05-11 (the day of the covered PRs), sequence 02 (since 2026-05-11-01 already existed), flagged **SYNTHETIC / BACK-FILLED** in the metadata block with explicit authoring date and provenance.

Empty sibling directory: `retrospective/2026-05-11-02/` was created but contains no spec files. Git ignored it on commit. This is the correct outcome for a synthetic retro that the author judges should not propose new skill specs from material it didn't witness contemporaneously — the directory exists as a placeholder for any future user-driven authoring.

## Part 4 — proposed ADRs

Architectural decisions surfaced or made in this session. **Titles + one-line rationale only — no specs.** Author via the `adr` skill if you decide any are worth recording.

- **Synthetic / back-filled retrospectives must be flagged as such in the metadata block** — Establishes the precedent that retro provenance is auditable; readers can tell whether a retro was contemporaneous or reconstructed. The `2026-05-11-02.md` file produced this session is the first instance.

- **Retrospectives are dated to the merge time of the last PR they cover, not the authoring time** — Preserves chronological browsing of `retrospective/*.md` against the PR stream. The synthetic retro this session produced is dated 2026-05-11 (covering PRs that merged 2026-05-11 01:24Z–12:48Z), not 2026-05-14 (the authoring date). The metadata block records both.

- **Every retrospective must include a "Commit hashes by PR" section** — Currently a convention in the `self-retrospective` skill; the audit this session ran was only possible because all five existing retros followed it. Worth promoting from skill-internal convention to a binding repo rule, since the audit-and-backfill skill depends on it.

- **Sequence numbers within a UTC date are append-only; back-fills take the next available NN, regardless of when the work happened** — This session produced `2026-05-11-02` (a back-fill) on 2026-05-14. The numbering rule is: scan `retrospective/YYYY-MM-DD-*.md`, take `count + 1`. Back-fills do not insert into the sequence retroactively.

- **Oversized MCP / API responses are processed out-of-band via the saved tool-result file, not by re-running the call** — The 134 KB PR-list response exceeded the tool-result token cap; the harness saved it to `/root/.claude/projects/.../tool-results/...txt` and the agent extracted fields via `python3 -c ...`. This is the right pattern; codify it.
