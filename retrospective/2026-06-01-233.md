## Part 3 — agents-file suggestions

### Suggestion 1: Verify load-bearing external facts with your own tool calls and controls — `AGENTS-MD-05abec3c4f`
- **Per-rule file**: [./2026-06-01-233/AGENTS-MD-05abec3c4f-verify-external-facts-with-controls.md](./2026-06-01-233/AGENTS-MD-05abec3c4f-verify-external-facts-with-controls.md)

**Proposed agent instruction:**
> **Verify load-bearing external facts with your own tool calls and controls.** When a fact the run depends on is asserted by a subagent or a web search — whether a repo/binary/tool exists, or how an API behaves — confirm it yourself with at least two independent signals and a control case before acting on it. Treat a subagent's research narrative as a lead, not a fact; a blanket transport error (e.g. a proxy returning 403 for every path, including known-good controls) tells you nothing about the underlying truth.
>
> *Grounded in: a subagent reported Gas City as "v1.2.0 / brew install" (confabulated specifics) while the repo's existence was real; direct GitHub-API/HTML/search probes with control repos distinguished a proxy-403 artifact from real existence.*

**Justification:** The G11 risk (is `gc` real?) is the entire architecture's #1 unknown; a single subagent's confident narrative nearly answered it wrong (the specifics were fabricated). The marginal cost of the right move was three `curl` calls with a control repo — seconds — versus building a whole sweep on a possibly-fabricated premise. The control case (a known-good repo returning the same 403) is what converted an ambiguous signal into a definite "proxy artifact."

### Suggestion 2: Lead-verify a subagent's contradiction verdict against the actual corpus text — `AGENTS-MD-77f39712af`
- **Per-rule file**: [./2026-06-01-233/AGENTS-MD-77f39712af-lead-verify-contradiction-verdicts.md](./2026-06-01-233/AGENTS-MD-77f39712af-lead-verify-contradiction-verdicts.md)

**Proposed agent instruction:**
> **Lead-verify a subagent's contradiction verdict before applying it.** When a subagent reports that a finding CONTRADICTS the corpus, grep the actual spec/doc text the contradiction names before annotating anything — a fact being true of the substrate does not contradict a document that never made the opposing claim. Reclassify to NEW-INFO when no opposing claim exists.
>
> *Grounded in: a harvest subagent flagged 3 CONTRADICTS-CLAIM facts; grepping the actual specs showed 0 true contradictions (the specs had deferred the field names to later verification or never referenced them).*

**Justification:** Applying three "v4 is wrong" annotations would have falsely impugned the corpus and triggered needless rework, when the corpus's deferral discipline had actually held up. The verification cost was three greps. Subagents err toward over-flagging contradictions because they reason from the new fact, not from what the doc actually claims.

### Suggestion 3: Run a cross-component seam adversary after a parallel uniform-schema fan-out — `AGENTS-MD-67a0daa199`
- **Per-rule file**: [./2026-06-01-233/AGENTS-MD-67a0daa199-seam-adversary-after-uniform-fanout.md](./2026-06-01-233/AGENTS-MD-67a0daa199-seam-adversary-after-uniform-fanout.md)

**Proposed agent instruction:**
> **Run a cross-component seam adversary after a parallel uniform-schema fan-out.** Per-deliverable review is not enough when parallel subagents author interdependent components: even subagents that verbatim-cite the same binding decision drift on the wire types at their shared boundary. After the fan-out, dispatch one adversary whose sole job is pairwise seam consistency (field names, wire types, who-guarantees-what) before integrating.
>
> *Grounded in: parallel Sweep-2 builders for C23 and C41 both cited the same D-5 boundary yet produced EventId{stream,seq} vs bare uint64 at the chain seam — a HIGH build-breaker only the seam adversary caught.*

**Justification:** Verbatim-citing the same binding decision (a rule that worked well for paraphrase-drift) did NOT prevent type drift at the shared boundary, because each builder interpreted the un-specified field type locally. One extra adversary per cluster caught a defect that would otherwise surface only at integration/implementation time, when it is far more expensive.

### Suggestion 4: Commit each completed subagent deliverable on its completion signal — `AGENTS-MD-5a9742e567`
- **Per-rule file**: [./2026-06-01-233/AGENTS-MD-5a9742e567-commit-completed-deliverable-on-completion.md](./2026-06-01-233/AGENTS-MD-5a9742e567-commit-completed-deliverable-on-completion.md)

**Proposed agent instruction:**
> **Commit each completed subagent deliverable on its completion signal.** In the ephemeral sandbox with a git-state stop-hook, do not batch-wait a whole wave of async subagents before committing — commit each deliverable the moment its agent reports complete, adding explicit paths so a sibling's in-progress edit is not captured. Use a background stabilization watcher, not a foreground wait, to bridge to a still-running agent.
>
> *Grounded in: the git stop-hook fired repeatedly while sibling builders were mid-write; committing each completed component by explicit path resolved it without capturing partial edits.*

**Justification:** The "commit at wave boundary" guidance conflicts with a stop-hook that fires at every turn-end; the resolution is per-completed-deliverable commits by explicit path, which satisfies both the hook and sandbox-loss protection without ever staging a half-written file. Cost: one `git add <paths>` per completion instead of one per wave.

### Suggestion 5: Use jentic for GitHub operations outside the session-scoped repo — `AGENTS-MD-1748962679`
- **Per-rule file**: [./2026-06-01-233/AGENTS-MD-1748962679-jentic-for-out-of-scope-github.md](./2026-06-01-233/AGENTS-MD-1748962679-jentic-for-out-of-scope-github.md)

**Proposed agent instruction:**
> **Use jentic for GitHub operations outside the session-scoped repo.** The GitHub MCP is hard-scoped to the session's repository; calls to any other repo are denied. To read PRs/issues/contents of a different repository, use the jentic execute tool against the github.com API (search the operation, load its schema, execute) or git clone for file content — do not assume the GitHub MCP can reach it.
>
> *Grounded in: reading lago-morph/gascity-prototype PR descriptions required jentic pulls/list because the GitHub MCP rejected the out-of-scope repo.*

**Justification:** Hitting the scope wall mid-task and not knowing the fallback wastes a round-trip and risks reporting a capability as unavailable. Naming jentic as the out-of-scope GitHub path makes it a one-step move.

### Suggestion 6: Defer spec wiring that would reframe an operator-adopted decision — `AGENTS-MD-6189f71f05`
- **Per-rule file**: [./2026-06-01-233/AGENTS-MD-6189f71f05-defer-reframing-spec-wiring.md](./2026-06-01-233/AGENTS-MD-6189f71f05-defer-reframing-spec-wiring.md)

**Proposed agent instruction:**
> **Defer spec wiring that would reframe an operator-adopted decision.** When a freshly-decided brief implies a change to a decision the operator has already adopted, do not silently propagate the change into specs — record the decision, flag the reframing as an explicit operator morning-review item, and defer the spec wiring until the operator re-adopts. A downstream brief acting alone does not relitigate an adopted decision.
>
> *Grounded in: auto-001's rubric reframes operator-adopted D-20 as conditional-on-prevention; the C43/C34/C42/C56/C57 wiring was deferred pending operator re-adoption rather than applied.*

**Justification:** Silently rewriting an adopted decision in the specs would erase the operator's explicit sign-off and bury a risk-tolerance change in a diff. Deferring + surfacing it as a morning-review item keeps the operator's editorial authority intact at trivial cost (one summary bullet + a HANDOFF line).
