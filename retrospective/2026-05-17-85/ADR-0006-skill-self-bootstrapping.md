# ADR 0006: Skill self-bootstrapping

## Context

Skills under `.claude/skills/<name>/` traditionally ship documentation and scripts. The `research-pipeline` skill is more ambitious — it ships GitHub Actions workflows that need to be installed at `.github/workflows/`, a JSON Schema for the catalog at `reference-only/sources.schema.json`, an initial empty catalog `reference-only/sources.json`, and a category list `reference-only/categories.json`.

The traditional install flow ("copy the skill, then manually install the workflows") leaves repos in inconsistent states when users forget the manual step or when templates evolve. Within this session we hit this exact failure mode: workflows weren't installed for the first ~6 PRs (#79-#84) because nobody ran `install-workflows.py`. The user explicitly asked for self-syncing — "all a user has to do is copy the skill into their repo, and setup is done automatically."

## Decision

**Every file the research-pipeline skill depends on must either (a) live inside the skill directory hierarchy, OR (b) be auto-generated by the skill from a template on first run if missing.** The skill is responsible for its own bootstrap; the user just copies the skill directory.

Operationalization:
- The skill ships **templates** for everything it installs into the consumer repo. Templates live under `resources/_<artifact-class>/` (e.g., `resources/_workflows/`, `resources/_catalog/`).
- `scripts/install-<artifacts>.py` reads templates, substitutes `__PLACEHOLDER__` tokens (skill path, repo identity) from the SKILL.md config block, writes to the canonical consumer location, auto-commits.
- The script supports three modes:
  - `--check` → exit 0 if installed == template; exit 1 if missing or drifted; exit 2 if template missing (skill-install defect).
  - (default) → install missing, log drift, don't overwrite.
  - `--force` → overwrite drifted/installed, auto-commit.
- The SKILL.md **pre-flight** runs `--check` on every invocation and runs `--force` on exit 1 **without asking the user**. The install is mechanical and recoverable — every file is regenerated from a template; nothing custom is destroyed.
- A CI gate (`test-research-pipeline.yml`, one of the installed workflows) runs `--check` on every PR touching the skill. Template edits that don't propagate to installed files block the merge.

## Alternatives considered

- **Manual install with user prompt** — "do you want to install workflows? (y/N)". Rejected: leaves repos inconsistent; the user already opted in by copying the skill.
- **Optional self-install with explicit user-trigger** — "run `install-workflows.py` after copying the skill." Rejected: same failure mode as manual; first six PRs forgot to run it.
- **Ship installed files as part of the skill's commit when adopted** — bake installed copies into the skill PR. Rejected: doesn't survive subsequent template edits (drift returns immediately).
- **Generate installed files at runtime, never persist** — workflows-as-code rendered on every invocation. Rejected: GitHub Actions needs the YAML to exist in `.github/workflows/`.

## Consequences

**Positive:**
- Copying the skill into a fresh repo + running the LLM-driven first invocation results in fully-installed infrastructure with no user prompts.
- Template edits in one PR automatically propagate to consumer repos on next pre-flight.
- The CI gate provides a hard failure if a template edit is forgotten — guarantees lockstep.
- The pattern generalizes: any future "self-installing" skill follows the same recipe (see [skill spec](./self-bootstrapping-skill-spec.md)).

**Negative:**
- The "no user prompt" rule means the LLM modifies the consumer repo on first run without explicit consent. Mitigation: the user already consented by copying the skill into the repo; the auto-commits are reviewable in git history.
- The `--force` flag is dangerous for user-edited files. Mitigation: the pattern is strictly for templated artifacts; user-editable config files (like `categories.json` once it has user edits) are handled differently — `--check` reports drift but `--force` refuses without `--clobber`.
- Template/installed lockstep adds CI gate work — every PR touching the skill runs `pytest` + `install-workflows.py --check`.
