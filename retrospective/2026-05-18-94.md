## Part 1 — what happened

### Phase 1 — Round-11 manual drain (16 files → PR #93)

Goal: drain the 16-file mixed-media drop in `research/manual/`. Approach: run `drain.py`, fix whatever it surfaced.

The drain surfaced more than expected. A `README.md` in the drop dir was being flagged every run (no extractable URL). A PDF's `/URL` annotation pointed at the paper's github code repo, not at arxiv — wrong canonical URL. Two MHTML files had `=?utf-8?Q?...?=` MIME-encoded subject lines that ended up as titles in the catalog. And a few files were paired with sidecar "URL of <file>.txt" companions — a manual workaround the user uses when they forget to give an inline URL.

I extended `drain.py` with companion-URL plumbing (parse paired `.txt`, propagate URL to the file, consume companion alongside it), fixed the two MIME-encoded titles by hand (the only direct-jq edits in PR #93), and opened the PR. It merged.

### Phase 2 — bug surfaces in regenerated `sources.md`

After PR #93 merged, the auto-regenerator workflow produced a new `sources.md`. The user noticed: every record I'd just attached an MHTML file to STILL had a stale `[want] no filename` entry on it — the catalog still asked for the URL even though I'd just given the file. The auto-regen had exposed a drain.py bug that PR #93 itself never noticed.

Root cause: `drain.py`'s "attach to existing record" path appended the new file entry but never cleared matching `[want]` placeholders. Promotion logic existed for YouTube transcripts but not for generic page-content wants.

### Phase 3 — user scope: plan-update discipline + 4 more

The user asked me to investigate the bug, then asked separately about plan-update discipline (PLAN.md had drifted over multiple PRs because each catalog-touching commit only sometimes updated it). They gave me four scope questions via `AskUserQuestion`: which discipline mechanism, which subset of three small fixes I'd recommended, whether to fix the bug now or later. Answers: drain.py auto-appends + plan-audit subskill; ALL three small fixes; bug-fix in this PR; never edit JSON directly.

Mid-work they piled on: the want-promotion bug needed a "format-final rule" (MHTML always best; other formats best iff URL terminal extension matches) — that's the user's spec, not mine.

### Phase 4 — implementation marathon (PR #94)

Scope had grown past comfortable working-memory length, so I wrote `.plan-discipline-progress.md` as a checkbox tracker (deleted before commit). Work order:

1. **Want-promotion fix.** `is_format_final(file_format, canonical_url)` + `_purge_satisfied_wants(files, canonical_url)` in drain.py. First version only triggered on format-final attach; the catalog scan caught only 11 of 14 stale records. Tightened to include "same-format `have` already on record" — caught all 14. Added `drain.py --tidy-wants` catalog-wide sweep mode and ran it to fix the 14 records.
2. **README skip-list.** `INVENTORY_SKIP_FILENAMES` in stage 1 (README, NOTES, AGENTS, claude.md, .gitignore).
3. **PDF /URL ranking.** Scoring table: arxiv/doi/openreview > generic > github (-50). Re-fetched record `e588b9bb1a` and migrated the CaMeL PDF to the existing arxiv record `24ca29ee98`, retiring `e588b9bb1a` via `pointer_to`. All record edits via jq, never direct.
4. **RFC 2047 title decode.** `_decode_rfc2047` using `email.header.decode_header` + `make_header`.
5. **Plan-update discipline.** SKILL.md Hard rule #10. New `scripts/update_plan.py` with `update_plan_after_drain(result, plan_path)` — auto-appends Session bullet under §1, row in §10, bumps Version line. drain.py Stage 4c calls it after every material drain. New `scripts/check-plan-consistency.py` (5 checks: version line, latest catalog commit also touched PLAN, recent-N orphan check, round-table mismatch, Version-date staleness). Wired into `lint-sources.sh` as advisory; `--strict` for CI.
6. **Tests.** 25 new tests across `test_drain`, `test_extract_url`, `test_extract_title`, `test_check_plan_consistency`. Suite 219 → 244.

Opened PR #94 ready-for-review.

### Phase 5 — merge conflict (cosmetic, not semantic)

Main had moved during my work: the auto-regen workflow had run on main after PR #93 merged. It used `jq -S 'to_entries | sort_by(.key) | from_entries'` to normalize; my drain.py used `json.dumps(sort_keys=True)`. Both produce sorted output, but jq inserts new keys at the END of an object regardless of input order — so my jq-set `pointer_to` field landed at the end while normalize_and_write expected it alphabetically. Conflict on `sources.json` followed.

Resolved by taking "ours", re-running the canonical normalizer to ensure idempotency, and regenerating `sources.md`. The diff after resolution was 2 lines.

### Phase 6 — user spotted the deeper drift

User: "update the research pipeline skill to fully specify the jq command to use when saving the json file so everywhere will emit the same json in the same order, including the individual entries."

The merge conflict was a symptom: two normalizers existed, and they had diverged subtly. The fix was consolidation, not alignment.

New `scripts/normalize-sources-json.sh` (runs `jq -S '.'` atomically). Pointed every consumer at it: SKILL.md Hard rule #2, both regen workflows (committed + skill-shipped templates), validate-sources error message, 10 jq recipes across `resources/_catalog/` and `_drain/`. drain.py's `normalize_and_write` got a contract docstring naming the helper as the reference. New `test_normalize_sources.py` (3 tests): byte-equivalence Python ↔ jq across 6 fixtures, idempotency, "committed catalog is currently in canonical form."

247 tests passing. PR #94 merged.
