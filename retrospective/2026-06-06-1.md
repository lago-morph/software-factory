## Part 1 — what happened

This session built and shipped a dockerized Gas City prototype (PR #1, merged), added Gate B1 backbone components, and wrote end-user docs plus an example formula. Together these implement the v4 architecture's substrate (Gate B0) and Gate B1.

### Phase 1 — Investigation

The session began by reading the v4 specs and the existing gascity-prototype. The decisive discovery: gc's bead store has a `file` provider (a gc-native JSON store) alongside `bd`/dolt providers, but `gc bd` is **gated** to bd-contract providers, and the bundled gastown pack makes roughly 368 `gc bd` calls. The file provider therefore cannot run the proven gastown fleet. This single constraint drove the entire bead-store design that followed and turned the storage choice from a config tweak into an architectural decision.

### Phase 2 — Built the package

The deliverable is a multi-stage Dockerfile that compiles `gc` from source and installs dolt, bd, node, claude-code, tmux, and socat; a docker-compose; an entrypoint (renders city.toml, provisions local rigs, bridges the bead store, runs `gc start`); a gastown-importing pack; a city.toml; and a `.env`. The image is laptop-portable — it builds everything itself with no pre-staged binaries, unlike the earlier gascity-prototype which `COPY`ed host-built binaries into the image.

### Phase 3 — Bead-store pivots

The bead-store design moved through several positions driven by user clarifications: first "use file"; then the user clarified they wanted a local **server** reachable by the whole compose group via host/port with a non-synced data file; clarified that "socket" simply meant a TCP host/port; clarified they are on a Claude **Max subscription with no API key**; and clarified the laptop is **Windows/amd64, not Apple Silicon** (so arm was dropped). The implementation tried an embedded bd, then a dedicated external Dolt service — which hit a gc external-endpoint bootstrap circularity (`use-external` needs scope metadata that only scope-init creates, and there is no `gc init` external flag) — and finally settled on a **gc-managed Dolt server plus a socat bridge** to `0.0.0.0:3307`. (Managed Dolt binds loopback on a hashed port and rejects host `0.0.0.0`, and pinning `[dolt].port` breaks gc 1.1.1's managed lifecycle, so the bridge republishes the loopback port instead.) The user chose this option over the dedicated-service alternative via AskUserQuestion.

### Phase 4 — In-sandbox build + boot verification

Building and booting the image inside the sandbox caught four real bugs that would have hit the laptop too: (a) an **ICU SONAME mismatch** — building gc on Debian bookworm (ICU 72) then running on ubuntu noble (ICU 74) made gc fail to load (exit 127); fixed by building on the same `ubuntu:24.04` base as the runtime. (b) dolt 2.1.4 had **removed** `--user`/`--password` from `sql-server`; the entrypoint switched to `DOLT_ROOT_HOST=%` for cross-container root. (c) gc 1.1.1 requires a `[providers.claude] base="builtin:claude"` catalog entry. (d) the workspace `name` field is deprecated in city.toml and was moved to `.gc/site.toml`. The agents were deliberately left **tokenless** so they fail auth harmlessly — this verifies the full boot path without spending subscription tokens.

### Phase 5 — Sandbox docker constraints

The sandbox's TLS-inspection proxy blocks HTTPS inside build containers (`curl` exit 60, `git` certificate failure). This was worked around **for verification only** by building a throwaway copy of the Dockerfile patched to trust the sandbox CA — the committed Dockerfile stayed clean with no sandbox hacks. Separately, backgrounding `docker build ... &` inside the tool wrapper produced premature "completed exit 0" notifications while the build was still running, so true completion had to be confirmed via process and artifact checks rather than the wrapper's signal.

### Phase 6 — Gate B1 components

Four parallel subagents built the Gate B1 backbone components: C20 (bead schema), C08/C09 (spec intake), C43 (fence boundary-typing), and C29 (model-floor). Each is self-contained with stdlib-only tests; the orchestrator verified all green and committed them. The session stopped at B0+B1, deferring the B2 eval tier (Inspect AI — the plan's "slow down" hinge) and the B3 bootstrap as work needing focused care.

### Phase 7 — Docs and formula

The session wrote a plain-language `docs/GETTING-STARTED.md` following the human-scoped-deliverables conventions (small Mermaid diagram, corpus vocabulary, no time estimates) covering tmux multi-agent viewing, plus a 4-node `sf-small-task` formula (survey → implement → verify → report).

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory; that file contains exactly two sections — `# agent instruction` (the verbatim rule text the CI/CD assembler concatenates into `AGENTS.md`) and `# justification` (the persuasion text the assembler strips out). This Part 3 mirrors that content inline so the reviewer has every proposed rule plus its justification at decision time.

### Suggestion 1: Match the CGO build base to the runtime base — `AGENTS-MD-75aee78be0`

- **Per-rule file**: [./2026-06-06-1/AGENTS-MD-75aee78be0-match-the-cgo-build-base-to-the-runtime-base.md](./2026-06-06-1/AGENTS-MD-75aee78be0-match-the-cgo-build-base-to-the-runtime-base.md)

**Proposed agent instruction:**

> **Match the CGO build base to the runtime base.** When building a CGO binary in a multi-stage Docker image, build it on the same base image (same distro release) as the runtime stage, or use a binary that links system libraries by SONAME (e.g. ICU); otherwise it will fail to load at runtime with a missing-library error.
>
> *Grounded in: gc built on bookworm (ICU 72) failed to load on noble (ICU 74).*

**Justification:**

This session compiled `gc` in a Debian bookworm builder stage and ran it on an ubuntu noble runtime stage. bookworm ships ICU 72, noble ships ICU 74, and `gc` links ICU by versioned SONAME, so at runtime the loader could not find `libicui18n.so.72` and the binary failed with exit 127 — a failure a build-only check hides entirely and that would have hit the laptop identically. The fix was free: build on the same `ubuntu:24.04` base. One base-image choice versus a silent, laptop-reproducing runtime failure is a strong asymmetry in favor of the rule.

### Suggestion 2: Keep the committed Dockerfile sandbox-clean; verify via a throwaway patched copy — `AGENTS-MD-fc127c82fa`

- **Per-rule file**: [./2026-06-06-1/AGENTS-MD-fc127c82fa-keep-the-committed-dockerfile-sandbox-clean.md](./2026-06-06-1/AGENTS-MD-fc127c82fa-keep-the-committed-dockerfile-sandbox-clean.md)

**Proposed agent instruction:**

> **Keep the committed Dockerfile sandbox-clean; verify via a throwaway patched copy.** Never add sandbox-specific hacks (e.g. trusting a TLS-inspection CA) to a committed Dockerfile meant for laptops; to verify inside such a sandbox, build a throwaway copy patched only for the sandbox and leave the committed file clean.
>
> *Grounded in: the sandbox TLS-proxy blocked in-build HTTPS.*

**Justification:**

The sandbox's TLS-inspection proxy breaks in-build HTTPS (`curl` exit 60, `git` cert failure), so the Dockerfile would not build here without trusting the sandbox CA. Adding that trust step to the real Dockerfile would ship a sandbox-only trust anchor to every laptop user — a security smell and a confusing artifact in a file whose purpose is portability. Patching a throwaway copy costs one extra file and a `cp`-then-patch step; contaminating the shipped file costs every future reader the work of reverse-engineering and stripping environment hacks.

### Suggestion 3: Boot images tokenless to verify without spending subscription — `AGENTS-MD-d66cdaeb5f`

- **Per-rule file**: [./2026-06-06-1/AGENTS-MD-d66cdaeb5f-boot-images-tokenless-to-verify.md](./2026-06-06-1/AGENTS-MD-d66cdaeb5f-boot-images-tokenless-to-verify.md)

**Proposed agent instruction:**

> **Boot images tokenless to verify without spending subscription.** To validate a container's full boot/wiring without spending API/subscription tokens, start it with no auth token so agent processes fail auth harmlessly while servers and schemas still initialize, then assert on the wiring rather than on agent output.
>
> *Grounded in: verified the city boot + bead store with no CLAUDE_CODE_OAUTH_TOKEN.*

**Justification:**

Verifying the image end-to-end means booting the whole stack, and this session needed ~6 rebuild-and-boot passes; running real agents would spend Claude Max tokens on each. Leaving agents tokenless makes them fail auth instantly while the managed Dolt server, socat bridge, bead-store schema, and provider catalog all initialize fully — which is exactly where the dolt `--user` and provider-catalog bugs surfaced. The marginal cost is omitting an env var; the payoff is unlimited verification passes at zero token cost.

### Suggestion 4: Don't trust a wrapper 'completed' signal for &-backgrounded long commands — `AGENTS-MD-78ef4ca164`

- **Per-rule file**: [./2026-06-06-1/AGENTS-MD-78ef4ca164-dont-trust-wrapper-completed-signal-for-backgrounded-commands.md](./2026-06-06-1/AGENTS-MD-78ef4ca164-dont-trust-wrapper-completed-signal-for-backgrounded-commands.md)

**Proposed agent instruction:**

> **Don't trust a wrapper 'completed' signal for &-backgrounded long commands.** When a long command is backgrounded with `&` inside a tool wrapper, the wrapper may report completion immediately; confirm true completion by checking the process and its output artifact, not the wrapper's exit signal.
>
> *Grounded in: a premature "completed exit 0" while `docker build &` was still running.*

**Justification:**

A `docker build ... &` inside the bash tool wrapper produced a "completed exit 0" while the build was still running — the `&` detaches the build, so the wrapper saw the shell return, not the build finish. Acting on that signal means inspecting a half-built image and drawing wrong conclusions about whether a fix landed. The defense is one or two status checks (is the PID alive; does the tagged image exist with a fresh timestamp); the cost of skipping it is confident verification on the wrong artifact.

### Suggestion 5: Surface a storage/tool directive vs hard-dependency fork before building — `AGENTS-MD-fecb431d3f`

- **Per-rule file**: [./2026-06-06-1/AGENTS-MD-fecb431d3f-surface-storage-tool-directive-vs-hard-dependency-fork.md](./2026-06-06-1/AGENTS-MD-fecb431d3f-surface-storage-tool-directive-vs-hard-dependency-fork.md)

**Proposed agent instruction:**

> **Surface a storage/tool directive vs hard-dependency fork before building.** When a user's storage or tooling directive conflicts with a hard dependency of a component you're adopting, surface the fork with AskUserQuestion (naming the trade-off and the rework risk) before building, rather than silently picking one side.
>
> *Grounded in: "use file for the bead store" conflicted with the gastown pack's 368 `gc bd` calls.*

**Justification:**

The directive "use file for the bead store" conflicted with a hard dependency — `gc bd` is gated to bd-contract providers and gastown makes ~368 `gc bd` calls, so file cannot run gastown. Silently honoring the directive yields a package that boots but cannot run its workload; silently overriding it ignores a clear instruction. Surfacing the fork via AskUserQuestion (which ultimately led the user to pick managed Dolt + socat) costs one question; a silent choice costs a full rebuild on a misunderstood constraint.

### Suggestion 6: Container Claude auth is a subscription token, not an API key — `AGENTS-MD-bc19fd6399`

- **Per-rule file**: [./2026-06-06-1/AGENTS-MD-bc19fd6399-container-claude-auth-is-a-subscription-token.md](./2026-06-06-1/AGENTS-MD-bc19fd6399-container-claude-auth-is-a-subscription-token.md)

**Proposed agent instruction:**

> **Container Claude auth is a subscription token, not an API key.** When packaging Claude agents in a container for a subscription user, authenticate with a `claude setup-token` OAuth token (`CLAUDE_CODE_OAUTH_TOKEN`); do not assume or require `ANTHROPIC_API_KEY`.
>
> *Grounded in: the user is on Claude Max with no API key.*

**Justification:**

The user runs on Claude Max with no API key. A container assuming `ANTHROPIC_API_KEY` is unusable for them — they have nothing to supply, and the natural-but-wrong fix imposes a separate paid plan on someone who already pays for Max. The correct path is a `claude setup-token` OAuth token as `CLAUDE_CODE_OAUTH_TOKEN`. Baking this in is free at authoring time; getting it wrong means the user cannot authenticate the agents in the very deliverable they requested.
