## Part 1 — what happened

### Phase 1 — v3 build-guide items 5-6 (PRs #206, #207)

Resumed from a prior-session handoff at `architectures/v3/build-guide/HANDOFF.md`. The task was per-candidate methodology Mermaid diagrams + discipline binding tables + substrate composition diagrams for ten v3 candidate methodologies, with explicit sample-first discipline: produce one candidate as a representative, get sign-off, then produce the other nine. The user identified GF-M as the sample candidate.

The sample shipped in PR #206 with three artifacts (methodology diagram, discipline binding table, substrate composition diagram) plus a ~150-word prose paragraph. The remaining nine candidates shipped in PR #207 with 19 total diagrams (10 methodology + 9 substrate, plus BF-L's six-view Codebase Model interior as a second substrate diagram). All validated. Format held across all candidates because GF-M had locked it.

### Phase 2 — repo-root README primer (PR #208)

The user asked for a primer at the repo root targeted at smart external engineers without the corpus background. Different audience from jonathan@manton.com — defines terms inline (greenfield, brownfield, substrate vs methodology, failure modes, Attractor), reduces author-attribution density. ~8500-word document with 12 Mermaid diagrams (three-layer architecture, Five Levels, plus one methodology diagram per candidate from the build-guide work). Marked explicitly as a snapshot dated 2026-05-29.

### Phase 3 — the pivot conversation

The user posed two pointed questions that pivoted the work substantially. First: "I don't see anything about continuous improvement, evaluation of results, how the spec is refined, nothing." The README primer had missed the closed-loop / continuous-improvement framing that's load-bearing for the 12 principles. Second, after working through whether any of the 10 candidates were strictly incompatible with the 12 principles: "What if instead of figuring out the right methodology, we instead create tooling and the most basic environment that supports the 11 principles other than sharing pipeline files?"

This was the pivot. The corpus's central finding (methodology is the variable; substrate is convergent) was already in the v3 work, but v4 takes it seriously to its logical end: build a principle-bound runtime first, methodologies become pipeline configurations on top. The v3 ten candidates collapse from "ten architectural decisions" to "ten pipeline files to run on the same platform with the same scenarios and the same judge."

### Phase 4 — research and refinement

Several focused subagent dispatches established the technical ground for v4:

- **Overstory adapter status**: archived 2026-05-28 (one day before this session); Warren is the successor. Workers Max-compatible but two subsystems still hard-require API key.
- **Claude Agent SDK Max compatibility**: starts June 15, 2026 with monthly credit. Until then, subprocess automation of `claude` CLI is the supported path.
- **Gas City tmux extractability**: tmux runtime is cleanly extractable (vocabulary-free `runtime.Provider` interface, ~20 Go files, MIT). But for v4 we'd want minimum-viable Gas City install rather than just the tmux runtime.
- **Gas City nine concepts**: detailed mapping to the 12 principles. Smallest install covers principles 1, 2, 3-basic, 4, 9, 10 natively. Gaps at 5, 6, 7, 11.
- **Layer 2-6 coverage in integrated runners** (async during gene-transfusion conversation): OpenHands has full SWE-Bench eval in sibling `benchmarks/` repo; Fabro has CSS model stylesheet; Kilroy has direct CXDB integration; Mammoth/Tracker has `Diagnose`/`Audit`/`Doctor` programmatic diagnosis APIs (strongest Layer 4 transfusion source in survey).
- **Claude Code telemetry**: native OTLP support via env vars, `OTEL_LOG_RAW_API_BODIES=file:<dir>` escape hatch for conversation-shaped storage, all works under Max with no API key.
- **CXDB ingestion**: Apache 2.0 at `github.com/strongdm/cxdb`. Two protocols (msgpack :9009, HTTP :9010). **No native OTLP receiver** — StrongDM explicitly designed against the OTel span-tree model.

### Phase 7 — pack-vs-fork correction (PR #211)

User caught a real inconsistency: "Why did you suggest forking gascity? I thought its whole thing was you could extend with packs." I had recommended forking + vendoring Gas City's `internal/` paths in v4 README and AI-CONTEXT. The recommendation was wrong: Gas City's pack model (TOML + tool node binaries + prompt templates) handles all v4 extension without Go library imports. The `internal/` constraint only matters if you want to use Gas City as a Go library, which v4 doesn't.

I had conflated two earlier-discussed goals: "extend Gas City for v4" (pack-shaped) and "extract the tmux runtime as a standalone library for other pipeline runners" (which would require forking). For v4 only the first matters. PR #211 corrected the framing in both v4 docs with surgical Edit operations, added explicit pack-vs-fork decisions to the AI-CONTEXT decision log.

## Part 3 — agents-file suggestions

### Suggestion 1: Pivot on substantive pushback — `AGENTS-MD-710e0637de`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-710e0637de-pivot-on-substantive-pushback.md](./2026-05-29-211/AGENTS-MD-710e0637de-pivot-on-substantive-pushback.md)

**Proposed agent instruction**:

> **Pivot on substantive pushback.** "When the user pushes back substantively on a recommendation, treat the pushback as a signal that the framing itself may be wrong, not just a request for clarification. Re-examine the load-bearing assumption before defending or restating the original recommendation. If the assumption was wrong, acknowledge it explicitly ('Yes, you're right') before pivoting."
>
> *Grounded in: the v4 pack-vs-fork correction (PR #211) and the BLAKE3-CAS scope-creep correction in the same session.*

**Justification**: The cost of NOT pivoting on substantive pushback compounds — the user gets frustrated, the wrong recommendation propagates to downstream artifacts (the fork recommendation propagated to both v4 README and AI-CONTEXT before correction), and the eventual correction costs more than catching it the first time. The marginal cost of pivoting is roughly two minutes of "let me re-examine the assumption" thinking. Asymmetry is large.

### Suggestion 2: No invented limitations — `AGENTS-MD-73f42f69a0`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-73f42f69a0-no-invented-limitations.md](./2026-05-29-211/AGENTS-MD-73f42f69a0-no-invented-limitations.md)

**Proposed agent instruction**:

> **No invented limitations.** "When evaluating an OSS dependency or architectural option against a defined principle set, do not introduce limitations or 'gaps' that aren't grounded in the agreed principle set. Stay scoped to what the agreed evaluation criteria actually require; do not drag in nice-to-have capabilities (counterfactual branching, runtime sliders) and frame them as deficiencies."
>
> *Grounded in: claiming BLAKE3-CAS counterfactual branching was a 'Gas City gap' when it isn't in the 12 principles; the user called this out as scope creep.*

**Justification**: Inventing limitations introduces decision noise — the user has to spend cognitive cycles separating real constraints from invented ones. In the BLAKE3-CAS case, I dragged a CXDB-vs-Gas-City difference into the evaluation when the 12 principles never required it; the user correctly identified this as scope creep. The marginal cost of staying scoped is essentially zero (one check: "is this in the agreed criteria?"); the cost of invented limitations is conversation overhead and risk of bad decisions made on false constraints.

### Suggestion 3: Check the project's documented extension model before recommending fork — `AGENTS-MD-8106bd98b3`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-8106bd98b3-check-extension-model-before-fork.md](./2026-05-29-211/AGENTS-MD-8106bd98b3-check-extension-model-before-fork.md)

**Proposed agent instruction**:

> **Check the project's documented extension model before recommending fork.** "Before recommending forking or vendoring an OSS dependency, identify the project's documented extension model (packs, plugins, config, etc.) and verify whether the proposed extension can be achieved within that model. Reach for fork only when source-level modification is genuinely required (new core interface, modified internal behavior, urgent bug fix not yet upstream)."
>
> *Grounded in: incorrectly recommending Gas City fork+vendor when the pack model handles all v4 extension needs.*

**Justification**: I recommended forking Gas City + vendoring its `internal/` paths into the v4 docs. The recommendation was wrong because Gas City's whole extension model is packs, which don't require Go library imports. The user caught it explicitly: "I thought its whole thing was you could extend with packs." Forking commits the team to maintaining a fork forever; pack-based extension just means writing TOML and tool-node binaries. The cost of forking when not needed is heavy and ongoing; the marginal cost of checking the extension model is one repo README pass.

### Suggestion 4: Sample-first for multi-part deliverables — `AGENTS-MD-e57e9f3d80`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-e57e9f3d80-sample-first-multi-part.md](./2026-05-29-211/AGENTS-MD-e57e9f3d80-sample-first-multi-part.md)

**Proposed agent instruction**:

> **Sample-first for multi-part deliverables.** "For multi-part deliverables where the parts share a format that needs human validation (per-candidate documents, per-component specs, per-something-N artifacts), ship the first sample as its own PR with the format established but only one part complete. Wait for the PR to merge — treat merge as the signoff signal. Then ship the remaining parts in a second PR. Do not produce N parts simultaneously in an unvalidated format."
>
> *Grounded in: build-guide items 5-6 successfully shipped as PR #206 (GF-M sample) then PR #207 (9 others), avoiding the risk of producing 30 diagrams in a wrong format.*

**Justification**: Build-guide items 5-6 had 30 Mermaid diagrams across 10 candidates. If the format had been wrong, fixing 30 diagrams would have been substantial rework. The sample-first pattern shipped one candidate (GF-M, 3 diagrams), validated by merge, then shipped the other 9 (27 diagrams) confidently. Format held. The marginal cost of the sample-first PR is one extra PR cycle; the cost of producing N parts in a wrong format scales with N.

### Suggestion 5: Dual artifacts for major architecture proposals — `AGENTS-MD-e23b66f5c0`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-e23b66f5c0-dual-artifacts-architecture.md](./2026-05-29-211/AGENTS-MD-e23b66f5c0-dual-artifacts-architecture.md)

**Proposed agent instruction**:

> **Dual artifacts for major architecture proposals.** "For architectural proposals load-bearing for multiple downstream sessions, produce two paired documents: a human-facing approach document (narrative, diagrams, conversational, per human-scoped-deliverables conventions) AND a dense AI-readable context document (structured sections, navigable, decision history with rationale, all alternatives considered, license caveats, config skeletons). Place both in the same directory. Single-artifact docs serve neither audience well."
>
> *Grounded in: v4 architecture proposal shipped as README.md (human) + AI-CONTEXT.md (AI) in PR #209.*

**Justification**: A human reader and an AI agent picking up cold need different things. The human wants narrative, diagrams, decisions framed conversationally. The AI agent wants navigable structure, every decision with rationale, every alternative considered, every license caveat, specific config skeletons. A single document trying to serve both either becomes too dense for humans or too narrative for AI pickup. v4's two-doc structure scales: each can grow without polluting the other. The marginal cost is writing one more file at architecture-proposal time, which is small relative to the proposal's total cost.

### Suggestion 6: Failure-mode coverage matrix for architecture evaluation — `AGENTS-MD-e19d6acad1`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-e19d6acad1-failure-mode-coverage-evaluation.md](./2026-05-29-211/AGENTS-MD-e19d6acad1-failure-mode-coverage-evaluation.md)

**Proposed agent instruction**:

> **Failure-mode coverage matrix for architecture evaluation.** "When evaluating an architectural plan that operates in a domain with a defined catalog of failure modes, produce an explicit coverage matrix mapping every catalogued failure mode against the plan's mechanisms with a four-class status (Addressed, Partial, Gap, Caution). Catalogued failures that go unmapped are silent risks; the matrix makes them visible. Especially flag Caution modes — places where the plan's design could worsen a failure if not actively guarded."
>
> *Grounded in: v4 F-mode coverage analysis (PR #210) mapped all 61 F-modes and surfaced 4 Cautions (F52 Tempting-Wrong-Hybrid, F35 Federation drift, F47 Goodhart, F25 Design starvation) that would have been hidden without the matrix.*

**Justification**: The v4 F-mode coverage matrix surfaced 4 Cautions and 11 Gaps that would otherwise have hidden in the plan's optimism. F52 specifically — v4's emphasis on self-healing + self-optimization is exactly the "more controller patches" Schillace warns against; the matrix forced this admission. Without the matrix, v4 would have shipped with the optimism intact and discovered the cautions during implementation. The marginal cost of producing the matrix is one focused session against the failure-mode catalog; the cost of not producing it is shipping a plan that quietly amplifies known failure modes.

### Suggestion 7: Gene transfusion as default for factory self-build — `AGENTS-MD-3e26c8cca5`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-3e26c8cca5-gene-transfusion-default.md](./2026-05-29-211/AGENTS-MD-3e26c8cca5-gene-transfusion-default.md)

**Proposed agent instruction**:

> **Gene transfusion as default for factory self-build.** "When asking a factory (or any AI agent) to build a complex component, always identify the strongest available exemplar from public OSS or established research and brief the agent to transfuse from that exemplar rather than invent from scratch. Current-generation models port and adapt reliably; they invent unreliably. Record the exemplar's URL in the component's transfused_from metadata."
>
> *Grounded in: v4 plan relies on gene transfusion at every Phase 3+ component (LocalStack for Layer 5 twins, Tracker Diagnose APIs for Layer 4 Healer, DSPy for Layer 6 prompt optimization, etc.), which makes the bootstrap plan credible.*

**Justification**: Gene transfusion is the technique that makes "factory builds factory" actually plausible. Without it, you'd be asking the factory to invent a diagnosis agent, a Healer, a twin scaffolder — all from scratch. Current models struggle at invention; they excel at porting. The v4 plan named specific transfusion sources for every Phase 3+ component, which is what shrinks the engineering risk from "research-frontier work" to "transfusion-and-orchestrate work." The marginal cost is one identification step per component; the asymmetry of value is enormous.

### Suggestion 8: License hygiene table for multi-OSS plans — `AGENTS-MD-7efe35ce8a`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-7efe35ce8a-license-hygiene-table.md](./2026-05-29-211/AGENTS-MD-7efe35ce8a-license-hygiene-table.md)

> **License hygiene table for multi-OSS plans.** "Any architectural plan involving multiple OSS components must include a license hygiene table that lists every project, its license, and specific cautions for restrictive or unusual licenses. ### Suggestion 9: Validate Mermaid diagrams via MCP validator before shipping — `AGENTS-MD-b2e4235346`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-b2e4235346-validate-mermaid-before-ship.md](./2026-05-29-211/AGENTS-MD-b2e4235346-validate-mermaid-before-ship.md)

**Proposed agent instruction**:

> **Validate Mermaid diagrams via MCP validator before shipping.** "Do not ship Mermaid diagrams in human-facing or AI-readable documents without validation via the Mermaid validator MCP tool. Validation catches syntax errors and ensures the diagram will render in the reader's environment. For large batches (≥10 diagrams), validate in parallel batches. ### Suggestion 10: Async subagents for long-running research — `AGENTS-MD-2c34b85dfc`

- **Per-rule file**: [./2026-05-29-211/AGENTS-MD-2c34b85dfc-async-subagents-long-research.md](./2026-05-29-211/AGENTS-MD-2c34b85dfc-async-subagents-long-research.md)

**Proposed agent instruction**:

> **Async subagents for long-running research.** "For research questions expected to take more than a few minutes (multi-source web research, deep repo inspection, multi-project surveys), dispatch the subagent as async background work (run_in_background=true) so main work can continue. Continue the conversation with the user on related topics until the notification arrives. Do not block on long subagent calls when the user is engaged."

The async dispatch pattern let the layer-2-6 coverage survey run in parallel with the gene-transfusion discussion; results integrated into v4 design when they arrived. The marginal cost of async is one `run_in_background=true` parameter; the gain is no conversational dead air on long research.
