## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory at `./2026-05-25-170/AGENTS-MD-<hash>-<kebab-name>.md` — the per-rule file contains exactly two sections: `# agent instruction` (verbatim rule text the CI/CD assembler concatenates into `AGENTS.md`) and `# justification` (persuasion text the assembler strips out).

This Part 3 mirrors that content inline so the retrospective reviewer has every proposed rule + its justification in one place at review-decision time.

### Suggestion 1: TL;DR structure-not-conclusions test — `AGENTS-MD-a1ca4ac935`

- **Per-rule file**: [./2026-05-25-170/AGENTS-MD-a1ca4ac935-tldr-structure-not-conclusions-test.md](./2026-05-25-170/AGENTS-MD-a1ca4ac935-tldr-structure-not-conclusions-test.md)

**Proposed agent instruction**:

> **TL;DR structure-not-conclusions test.** Every line of a top-of-doc `## TL;DR (≤200 words)` section MUST pass the heuristic "would this line need updating if the doc's conclusions changed?" — if yes, rewrite to name a structural element rather than a conclusion. Conclusion-restatement TL;DRs drift silently and fail the regeneration loop the TL;DR-first discipline depends on.
>
> *Grounded in: PR A5 verification subagent flagged the candidate-registry TL;DR's "GF → BF continuity matrix is withdrawn" line as restating a policy conclusion.*

**Justification**: The 2026-05-25 PR A2 lead-agent-inline TL;DR on `architectures/v3/candidate-registry.md` contained a line announcing a policy decision (the GF→BF continuity matrix is withdrawn per DEC-1.b). The fresh-context verification subagent in PR A5 correctly applied the heuristic — would this line need updating if the policy flipped? Yes ⇒ restates content. Fixed in PR A5 by rephrasing to name the structural element (presence of a strikethrough section) rather than the verdict. Without the rule, future TL;DR authors will repeat the failure mode; the PR-A3 end-of-run TL;DR regeneration sub-step cannot mechanically catch this because the regen-subagent does not know what was conclusion vs structure. The marginal cost of the rule is one mental check per line at authoring time. The asymmetric cost without the rule is that the TL;DR-first discipline (the load-bearing context-slimming pattern from CONTEXT-SLIMMING-PLAN.md) silently rots.

### Suggestion 2: Framework-ADR scope-boundary discipline — `AGENTS-MD-a9fb7b42f8`

- **Per-rule file**: [./2026-05-25-170/AGENTS-MD-a9fb7b42f8-framework-adr-scope-boundary-discipline.md](./2026-05-25-170/AGENTS-MD-a9fb7b42f8-framework-adr-scope-boundary-discipline.md)

**Proposed agent instruction**:

> **Framework-ADR scope-boundary discipline.** Common ADRs for substrate primitives that have deferred per-variant ADRs MUST carry an explicit scope-boundary statement in their `## Consequences` section naming (a) the variant landscape, (b) the deferral target (next run / wave / phase), (c) the cross-reference requirement for downstream consumers (e.g., "Phase-N specs MUST reference BOTH this framework ADR AND the candidate's per-variant ADR").
>
> *Grounded in: ADR 0036 (P-30 event registrar substrate) carried the verbatim DISTINCT-primitives scope warning because Round-2 adversarial review caught the risk.*

**Justification**: In the 2026-05-25 Wave 5.1b dispatch, four framework ADRs (P-19, P-28, P-29, P-30) had per-variant ADRs deferred to Wave 5.3 next run. The pre-mortemer Round-2 reviewer surfaced a specific failure mode: a Phase-6 architecture-spec author might cite "the P-30 ADR" for state-machine semantics not realizing the common ADR covers Temporal substrate only — the U-A re-entry and D7-U-1 survival-window state machines are separate per-variant ADRs in Wave 5.3. Each Wave-5.1b subagent's brief explicitly required this scope-boundary text in the Consequences section, and all four complied. Codifying as a project-wide rule means future variant-bearing framework ADRs apply the discipline without per-subagent reminders. Cost: a few sentences in Consequences. Cost without: silent under-reference at Phase 6 where consumers cite the framework but miss the variant.

### Suggestion 3: Full retrospective package; lean-mode is anti-pattern — `AGENTS-MD-1d7c94415e`

- **Per-rule file**: [./2026-05-25-170/AGENTS-MD-1d7c94415e-full-retrospective-package-default-lean-mode-is-anti-pattern.md](./2026-05-25-170/AGENTS-MD-1d7c94415e-full-retrospective-package-default-lean-mode-is-anti-pattern.md)

**Proposed agent instruction**:

> **Full-retrospective-package default; lean-mode is anti-pattern.** The `self-retrospective` skill's full output (main report PLUS sibling-directory SKILL-SPEC, ADR-draft, and per-rule AGENTS-MD files) is the default. Lean-mode (main-report-only) is acceptable only when context budget is mechanically demonstrated to be exhausted, not when it merely feels tight. When in doubt, author the full package — the skill's value is the durable IDs and the standalone-readable sibling artifacts.
>
> *Grounded in: 2026-05-25 retro initially shipped lean-mode citing context; user rebuked, full package authored on second attempt with no actual context exhaustion.*

**Justification**: In the 2026-05-25 Phase-5-entry run, PR B6 first authored a lean-mode retrospective citing context-budget tightness. The user pushed back ("you have plenty of context. Do a proper retrospective"), and the full package was authored on a second attempt with no observed context exhaustion. Lean-mode loses the durable IDs (SKILL-SPEC, ADR, AGENTS-MD hashes), loses the standalone-readable sibling artifacts that downstream CI/CD pipelines depend on, and produces a retrospective whose proposals must be re-derived rather than mechanically adopted. The asymmetric cost without the rule: every retrospective with a tight-feeling context invents reasons to lean-mode; durable IDs erode session-to-session. The marginal cost with the rule: 10-15 minutes of extra authoring per retro when context is in fact tight — a small premium for an artifact that has to survive sessions.

### Suggestion 4: ADR-number-to-filename mapping in subagent dispatch briefs — `AGENTS-MD-8740bd7b0a`

- **Per-rule file**: [./2026-05-25-170/AGENTS-MD-8740bd7b0a-adr-number-to-filename-mapping-in-subagent-dispatch-briefs.md](./2026-05-25-170/AGENTS-MD-8740bd7b0a-adr-number-to-filename-mapping-in-subagent-dispatch-briefs.md)

> *Grounded in: Wave 5.1b ADR 0034 (P-27) authored a forward-reference to a future P-26 ADR at the wrong number (assumed 0033, which was actually P-25); caught at lead-agent aggregation and fixed inline.*

The cross-reference broke and was caught only by `check-internal-refs.py` at aggregation. The cost of the rule is one extra paragraph in the dispatch brief (~10 lines, easily templated). The cost without is one cross-reference bug per fanout, only sometimes catchable by the link checker (if the speculative target file exists at the wrong path, the linker will not flag).

### Suggestion 5: Deferred-work binding-artifact triple — `AGENTS-MD-2adf78e54a`

- **Per-rule file**: [./2026-05-25-170/AGENTS-MD-2adf78e54a-deferred-work-binding-artifact-triple.md](./2026-05-25-170/AGENTS-MD-2adf78e54a-deferred-work-binding-artifact-triple.md)

**Proposed agent instruction**:

> **Deferred-work binding-artifact triple.** When an autonomous run defers in-scope work to a successor run, the deferral MUST appear as a binding constraint in all THREE of: (a) the session handoff doc (`SESSION-HANDOFF-*-close.md`), (b) the morning summary's "what I deliberately did NOT do" section, and (c) the next-run dispatch prompt (or its absence flagged as a follow-up). Divergence among the three is a process bug — pick one source of truth and propagate to the others before run-close.
>
> *Grounded in: 2026-05-25 Wave 5.3 deferral — all three Round-2 adversarial reviewers raised the "binding artifact" concern from different angles (pre-mortem, governance, naive newcomer).*

**Justification**: In auto-005 Round 2, the cost-hawk Round-1 reviewer correctly argued that Phase 5 needed to split across two runs (PR-cap pressure). But the deferral mechanism was unspecified in Round 1 — the Round-2 pre-mortemer, regulator/governance, and naive-newcomer reviewers all independently raised the concern that an informal deferral can dissolve at run boundary (next agent picks up; user changes priority; dispatch prompt drifts). Convergent Round-2 finding became the binding constraint codified in PR B4's handoff doc. Cost of the rule: triple-write the same deferral text. Cost without: deferred work silently disappears across runs.

### Suggestion 6: Dispatch-prompt edit-before-run pattern — `AGENTS-MD-a43c9584c9`

- **Per-rule file**: [./2026-05-25-170/AGENTS-MD-a43c9584c9-dispatch-prompt-edit-before-run-pattern.md](./2026-05-25-170/AGENTS-MD-a43c9584c9-dispatch-prompt-edit-before-run-pattern.md)

**Proposed agent instruction**:

> **Dispatch-prompt edit-before-run pattern.** When the user surfaces a quality concern about a dispatch prompt for an upcoming autonomous run, commit the modification to the prompt file in its own PR BEFORE kicking off the run — do not fold the modification into the run's first work-PR. The edit is then mechanically auditable (the run's scope envelope can cite the prompt at a stable commit) and the run benefits from the improvement.
>
> *Grounded in: 2026-05-25 PR #158 added the Phase-A verification step to `next-agent-prompt-phase-5.md` before the run started; the verification caught the registry-TL;DR concern in PR A5.*

**Justification**: PR #158 was a tiny standalone PR that added a verification subagent step to the dispatch prompt. The pre-run merge meant the scope envelope (PR A0) could cite the prompt at a stable commit; the verification step itself caught a real quality issue at PR A5. If the modification had been folded into the first work-PR, the audit trail would have been muddier (mixing prompt-edits with first phase work) and the verification step would not have been part of the recorded scope. Cost: one extra PR per dispatch-prompt modification. Cost without: the modification becomes a "by the way" commit in a larger PR, audit-trail erosion.
