# P-24 — Change-history / attribution store (append-only, signed)

**Dispatch tier:** per-primitive (designed-system).
**Claimed by:** [BF-S/S-4](../tracks/brownfield-substrate-first.md#11-substrate-primitive-classes-the-load-bearing-layer); composed by [BF-L Codebase Model historical view](../tracks/brownfield-legacy-ingestion-first.md) as one of the six views.
**Registry buildability scope:** designed-system — git plumbing is commodity; the per-symbol-granularity uplift via the codebase index (P-22) and the dual-signing model for factory-authored vs. human-authored events is the design content.
**Research-grade-uncertainty flag:** none.

## Contract restatement

An append-only, tamper-evident store of per-symbol attribution events at fine granularity: for every named symbol the codebase index (P-22) knows about — function, class, method, type, top-level binding, schema field — the store answers "show me the ordered list of change events that touched this symbol, with author identity (human / agent / model), parent-commit linkage, signature status, and the surrounding diff slice." Each event is signed (mitigating F32 unsigned-coordination); the log is append-only at the substrate layer (forbidding tombstone rewrites that would defeat F54 goal-subversion forensics); per-cycle / per-agent / per-model attribution is structurally required, not best-effort (closing the F14 widened forensic-reconstruction gap). Queries served: symbol → ordered history; commit → symbol-set touched; (agent-id, time-window) → diffs authored; (model-id, time-window) → diffs reviewed-or-authored; verification status → which events fail signature check.

## Construction path

**Primary tool: Git plumbing + `git blame --line-porcelain` + Sigstore/cosign keyless signing + a Postgres `attribution_events` projection table.** Integration sentence: git's object model is already the append-only signed substrate the corpus assumes (commit hashes form a Merkle DAG; `git verify-commit` already validates GPG/SSH signatures on commits with the existing per-commit author trailer), so P-24's substrate layer is `git fast-import`-fed into a bare mirror that runs `git verify-commit` on every push and rejects unsigned commits — turning git itself into the append-only signed log without inventing a new storage layer. The **per-line-porcelain blame** output is run once per (commit, file) into a worker that calls P-22's symbol-range index (`symbol → file_path × line_range`) and joins line-blame to symbol, producing `attribution_events(symbol_id, commit_hash, author_id, agent_id, model_id, signature_status, parent_event_id, diff_slice, ts)` rows in Postgres; the join is the per-symbol uplift git cannot do natively.

**Secondary tool for factory-authored events: Sigstore `cosign sign-blob --identity-token`.** Integration sentence: events produced by factory agents (not by humans pushing commits through git's normal path) — e.g., a builder agent's intermediate diff that becomes a commit, a judge agent's review verdict on a diff, a knowledge-promotion event from the BF-S §1.2 step 8 — are signed with cosign keyless against an OIDC identity issued to the agent's run-token (one identity per (cycle, agent-role, model-id) triple), and the cosign bundle is stored in the event row's `signature_blob` column; `cosign verify-blob` reproduces the chain at audit time. This gives the factory the same Sigstore-grade transparency-log property as a published container image without standing up a separate transparency log instance.

## Per-symbol granularity gap (the design content)

Git is per-line and per-file; the contract is per-symbol. Bridging requires P-22's symbol-range index as a hard dependency: on every commit, the ingest worker queries P-22 for `(file_path, commit_hash) → [(symbol_id, line_start, line_end), ...]`, runs `git blame --line-porcelain` for the affected files, and groups blame lines by symbol range to attribute the symbol's change to that commit. When symbol ranges shift across commits (refactor, rename, move), P-22's incremental rename-tracking (treesitter + LSP `textDocument/rename` semantics where available, syntactic-similarity fallback otherwise) emits a `symbol_renamed(old_id, new_id)` edge that P-24 stores as a `parent_event_id` link — preserving the per-symbol history across the rename. This integration is the load-bearing design work; without P-22's symbol index and its rename-edges, P-24 degrades to per-file attribution and stops satisfying its contract.

## Signing model

Three signer classes, each attesting to a different fact: (1) **human git author** — standard `git commit -S` (GPG/SSH), attests "this human authored this diff"; verified by `git verify-commit` at ingest. (2) **Factory agent** — cosign keyless against the agent's OIDC run-token, attests "this (cycle, agent-role, model-id) produced this event at this time"; verified by `cosign verify-blob` against the run-token's expected issuer. (3) **Factory itself** — a long-lived factory key signs the *chained hash* over the `attribution_events` table at board-report cadence (per BF-S §1.1 S-4 / F43 RSI Board-Visibility Gap), attesting "no event below this point has been retroactively modified." Verification surface is the union: a query that returns events with mixed signer classes returns each event's `signer_class` so the caller can apply per-prong audit logic.

**BF-S/S-4** claims P-24 as a substrate primitive whose append-only signed contract is constitutive (per BF-S §1.1 S-4: required for F35, F43, F54, F58; "mitigating F32 mail-injection / unsigned coordination"). **BF-L** composes the same primitive into the Codebase Model's *historical view* — one of the six integrated views (per BF-L §2 §2.8: "historical — commit cadence per area, churn hotspots, attribution") — so BF-L's "Codebase Model" is a higher-level artifact for which P-24 is the storage substrate, not a competing primitive. **No same-vs-distinct verdict rendered** (per Phase-3.5 dispatch-shape constraints); the question of whether BF-L's historical view is just-P-24 plus a query API, or whether it adds independent design content (churn metrics, per-area cadence aggregations), is a Phase-4.2 question.

## Corpus-why citation

BF-S §1.1 names S-4 against four brownfield-critical / brownfield-high F-modes: **F14** (attribution collapse, widened to forensic reconstruction — Phase-1 bias-guard CANDIDATE-10 absorption: "swarm-built artifact fails, the operator's path back to root cause may require forensic reconstruction across N worktrees, M mail threads, K interleaved timelines"; brownfield-high); **F32** (mail-injection / unsigned coordination — signing closes the trust boundary at the storage layer rather than at the calling agent's good behaviour, the F53 voluntary-discipline argument applied to attribution); **F43** (RSI Board-Visibility Gap, brownfield-high — Caremark prong-1 board reporting requires demonstrable per-cycle attribution of which control ran on which artifact); **F54** (goal subversion across cycles, brownfield-critical — Kahana's multi-cycle objective-drift becomes detectable only with immutable per-cycle agent-and-model attribution to compare across cycles); secondary contributions to **F35** (federation-as-family drift) and **F58** (runtime/design-time compliance split, brownfield-high — runtime attribution is the evidence the design-time conformity assessment cannot self-produce). The corpus-specific problem P-24 solves is the brownfield-inherited "existing codebase already has unattributed agent contributions; the gap is inherited" (F14 brownfield severity rationale) — every cycle from day-0 forward must contribute structurally-required attribution, not retroactively-reconstructed attribution.
