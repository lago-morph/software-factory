# U-B invariant-authoring sub-track — Wave 4.5 deliverable

**Charter.** Phase-4 Wave-4.5 deliverable per [auto-002 Round 2](../decisions/auto-002-ub-path.md) (U-B invariant-authoring full sub-track authorized after smoke-test pass) and [auto-004 Round 2 §Wave 4.5](../decisions/auto-004-phase-4-dispatch-shape.md). Scale the [P-31 smoke-test recipe](../primitives/P-31-smoke-test-invariants.md) from 1-per-pair to **≥3 non-trivial machine-checkable cross-layer invariants per layer-pair, ≥15 total** across the five U-B layer-pairs (L0↔L1, L1↔L2, L2↔L3, L3↔L4, plus the long-distance L0↔L4).

**Method.** For each pair: (1) reference the smoke-test invariant by relative link; (2) add ≥2 additional invariants in the same (a)–(f) envelope shape; (3) maintain the smoke-test's discipline that *referential-integrity disqualifies* — every invariant must constrain *substance* (the content of one layer's artifact relative to another's content), not merely *presence* of a link.

**Honesty discipline carried forward.** If a pair fails to scale beyond 2, the gap is named. The fallback rule per [`u-b.md` §5](../substrate-requirements/u-b.md) and [auto-002 Round 2](../decisions/auto-002-ub-path.md) is explicit: any per-pair shortfall reverts to the smoke-test's 1-per-pair baseline with `accept-RG` flag on the substantive-drift portion for that pair. No fabricated invariants without corpus citation count.

## §1 L0 ↔ L1 — Standards ↔ Architecture

### Reference: smoke-test invariant L0-L1-1

The smoke-test invariant L0-L1-1 (three-RSI-control architectural-coverage) at [`P-31-smoke-test-invariants.md` §1](../primitives/P-31-smoke-test-invariants.md) requires that every L0 `RSIDeclaration{meets_three_part_test: true}` is covered by three L1 components whose `realizes-AILCCP-control` field enumerates the three Kahana-named controls (Human Approval Gate, Sandboxing, Immutable Logging). Corpus: [`31-caremark-rsi-board-exposure`](../../../research/31-caremark-rsi-board-exposure.md) §5; [`followup/10-governance`](../../../research/followup/10-governance.md) §6a.B. The smoke-test verdict: non-trivial (substance-coverage, not link-presence).

### Additional invariant L0-L1-2: lifecycle-phase ownership coverage

(a) **Cross-layer constraint statement.** For every L0 `LifecyclePhaseRequirement` object (one per AILCCP life-cycle phase: *Scoping & Design, Data Preparation, Modeling, Evaluation & Red Teaming, Deployment, Operations & Monitoring, Maintenance, Incident Response, Retraining, Decommissioning & Archiving*), the L1 `ArchitectureSpecification` must declare at least one component whose `owner` field is in the AILCCP-canonical ownership set `{Product, UX, Legal, Risk, ML-Engineering, Data-Science, QA, Security, SRE, Communications}` and whose `phase-coverage[]` array contains that phase's ID. The invariant fails if any declared lifecycle phase has zero L1 components claiming ownership, **or** if the declared owner role is outside the canonical AILCCP set.

(b) **Corpus citation.** [`followup/10-governance`](../../../research/followup/10-governance.md) §6a.C (Kahana, *Turning AI Governance Into Operational Infrastructure*, 2026-04-05). Verbatim primary: *"The ownership model spans Product, UX, Legal, Risk, ML Engineering, Data Science, QA, Security, SRE, and Communications, because AI governance requires coordinated action across disciplines."* Same source §6a.C also names the per-phase measurable metrics (e.g., *"Operations and Monitoring tracks mean time to repair, drift alerts per month, and SLO attainment"*), giving the invariant its per-phase teeth — an architecture that declares a phase but assigns no owner has no addressable accountability surface.

(c) **Construction sentence.** OPA + Rego against P-28 typed-object store. The Rego rule `data.invariants.l0_l1.lifecycle_phase_ownership.violation[result]` iterates `L0.LifecyclePhaseRequirement` objects, queries the L1 graph for components with `phase-coverage[]` containing the phase ID and `owner ∈ AILCCP_canonical_roles`, and emits a `LayerDriftEvent` if any phase has empty coverage or any owner is outside the canonical set. The canonical role set is L0-versioned (the AILCCP catalogue is an L0 artifact); a future AILCCP revision (Kahana flags ongoing expansion) updates the bundle, not the rule.

(d) **Positive example.** L0 declares ten `LifecyclePhaseRequirement` objects (one per AILCCP phase). L1 declares `EvalRunner{phase-coverage: ["evaluation-red-teaming"], owner: "QA"}`, `DataPrepValidator{phase-coverage: ["data-preparation"], owner: "Data-Science"}`, ... and so on for each of the ten phases. Every phase has at least one owner from the canonical set. Invariant passes.

(e) **Negative example.** L0 declares the ten phases. L1 covers nine — but `incident-response` has no owning L1 component. Or worse: `incident-response` is covered by `AutoTriageAgent{owner: "AgentOps"}`, where `"AgentOps"` is not in the AILCCP canonical role set. Invariant fires `LayerDriftEvent{layer-pair: "L0-L1", invariant-id: "lifecycle_phase_ownership", missing-phase-or-noncanonical-owner: ["incident-response"], severity: high, recommended-handback: L1-architect}`. This catches the *"who owns this when it breaks?"* Caremark question at architecture-design time rather than at incident time.

(f) **Honest verdict.** **Non-trivial.** This is not referential integrity — the invariant constrains *which set* the L1 component's `owner` field draws from (the AILCCP-canonical role enumeration), not merely whether the field is non-null. The AILCCP catalog supplies the substantive constraint: a renamed owner role outside the canonical set fails the check. Cross-references F58 (runtime/design-time compliance split) — declaring an owner role that does not map to an audit-able discipline at runtime *is* the F58 mechanism at architecture-design time.

### Additional invariant L0-L1-3: design-choices-disable-monitoring prohibition

(a) **Cross-layer constraint statement.** For every L1 component declaring `capability: "self-modification"` or `capability: "code-generation-to-skills-dir"` (the corpus-named RSI capabilities), the L1 graph must contain at least one sibling component with `governance-visibility: "monitorable-by-board"` whose `monitors[]` array contains the self-modifying component's ID. Additionally — and this is the substance-arm — the monitor's `evidence-trail-class` field must be in `{board-quarterly, regulator-audit-grade}` (not in `{operator-discretionary, opt-in-telemetry}`). The invariant fails if any self-modifying L1 component lacks a board-visible monitor, **or** if the monitor's evidence-trail-class is at the operator-discretionary tier.

(b) **Corpus citation.** [`31-caremark-rsi-board-exposure`](../../../research/31-caremark-rsi-board-exposure.md) §2 (Boeing/Hughes line, *In re Boeing Co. Derivative Litig.* 2021). Verbatim primary: *"Design choices that disable board-level monitoring can ground Caremark liability. In an RSI context, those design choices include allowing self-modification that bypasses change-management workflows, or architecting systems so that code and model histories cannot be reconstructed for board or regulator-facing investigations."* (Kahana primary; emphasis on architectural-level design choices.) Reinforcing source: [`31-caremark-rsi-board-exposure`](../../../research/31-caremark-rsi-board-exposure.md) §5 *"trappings vs substance"* — operator-discretionary telemetry is precisely a *trapping*: a monitor exists on paper but is not in the board's actual reporting line.

(c) **Construction sentence.** Postgres recursive CTE + OPA enum check, against P-28. The CTE walks the `monitors[]` edge from any L1 component back to all L1 components declaring an RSI-class `capability`; the result set is the un-monitored RSI components. OPA evaluates the enum check on `evidence-trail-class` against the canonical board-grade set (sourced from L0). Combined output: `LayerDriftEvent{layer-pair: "L0-L1", invariant-id: "design_disables_monitoring", offender-component: <ID>, defect: "no-board-grade-monitor" | "operator-discretionary-monitor-only", severity: critical, recommended-handback: L0-standards-author-or-L1-architect}`. Integration: triggered on every commit to an L1 object declaring an RSI capability; Patrol cadence sweeps for drift in the `evidence-trail-class` value.

(d) **Positive example.** L1 contains `AutoRefactorAgent{capability: "self-modification", id: "C-AGT-007"}`. L1 also contains `BoardAuditChannel{governance-visibility: "monitorable-by-board", monitors: ["C-AGT-007"], evidence-trail-class: "regulator-audit-grade"}`. Invariant passes.

(e) **Negative example.** L1 contains the same `AutoRefactorAgent{capability: "self-modification"}`. The only monitor pointing at it is `OperatorDashboard{governance-visibility: "monitorable-by-board", evidence-trail-class: "operator-discretionary"}` — i.e., the dashboard *exists* (referential integrity passes), but operators are not obligated to consult it and there is no audit record of consultation. This is the verbatim Hughes-style *trappings of oversight* trap. Invariant fires `LayerDriftEvent{invariant-id: "design_disables_monitoring", offender-component: "C-AGT-007", defect: "operator-discretionary-monitor-only", severity: critical, recommended-handback: L1-architect}`.

(f) **Honest verdict.** **Non-trivial.** The arm "every self-modifying component has *some* monitor" is referential integrity. The substantive arm is the enum-class check on `evidence-trail-class`: the difference between `regulator-audit-grade` and `operator-discretionary` is the difference between *substance* and *trappings* per Kahana's Hughes-line reading. Catches a Caremark-named architectural anti-pattern that is corpus-anchored verbatim.

### (Optional) Additional invariant L0-L1-4: AILCCP enabling-risk transparency coverage

(a) **Cross-layer constraint statement.** For each of the three L0 `IdentifiedRiskRequirement` objects rated severity `medium-enabling` (Kahana's specific class: transparency-and-explainability gaps that are *force multipliers* for higher-severity harms), the L1 graph must contain at least one component with `realizes-AILCCP-principle: "Transparency"` OR `realizes-AILCCP-principle: "Explainability"` (AILCCP #12) whose `signal-export[]` field declares the artifact-class the monitor emits. The invariant fails if any of the three medium-enabling risks has no Transparency/Explainability-realizing L1 component, or if the component's `signal-export[]` is empty (the *trappings* arm).

(b) **Corpus citation.** [`followup/10-governance`](../../../research/followup/10-governance.md) §6a.C (Kahana, *Turning AI Governance Into Operational Infrastructure*). Verbatim primary: *"As I see it, one of the more distinctive ideas in the framework is the 'enabling risk' concept. The three risks rated Medium severity are transparency and explainability gaps that function as force multipliers for other, more serious harms. A system that lacks Explainability makes every other harm harder to detect, harder to diagnose, and harder to remediate."* Cross-citation: Kahana §6a.C also states *"A factory should treat its three lowest-severity (but enabling) gaps as governance priorities equal to its highest-severity harms."*

(c) **Construction sentence.** OPA + Rego against P-28. Rule iterates L0 `IdentifiedRiskRequirement` objects with `severity_tag = "medium-enabling"` and joins to L1 components with the matching AILCCP-principle realization; emits a `LayerDriftEvent` if the join is empty or `signal-export[]` is empty. Integration: triggered on every L0 risk-catalogue update.

(d) **Positive example.** L0 declares `IdentifiedRiskRequirement{id: "R-MED-3", risk-class: "explainability-gap", severity-tag: "medium-enabling"}`. L1 contains `XAIDashboard{realizes-AILCCP-principle: "Explainability", signal-export: ["per-decision-rationale", "feature-importance"]}`. Invariant passes.

(e) **Negative example.** L0 declares the same risk. L1 contains `XAIDashboard{realizes-AILCCP-principle: "Explainability", signal-export: []}` — the component exists, the field is correctly tagged, but the dashboard exports nothing. Fires `LayerDriftEvent{invariant-id: "enabling_risk_coverage_empty_export", risk: "R-MED-3", severity: high, recommended-handback: L1-architect}`.

(f) **Honest verdict.** **Non-trivial.** The substantive arm is the `signal-export[]` non-emptiness check coupled to the AILCCP-principle enum match. Catches the *enabling-risk* failure mode Kahana names verbatim — the architecture *declares* Transparency/Explainability coverage but supplies no signal. This is corpus-named as a *force multiplier* for higher-severity harms; the invariant therefore defends against a substantive (not referential) gap.

## §2 L1 ↔ L2 — Architecture ↔ Spec

### Reference: smoke-test invariant L1-L2-1

The smoke-test invariant L1-L2-1 (`protects` linkage + binding-shape match) at [`P-31-smoke-test-invariants.md` §2](../primitives/P-31-smoke-test-invariants.md) requires every L1 `ArchitectureSpecification.rules[].id` to be `protects:`-targeted by an L2 spec object, *and* requires the binding shape (rule's `enforcement` field vs metric's `type` field) to match — catching the El Kaim *false specification* anti-pattern. Corpus: [`14-el-kaim-book-intent-and-spec-authorship`](../../../research/14-el-kaim-book-intent-and-spec-authorship.md) §15 + §17 ¶6.

### Additional invariant L1-L2-2: prohibited-action → EARS Unwanted-Behaviour coverage

(a) **Cross-layer constraint statement.** For every L1 `ArchitectureSpecification.agents[].prohibitedActions[]` entry — each one is a structured negative permission ("this agent shall not …") — the L2 spec must contain at least one acceptance criterion authored in the EARS *Unwanted Behaviour* pattern (keyword `If/Then`) whose subject is the same agent and whose system-response forbids the same action class. The substance arm is on the EARS *pattern* (must be the If/Then unwanted-behaviour form, not a Ubiquitous "shall" — which is positive, not prohibitive): the invariant fails if the matching L2 criterion is authored in any of the other four EARS patterns (Ubiquitous, State-driven, Event-driven, Optional-feature) because none of those four expresses *prohibition with consequence*.

(b) **Corpus citation.** Anchor 1: [`14-el-kaim-book-intent-and-spec-authorship`](../../../research/14-el-kaim-book-intent-and-spec-authorship.md) §13 (El Kaim, Ch8 §5). Verbatim primary on the L1 typed-object: *"agents — each with id, name, permittedActions, prohibitedActions. This is where the AI-action boundary lives."* Anchor 2: [`25-requirements-engineering-foundations`](../../../research/25-requirements-engineering-foundations.md) §2.2 (Mavin EARS). Verbatim primary on the prohibitive pattern: *"5. Unwanted behaviour (keywords If/Then): If \<trigger\>, then the \<system name\> shall \<system response\>. Example: 'If an invalid credit card number is entered, then the website shall display please re-enter credit card details.'"* The four other EARS patterns do not express prohibition; the `If/Then` pattern is the corpus-named shape for unwanted-behaviour spec.

(c) **Construction sentence.** Postgres CTE + a small EARS-pattern classifier function against P-28. The CTE joins L1.agents[].prohibitedActions[] to L2 acceptance criteria by subject (agent ID); the classifier function tags each L2 criterion with its EARS pattern (parser identifies the keyword and clause shape: deterministic for the five named patterns); the join filter requires `pattern = "If/Then"`. Output: orphaned prohibitions (no L2 If/Then coverage) and shape-mismatched coverage (L2 criterion exists but authored in a non-prohibitive pattern). Both emit `LayerDriftEvent{layer-pair: "L1-L2", invariant-id: "prohibition_ears_pattern_mismatch", ...}`.

(d) **Positive example.** L1 contains `agents.AITriageAgent{prohibitedActions: ["write-to-production-patient-record"]}`. L2 contains the acceptance criterion *"If the AITriageAgent attempts to write to a production patient record, then the system shall block the write and emit a `prohibited-action-attempt` event."* — classified as EARS If/Then. Invariant passes.

(e) **Negative example.** L1 contains the same prohibition. L2 contains *"The AITriageAgent shall only write to draft patient records."* — classified as EARS Ubiquitous (positive permission framing). The Ubiquitous pattern *appears* to cover the prohibition (every reviewer reading it nods), but it is the wrong shape: it permits the agent to do something rather than forbidding the agent from doing the prohibited thing, and downstream verifiers cannot trigger an "unwanted-behaviour-fired" assertion against a Ubiquitous criterion. This is structurally the El Kaim *false specification* (the structured form is correct; the binding shape is not). Invariant fires `LayerDriftEvent{invariant-id: "prohibition_ears_pattern_mismatch", agent: "AITriageAgent", prohibited-action: "write-to-production-patient-record", l2-criterion-pattern: "Ubiquitous", required-pattern: "If/Then", severity: high, recommended-handback: L2-spec-author}`.

(f) **Honest verdict.** **Non-trivial.** Referential integrity ("every prohibition has *some* L2 criterion") is a tier below. The substance arm constrains the *grammatical shape* of the L2 criterion against the EARS pattern table — Mavin's grammar itself supplies the substantive distinction (the If/Then pattern is the unique unwanted-behaviour shape). Catches the cross-layer anti-pattern where prohibitions are quietly absorbed by positive-framing specifications and downstream evaluators have no negative-case assertion to fire.

### Additional invariant L1-L2-3: dataObject authority → evidence-obligation trace test

(a) **Cross-layer constraint statement.** For every L1 `ArchitectureSpecification.dataObjects[]` entry tagged `classification ∈ {"regulated", "decision-support-evidence", "patient-data"}` (or any L0-declared regulated-data class), the L2 spec must satisfy El Kaim's *trace test*: every evidence-obligation the data class entails must trace to a `record-of-existence` target. Concretely: the L1 dataObject's `authority` field points at a system-of-record component; the L2 rule(s) protecting that dataObject must each carry an `evidenceSources` field naming a concrete log/register identifier (not the empty list, not the string `"TBD"`, not a free-text description). The invariant fails on (a) empty `evidenceSources`, (b) `evidenceSources` referencing only natural-language descriptions not bound to a typed-object ID, or (c) the named log/register not existing in the P-28 store.

(b) **Corpus citation.** [`14-el-kaim-book-intent-and-spec-authorship`](../../../research/14-el-kaim-book-intent-and-spec-authorship.md) §17 ¶6 (El Kaim Ch8 §9, false-specification failure mode). Verbatim primary: *"A document that uses the structured form, names the right fields, and references the right decisions, but whose constraints cannot actually be checked and whose evidence cannot actually be produced. This is worse than no specification at all, because it gives governance forums the appearance of control without the substance. The discipline that prevents false specifications is end-to-end execution: **every conformance rule must trace to a check that runs, every evidence obligation must trace to a record that exists, and every escalation trigger must trace to a path that activates**."* Reinforcing: [`14-el-kaim-book-intent-and-spec-authorship`](../../../research/14-el-kaim-book-intent-and-spec-authorship.md) §13 names the `rules.evidenceSources` field on the ArchitectureSpecification typed object verbatim.

(c) **Construction sentence.** Postgres recursive CTE + existence-check against P-28. CTE walks L1.dataObjects[] → L1.rules[].protects → L2.rules.evidenceSources[], filters to dataObjects with regulated classification, and checks that the eventual `evidenceSources[]` array (a) is non-empty, (b) every element is a typed-object ID resolving in P-28, and (c) the resolved object's `class` is in `{ImmutableLog, AppendOnlyRegister, WORM-bucket-ref, AuditChannel}`. Violations emit `LayerDriftEvent{invariant-id: "false_specification_evidence_trace", offender: <L1-dataObject-or-L2-rule>, defect: <empty | unresolvable-ID | wrong-class>, severity: high, recommended-handback: L2-spec-author}`. Integration: triggered on every L1.dataObject commit and on every L2.rule commit; Patrol sweeps the join nightly to catch drift caused by typed-object deletions upstream.

(d) **Positive example.** L1 contains `dataObjects.PatientCase{authority: "S-PVCASE", classification: "patient-data"}`. L2 contains `rules.AccessLoggingRule{protects: "RULE-PV-021", evidenceSources: ["LOG-PV-AUDIT-001"]}` where `LOG-PV-AUDIT-001` resolves to an `ImmutableLog` typed object in P-28. Trace: dataObject → rule → evidenceSource → resolvable typed-object-ID → class is in allowed set. Invariant passes.

(e) **Negative example.** L1 contains the same `PatientCase`. L2 contains `rules.AccessLoggingRule{protects: "RULE-PV-021", evidenceSources: ["written audit trail per HIPAA"]}` — `evidenceSources` is populated, but it contains a *natural-language description*, not a typed-object ID resolving in P-28. The structured-form check passes (the field is non-empty); the trace test fails (the description does not resolve). This is verbatim the *false specification* — *"references the right decisions, but whose ... evidence cannot actually be produced."* Invariant fires `LayerDriftEvent{invariant-id: "false_specification_evidence_trace", offender: "rules.AccessLoggingRule", defect: "unresolvable-ID", severity: critical (because classification=patient-data), recommended-handback: L2-spec-author}`.

(f) **Honest verdict.** **Non-trivial.** The check is exactly El Kaim's named substance test (*"every evidence obligation must trace to a record that exists"*) — not referential integrity, but a *resolvability + class-membership* test against the typed-object store. Catches a corpus-anchored anti-pattern that bypasses the structured-form check.

### (Optional) Additional invariant L1-L2-4: variation envelope → complexity-diagnosis field

(a) **Cross-layer constraint statement.** For every L1 `ArchitectureSpecification.variation.allowed[].condition` entry (the *governed variability* envelope per El Kaim Ch8 §5), the L2 spec describing the affected scope must carry a `complexity-diagnosis ∈ {Simple, Complicated, Complex, Complex-Adaptive}` field (INCOSE Complexity Primer §5.1). The substance arm: if `complexity-diagnosis = Complex` or `Complex-Adaptive`, the L2 spec must additionally carry a `region-of-outcome` field (not a point criterion). The invariant fails if the complexity-diagnosis is missing on a variation-permitted scope, or if a `Complex`-classified scope has only point-shaped acceptance criteria.

(b) **Corpus citation.** Anchor 1: [`14-el-kaim-book-intent-and-spec-authorship`](../../../research/14-el-kaim-book-intent-and-spec-authorship.md) §13 (`variation.allowed[].condition` field). Anchor 2: [`25-requirements-engineering-foundations`](../../../research/25-requirements-engineering-foundations.md) §5.4 + §5.6 (INCOSE Complexity Primer principle #12). Verbatim primary on the region-of-outcome principle: *"Focus on desired regions of outcome space rather than specifying detailed outcomes… Instead of zeroing in on an exact solution, focus on what range of solutions will have the desired effects, and design to avoid forbidden ranges."* Cross-citation: F39 (point-spec/region-mismatch) is the exact failure mode this invariant defends against at the L1↔L2 layer-pair.

(c) **Construction sentence.** Postgres + a small enum-check predicate. CTE walks L1.variation.allowed[] → affected L2 spec scope (resolved via `targetScope` reference) → checks L2.complexityDiagnosis presence and (conditionally) L2.regionOfOutcome presence. Violations emit `LayerDriftEvent{invariant-id: "variation_complexity_diagnosis_missing", offender: <L2-scope>, defect: <missing-diagnosis | complex-without-region>, severity: medium, recommended-handback: L2-spec-author}`.

(d) **Positive example.** L1 contains `variation.allowed[{type: "regional-extraction-pipeline", authority: "S-AI-TRIAGE", condition: "regional_dataset_present"}]`. The L2 spec for `S-AI-TRIAGE` carries `complexity-diagnosis: "Complex"` and `region-of-outcome: {"per-region accuracy in [0.85, 0.95] and reviewer-agreement above 0.7"}`. Invariant passes.

(e) **Negative example.** Same L1 variation entry. The L2 spec for `S-AI-TRIAGE` carries `complexity-diagnosis: "Complex"` but only a point criterion `field-level-accuracy ≥ 0.92`. Invariant fires `LayerDriftEvent{invariant-id: "variation_complexity_diagnosis_missing", defect: "complex-without-region", severity: medium, recommended-handback: L2-spec-author}`. This is F39 caught at the architecture-spec interface rather than at L4 reviewer-panel time.

(f) **Honest verdict.** **Non-trivial.** Substance is constrained on two arms — the enum value (must be one of four named complexity classes) and the conditional region-of-outcome presence (Complex-classified scopes cannot have only point criteria). Defends against the corpus-anchored F39 point/region-mismatch at the layer-pair where it is most cheaply detected (before any plan or code is touched).

## §3 L2 ↔ L3 — Spec ↔ Plan

### Reference: smoke-test invariant L2-L3-1

The smoke-test invariant L2-L3-1 (chunk-load ceiling + disjointness) at [`P-31-smoke-test-invariants.md` §3](../primitives/P-31-smoke-test-invariants.md) requires every L3 `PlanChunk.targets[]` to have `len ≤ 10` (steady-state; `≤ 5` at cold-start per U-B §5.6) and the `targets[]` arrays of sibling chunks under one parent spec to be pairwise-disjoint. Corpus: F36 Yang et al. (gpt-4o 98.7% → 85.0% as 1→19 requirements). Smoke-test verdict: non-trivial (count-relative-to-empirical-ceiling).

### Additional invariant L2-L3-2: F37 contradiction-detection escrow gate

(a) **Cross-layer constraint statement.** Every L2→L3 transition must be guarded by a contradiction-detection escrow record. Specifically: an L3 `PlanChunk` may only materialize against a parent L2 spec if the P-28 store contains a `ContradictionDetectionVerdict{parent-spec: <L2-id>, judge-panel-size: ≥ 3, cross-family: true, consensus-verdict: "no-contradiction-detected", confidence: ≥ 0.7}` whose timestamp is newer than the parent L2 spec's last-modified time. The substance-arm is on the judge-panel composition: `cross-family: true` requires the panel to span ≥ 2 distinct model families (per P-14 cross-family routing) — a single-family panel does not satisfy the invariant even at panel-size ≥ 3. The invariant fails if the verdict is missing, stale (older than the spec), single-family, sub-threshold confidence, or below panel-size minimum.

(b) **Corpus citation.** [`26-prompt-underspecification-academic`](../../../research/26-prompt-underspecification-academic.md) §3 (Larbi et al. arXiv:2507.20439v1). Verbatim primary anchors: *"GPT-4 Pass@1 drops from 73.8% to 6.7% on contradictory HumanEval prompts; RIR climbs to 89%; LLM-as-judge MCC ≤ 0.55 for contradiction detection."* The MCC ≤ 0.55 figure is the load-bearing constraint on the construction — a single judge is structurally unreliable, so the invariant cannot be a single-judge gate; the cross-family panel is the minimum-adequate-variety guard per Ashby (F51). Reinforcing source: [`14-el-kaim-book-intent-and-spec-authorship`](../../../research/14-el-kaim-book-intent-and-spec-authorship.md) §17 ¶6 (every conformance rule must trace to a *check that runs* — the escrow record is that check). Cross-citation: F37 is the failure mode; F51 (Ashby-deficient probabilistic guard) is the structural framing that forces the cross-family panel.

(c) **Construction sentence.** Postgres existence check + OPA enum/threshold rule against P-28. The CTE finds L3 PlanChunk objects whose parent L2 spec lacks a fresh `ContradictionDetectionVerdict`; OPA validates the verdict's `panel-size`, `cross-family`, and `confidence` fields against L0-versioned thresholds. The verdict itself is *produced* by P-14 (cross-family judge router) on every L2 spec write — the verdict is an artifact, not a runtime evaluation. Integration: the L2→L3 transition gate (P-29 policy mediator) refuses to materialize the PlanChunk if the invariant fails; Patrol cadence sweeps for stale verdicts after L2 edits.

(d) **Positive example.** L2 contains `Spec{id: "S-PV-12", last-modified: T0}`. P-28 contains `ContradictionDetectionVerdict{parent-spec: "S-PV-12", judge-panel: [{family: "anthropic", model: "claude-sonnet-4.5"}, {family: "openai", model: "gpt-5.2"}, {family: "google", model: "gemini-2.5"}], consensus-verdict: "no-contradiction-detected", confidence: 0.82, timestamp: T1 > T0}`. L3 PlanChunk materialization against `S-PV-12` is permitted. Invariant passes.

(e) **Negative example.** Same L2 spec at T0. (f) **Honest verdict.** **Non-trivial.** The substance is constrained on path-shape: the existence of a critical-path symbol of a specific tagged class. The invariant *does not* address RSI condition 2 (compounding capability) — that is the cross-cycle population-drift problem (OQ-PLEF-3, out of scope per [`u-b.md` §5](../substrate-requirements/u-b.md) caveat (d)). ### 6.4 Phase-5 ADR seeds

The 15 new invariants surface specific Phase-5 ADR scopes:

1. **ADR — Per-layer-pair invariant registry schema.** The invariants in §§1–5 above need a canonical typed-object representation in P-28 (`LayerPairInvariant{id, pair, statement, construction, severity, recommended-handback-layer, corpus-citations[]}`). The registry shape, version-migration policy, and L0-bundle distribution are an ADR. Reference invariants to seed: all 20.

2. **ADR — LayerDriftEvent severity calibration.** Each invariant declares a severity in `{critical, high, medium}`. The calibration policy (when does `high` escalate to `critical`? does it depend on the data class touched? on the AILCCP control class?) needs a corpus-anchored rule rather than per-invariant ad-hoc. Reference invariants to seed: L0-L1-3 (production-data class raises severity), L1-L2-3 (regulated-classification raises severity), L3-L4-3 (production-scissors raises severity).

3. **ADR — Recommended-handback-layer policy.** Some invariants name a single handback layer; others escalate (e.g., L3-L4-3 escalates to L0/L1 rather than the L4 builder, because the trifecta prohibition is an architecture/standards commitment). The escalation policy needs to be principled. Reference invariants to seed: L0-L1-3, L3-L4-3, L0-L4-3.

4. **ADR — Cross-family judge panel composition.** L2-L3-2 (F37 contradiction-detection escrow gate) requires a cross-family panel with `panel-size ≥ 3, confidence ≥ 0.7`. The exact panel composition policy (which families count as distinct? what is the family taxonomy?) and confidence-threshold-versioning need an ADR. Reference invariants to seed: L2-L3-2, L0-L4-1.

5. **ADR — Five-category Intervention Audit Trail symbol-tagging convention.** L0-L4-2 requires symbols tagged `@otel-event-category(<one of five>)`. The tagging convention, the language-specific implementation (Python decorator vs Go struct tag vs Rust attribute), and the verification mechanism need a substrate-level ADR. Reference invariants to seed: L0-L4-2, L0-L4-3 (`@implements-AILCCP` is a sibling convention).

6. **ADR — Construction-C hybrid composition rule (carries from substrate-requirements §2(b)).** Per [`u-b.md` §5](../substrate-requirements/u-b.md), seed (iii). This sub-track refines the seed: the deterministic-vs-judge split varies per invariant (L0-L4-2 is fully deterministic; L0-L4-1 is hybrid; L2-L3-2 is mostly-deterministic with judge residue). The composition rule needs to be invariant-specific.

7. **ADR — Cost-ceiling per-chunk parameterization.** L3-L4-4 references unified-B §4's *per-layer-not-flat* ceiling; the actual policy (how ceilings are calibrated; what happens on near-ceiling; cumulative ceiling drift across many chunks) is an ADR.
