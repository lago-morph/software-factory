## Part 3 — agents-file suggestions

### Suggestion 1: Cross-product integration pass after per-cluster seam reviews — `AGENTS-MD-759e9a22cc`

- **Per-rule file**: [./2026-06-02-242/AGENTS-MD-759e9a22cc-cross-product-integration-pass-after-per-cluster-seam-reviews.md](./2026-06-02-242/AGENTS-MD-759e9a22cc-cross-product-integration-pass-after-per-cluster-seam-reviews.md)

**Proposed agent instruction:**
> **Cross-product integration pass after per-cluster seam reviews.** "When a corpus is authored by parallel subagents grouped into clusters/products and each cluster gets its own seam review, run ONE final cross-product integration adversary over the whole corpus before declaring it done — tracing the end-to-end critical path and diffing every cross-cluster contract at the field level. Per-cluster reviewers each trust the *other* side of a seam crossing two clusters, so contradictions there survive every per-cluster review."
>
> *Grounded in: the Sweep-2 spine run's opus-panel integration adversary caught four build-breakers that all six per-cluster seam reviews missed.*

**Justification:** Six per-cluster seam adversaries ran and each returned accept-with-fixes; the corpus looked done. A single cross-product adversary then found a deadlock (C52↔C53), an enum collision that would make a finished-build query silently return nothing (`factory_build` `completed` vs envelope `closed`), a sequence-ordering contradiction (C09↔C05), and an enum-membership gap (C41 missing `tool:`). Each lived exactly at a seam crossing two cluster-reviews, where each reviewer verified its own side and trusted the other. The marginal cost is one extra reviewer pass at corpus close; the cost of skipping it is shipping four latent build-breakers that read as "reviewed."

### Suggestion 2: Validate Mermaid diagrams with a validator, not a grep for the diagram type — `AGENTS-MD-4436d4247f`

- **Per-rule file**: [./2026-06-02-242/AGENTS-MD-4436d4247f-validate-mermaid-with-validator.md](./2026-06-02-242/AGENTS-MD-4436d4247f-validate-mermaid-with-validator.md)

**Proposed agent instruction:**
> **Validate Mermaid diagrams with a validator, not a grep for the diagram type.** "When a deliverable requires valid diagrams, verify each one renders by running it through a Mermaid validator — do not accept a grep that merely confirms the diagram-type keyword is present. A `;` inside a `stateDiagram-v2` transition label (and `/`, `--`, `:`) silently breaks the parse while the type keyword still greps clean."
>
> *Grounded in: four Gas City diagrams were invalid despite passing the builders' type-presence self-check; only the validator caught them.*

**Justification:** The depth bar required valid Mermaid; builders self-attested by grepping for `stateDiagram-v2`/`sequenceDiagram`, which passed while four diagrams were actually unparseable (semicolons act as statement terminators). A broken diagram renders as an error block in the deliverable. One validator call per diagram (or a fix-pass subagent) is cheap; a corpus of broken diagrams that "passed self-check" is a silent quality failure. After the first product, baking the `;`-hazard into the dispatch addendum stopped recurrence — but the validator is the real gate.

### Suggestion 3: Seam adversary verifies field-level matches; never trusts a self-attested match — `AGENTS-MD-e846cebbd1`

- **Per-rule file**: [./2026-06-02-242/AGENTS-MD-e846cebbd1-seam-adversary-field-level-verify.md](./2026-06-02-242/AGENTS-MD-e846cebbd1-seam-adversary-field-level-verify.md)

**Proposed agent instruction:**
> **A seam adversary verifies field-level matches; it never trusts a builder's self-attested 'seam matches'.** "When two components share a contract (a record schema, a wire type), the cross-component reviewer MUST diff the producing and consuming field lists by name and type — a builder reporting 'consumes X's schema, matches' is not sufficient evidence."
>
> *Grounded in: a builder self-reported its `ScoreRecord` consumption matched while reading `score_value` where the producer froze `satisfaction_score`.*

**Justification:** The C33 builder's receipt explicitly said its ScoreRecord consumption "matched the D-39 frozen set, no missing fields." It did not — it read `score_value` while C32 froze `satisfaction_score`, a mismatch that would have silently dropped every score and left the satisfaction distribution permanently empty (the gate the entire back half trusts). The builder believed it matched. Only a reviewer that diffed the field lists by name caught it. Self-attestation of a seam is worth nothing; the field-level diff is a few minutes and catches the highest-severity class of silent failure.

### Suggestion 4: Durability-commit by exact path on the stop-hook nag during async subagent waves — `AGENTS-MD-62e1b37482`

- **Per-rule file**: [./2026-06-02-242/AGENTS-MD-62e1b37482-durability-commit-exact-path-async-waves.md](./2026-06-02-242/AGENTS-MD-62e1b37482-durability-commit-exact-path-async-waves.md)

**Proposed agent instruction:**
> **Durability-commit by exact path on the stop-hook nag during async subagent waves.** "In an ephemeral sandbox with async subagents whose files land before their completion receipts, commit completed files by their exact paths on each stop-hook reminder rather than waiting for the whole wave — and never blanket-`git add` while sibling subagents are mid-write on a *different* branch's files. Intermediate states are corrected by a later commit; lost work is not."
>
> *Grounded in: the Sweep-2 run committed ~25 waves this way, across two concurrently-pipelined product branches, with no lost work and no cross-branch file mixing.*

**Justification:** Async subagents write their files, then return a receipt some time later; the stop hook fires whenever the tree is dirty. Waiting for the full wave before committing risks losing completed work if the sandbox is reclaimed; blanket-committing risks (a) capturing a sibling's mid-write file and (b) mixing one product's files onto another product's branch when pipelining. Committing the notified/complete files by exact path on each nag resolves both: durability without contamination. This pattern carried 44 commits across 7 stacked branches cleanly.

### Suggestion 5: Self-check grep tokens must match the exemplar's actual spelling — `AGENTS-MD-13911c4646`

- **Per-rule file**: [./2026-06-02-242/AGENTS-MD-13911c4646-self-check-grep-match-exemplar-token.md](./2026-06-02-242/AGENTS-MD-13911c4646-self-check-grep-match-exemplar-token.md)

**Proposed agent instruction:**
> **Self-check grep tokens must match the exemplar's actual spelling.** "When a subagent self-verifies a deliverable with a grep (per the tool-verification rule), the grep pattern MUST match the exemplar's literal token, not a plausible guess — publish the exact token in the dispatch brief so every subagent uses it."
>
> *Grounded in: four Sweep-2 builders hit a `R/W-by` vs `R/W by` mismatch, each reporting the grep returned 0 and adding a caveat that the column was present anyway.*

**Justification:** The self-check rubric told builders to `grep -c "R/W-by"`, but the C20 exemplar's ownership column is spelled `R/W by` (space, no hyphen). Four builders dutifully ran the grep, got 0, and had to hand-explain that the column existed despite the rubric's own pattern missing it — noise that erodes the self-check's value and could mask a genuine absence. The fix is one character of diligence: publish the exemplar's literal token in the dispatch. A tool-verified self-check is only as good as the token it greps for.
