# ADR: Context-slimming via entry doc + task-aware reading lists + TL;DR on heaviest docs

- **ID**: ADR-09a7c6bf00
- **Status**: Draft (not yet adopted to docs/adr/; implementation deferred to later PR chain)
- **Date**: 2026-05-25
- **Source retrospective**: ../2026-05-25-151.md
- **PRs covered**: #151

## Context

The Phase-4 startup prompt I authored at the end of the 2026-05-25 overnight run filled a fresh agent's context window to 147K tokens immediately. Root cause: the prompt's read-order section listed nine foundational documents (`AGENTS.md`, the active SESSION-HANDOFF, `phase-3.4-decisions-resolved.md`, `candidate-registry.md`, `primitives/index.md`, two decision briefs, one smoke-test result, the synthesis plan, and the overnight summary) totaling ~1690 lines of markdown, all eagerly loaded.

The user observed this and asked for proposals to reduce session-start context-window load while not losing accuracy. They specifically named progressive disclosure as a candidate, with the constraint: "the root document NOT talking about the information in the sub-documents, but only saying what is contained there." This is the staleness mitigation — if a root doc names topic-level contents only, the root doesn't drift when sub-docs are edited.

I returned 6 proposals: progressive-disclosure entry doc; tighter SESSION-HANDOFF with stable symlink; task-aware reading lists in the prompt; TL;DR-first document discipline; compacted-state file at end-of-run; hot/cold separation by recency. User picked the combination of proposals 1 + 3 + 4 and asked for a detailed plan in [`CONTEXT-SLIMMING-PLAN.md`](../../CONTEXT-SLIMMING-PLAN.md) at repo root. PR #151 committed the plan; implementation was explicitly deferred until the current long-running synthesis chain completes to avoid merge conflicts.

## Decision

**Reduce new-agent session-start context window load by introducing `AGENT-ENTRY.md` at repo root as the single navigation document that names what each sub-doc contains at topic level but does not restate content, embedding task-aware reading lists in the entry doc for the most common next moves, and adding TL;DR sections to the two heaviest foundational docs (`ARCHITECTURE-V3-SYNTHESIS-PLAN.md` and `architectures/v3/candidate-registry.md`) regenerated by subagent at end-of-run so staleness is bounded to one run.** Per-primitive sketches stay drill-on-demand. Smaller foundational docs (`AGENTS.md`, `phase-3.4-decisions-resolved.md`, the active SESSION-HANDOFF, `primitives/index.md`) do not receive TL;DRs — they are small enough that full reading is cheap.

Implementation deferred to 4 sequential PRs (A: entry doc + task-aware reading lists; B: TL;DRs on the two heaviest docs; C: autonomous-run skill update with TL;DR-regeneration end-of-run sub-step + task-aware reading list section in handoff template; D: startup-prompt template update referencing the entry doc). Expected savings: ~30-35% of current eager-read; session-start budget drops from 147K to ~90-110K tokens.

## Alternatives considered

- **Compacted-state self-summarization at end-of-run.** Rejected as the primary mechanism because the lead agent's compaction is hard to trust across many runs — fidelity loss compounds. Kept available as a possible future addition if the entry-doc approach proves insufficient.
- **Hot/cold file separation by recency** (move older artifacts to `cold/`, keep only active state in `hot/`). Rejected as premature structural change — entry doc + reading lists achieve similar session-start savings without moving files around.
- **Cut content from the foundational docs themselves.** Rejected because each doc has its size for reasons; cutting would lose accuracy. Indirection via entry doc + drill-on-demand achieves savings without cutting.
- **Apply TL;DRs to every foundational doc.** Rejected as creating maintenance burden disproportionate to savings. Only the two heaviest docs (>300 lines and growing) justify the TL;DR + regenerator overhead.
- **Maintain TL;DRs alongside the body manually.** Rejected because manual TL;DRs drift relative to body edits; the user explicitly flagged this concern. The auto-regenerate-at-end-of-run pattern bounds staleness to a single run.
- **Auto-load `AGENT-ENTRY.md` via harness hook (like `AGENTS.md`).** Considered but deferred — would require harness change. Opt-in via prompt instruction works for now and can be upgraded later if the pattern proves valuable enough.

## Consequences

**Easier.** Future unattended-run startup prompts read as "read `AGENTS.md`, then `AGENT-ENTRY.md`, then follow its navigation for your stated task" — a 3-step instruction instead of a 9-doc reading list. Session-start context window has ~50K tokens of headroom for the agent's actual work. Per-task reading lists pre-curate the right detail per the most common next moves; new agents land already knowing which subset of artifacts is relevant.

**Harder.** Adds one new top-level doc (`AGENT-ENTRY.md`) that must be kept in sync with the file structure (when files move, the entry doc's links break — caught by [`scripts/check-internal-refs.py`](../../scripts/check-internal-refs.py)). Adds a TL;DR-regeneration sub-step to the autonomous-run skill's end-of-run protocol — one extra subagent dispatch per run. Per-task reading lists in the handoff doc require the lead agent to anticipate the next session's tasks; un-anticipated tasks fall back to the entry doc's navigation.

**Accepted trade-off.** The 30-35% session-start context savings is substantial and applies to every future session. The added maintenance burden is bounded (one entry doc; two TL;DRs auto-regenerated). The risk of accuracy loss via staleness is mitigated by: (a) the entry doc's discipline of naming topics not restating content (so it doesn't go stale on doc-body edits, only on file-rename / file-add); (b) the TL;DR regeneration at end-of-run (so TL;DRs are at most one run stale).
