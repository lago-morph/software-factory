First lesson, immediate: the Read tool's per-call token limit (25k) is **smaller than this index**. The first attempt to `Read` the whole file errored. Recovery: read it in three `offset`+`limit` chunks (1–300, 301–600, 601–864). This is a known pattern, but worth recording — for index files this size, plan the chunking up-front.

### Phase 2 — 13 cluster-by-cluster subagent runs

The user's brief was unambiguous: *"To actually process the cluster, spawn a single subagent to do the ingestion and do the updates. You are using subagents to preserve your context window, not for parallelism."*

This is the difference between two skills the harness exposes:
- `parallel-subagent-fanout` — dispatch N subagents concurrently, merge results.
- (newly extracted) `cluster-drain-orchestration` — dispatch 1 subagent at a time, commit between each, orchestrator-context preservation.

The choice was right because **the orchestrator's context window was the binding constraint**. Each cluster's subagent ran 5–18 minutes wall-clock and produced 200–800 words of change report. If I had run them in parallel, all 13 change reports (~6000 words of summary) would have arrived at once, blown through compression boundaries, and lost surprise-extraction fidelity. Serial dispatch let me digest each change report fully, transcribe surprises into PLAN.md, commit, push, and only then move to the next cluster.

The per-cluster loop was:

```
1. Read PLAN.md / new-index.md cluster block / target reports (1-2 minutes of orchestrator thought)
2. Write a per-cluster brief (5-15 minutes of orchestrator writing)
   - List source files (absolute paths)
   - List target reports (existing + new)
   - Specify what to add (sections, specific numbers, specific quotes)
   - Specify what NOT to touch (PLAN.md, other reports)
   - Image-extraction instructions if KEPT MHTMLs present
   - The mhtml_extract.py canonical path
   - The 1-based-info / 0-based-save off-by-one warning
   - The AVIF-inside-`.png` Pillow conversion warning
   - Deliverable format: 300-600 word change report
3. Spawn ONE general-purpose subagent. Wait.
4. Verify: git status --short; git diff --stat HEAD
5. Update PLAN.md (flip ⬜ → ✅ + inline 3-8 surprises)
6. Commit with multi-line message; push
```

## Part 4 — proposed ADRs

In addition to the 5 ADRs proposed in the original retro (F-mode numbering policy / per-report figure directory convention / cluster-orchestration commit cadence / `mhtml_extract.py` contract / forward-allocate report numbers), this deeper pass surfaces:

- **Parallel-fanout vs serial-cluster-drain decision criterion** — record the binding-constraint reasoning that makes serial-with-context-preservation the right choice for ingestion drains while keeping `parallel-subagent-fanout` available for build-and-test work. Two skills, one harness; the ADR records when to pick which.
- **Retrospective filename collision policy** — adopt the `-a/-b/-c/...` suffix per the `self-retrospective` skill's anti-collision rule, and document that contemporaneous + deeper retros for the same PR-anchor are explicitly allowed (this session produced both).
- **Subscribe-to-PR-activity timing** — subscribe immediately after opening the PR draft, not at end. The deeper-than-needed subscription cost (a few extra wakeups while the PR is draft) is dominated by the cost of forgetting to subscribe later.
- **Subagent change-report length contract** — codify the 300-600 word window. Below 300 the orchestrator can't extract surprises reliably; above 600 starts to defeat the context-preservation goal.
- **Drain-pass and indexing-pass must not share branches** — the report-18 cross-section drift caught in Cluster F was the residue of an indexing pass forward-editing a sources table on a different branch that had merged. Indexing should never write to a *report's body or its sources table*; only the drain pass should.

## What this retrospective surfaces that the original missed

Eight items not adequately covered in `retrospective/2026-05-16-67.md`:

1. **The Read-tool token limit on the index file.** The very first move of the session hit a 39,606-token read against a 25k limit. Worth surfacing because index files of this scale will recur.
2. **The Phase-0 commit was the highest-leverage move of the entire session.** Forward-allocating numbers 27–37 in a committed document eliminated an entire class of mid-stream collisions. The original retro mentions forward-allocation in passing; this retro lifts it to architectural-decision status.
3. **Cluster F's catch of Cluster E's cross-section drift.** The original retro mentions the catch but doesn't frame it as a *cross-cluster verification pattern* — i.e., each cluster's primary-text drain is a chance to audit the previous cluster's table-editing claims. This is itself a reusable pattern.
4. **Two subagents (Clusters I and K) claimed images were "already present from prior orchestrator pass."** Both turned out to be true (the PNGs *had* been extracted on `main` by the indexing branch), but the claim was unverifiable from the change report alone. A `ls` + `file` verification on the orchestrator side would have been ~10 seconds and would have caught any drift. Going forward: never trust "already present" claims from a subagent — always verify.
5. **The Cluster A and Cluster B checkbox lapse.** The user caught it post-merge. The lapse happened because Cluster A+B ran as a single combined subagent and I wrote one detailed drain note but never flipped the individual ⬜ rows for A and B. This is a real category of error: when two pre-allocated checklist rows are filled by a single subagent run, the orchestrator must remember to flip both.
6. **Mid-session tool discovery via `ToolSearch`.** I had to ToolSearch for `mcp__github__pull_request_read` when finalizing the PR. The harness uses deferred tools loaded on-demand. This is by design (token economy) but worth a workflow note: at session-end PR steps, expect to ToolSearch for GitHub tools.
7. **Stop-hook unpushed-commits warnings as a feedback discipline.** The `~/.claude/stop-hook-git-check.sh` fired repeatedly during the session, each time reminding me to push the commit I'd just made. This wasn't a bug — it was a working safety net. The pattern *commit after subagent / push immediately* survived 13 cluster cycles without an unpushed-commit gap of more than one tool turn.
8. **The retrospective itself was used twice — contemporaneous + deeper.** The skill explicitly supports collision-suffix `-a/-b/-c/...` filenames; this is the first time in the corpus that two retros for the same PR-anchor land in the same session. Worth a precedent note.

## Part 5 — what was correct vs what should have been better

### Correct

- **Strict serial subagent dispatch.** Context preservation was the binding constraint; the orchestrator never lost a thread.
- **Forward-allocating numbers up front.** Zero report-number collisions across 11 new reports.
- **One commit per cluster.** PR #67's commit log is a 1:1 mirror of the cluster sequence. Reviewers can audit cluster-by-cluster.
- **PLAN.md updates inline with cluster commits.** Surprises were captured *while fresh* — the per-cluster surprise lists ended up driving the PR body and this retro.
- **Subscription via `mcp__github__subscribe_pr_activity` immediately on ready-for-review.** The webhook fired on merge within minutes; cleanup was automatic.
- **`research/manual/new-index.md` preserved per user instruction.** The index is the audit trail for what was drained and what was skipped.

### Should have been better

- **The Cluster A/B checkbox lapse.** Caught by user, not by me. Two minutes of orchestrator attention pre-commit would have caught it.
- **The Cluster E "already present pre-edit" claim** went unverified at commit time. The orchestrator should have grepped for "🟡" / "still ❌" / "mirror-anchored" in report 18 *before* the commit message went out. Cluster F's catch was lucky, not structural.
- **The "image already present from prior pass" claims (Clusters I, K)** were taken on trust. They were true, but `ls` + `file` verification was a 10-second check and would have hardened the audit trail.
- **Did not run `post-edit-reread-pass` after the Cluster J followup/10 +148 lines.** That was a multi-section long-doc edit that arguably qualified for the discipline. Got lucky that nothing drifted.
- **PR body word count drift.** The PR body landed at ~6500 words. A 3500-word body would have served the same purpose with less padding. The padding came from copy-pasting from PLAN.md surprise blocks rather than rewriting them for PR-reviewer audience.
- **The retrospective filename suffix policy was rediscovered, not remembered.** The `self-retrospective` skill documents the `-a/-b/...` pattern; I noticed it in the SKILL.md preface, not in muscle memory. Worth promoting to an AGENTS.md rule.
