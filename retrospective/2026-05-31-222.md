## Part 3 — agents-file suggestions

Proposed additions to `AGENTS.md`. Each rule has its own per-rule file in the sibling directory carrying `# agent instruction` (concatenated into `AGENTS.md`) and `# justification` (stripped by the assembler). Mirrored inline below for review.

### Suggestion 1: Verify the committed tree, not the working tree, after a revert — `AGENTS-MD-efcebc57aa`

- **Per-rule file**: [./2026-05-31-222/AGENTS-MD-efcebc57aa-verify-committed-tree-after-revert.md](./2026-05-31-222/AGENTS-MD-efcebc57aa-verify-committed-tree-after-revert.md)

**Proposed agent instruction:**

> **Verify the committed tree, not the working tree, after a revert.** When you revert or `git checkout --` a file to undo a change, verify the result with `git show HEAD:<path>` (or grep over the committed blob), not by reading the working tree — and never claim a fix landed on the strength of a working-tree read alone.
>
> *Grounded in: the wrap-up session's spec-annotation reconciliation, where a working-tree revert had to be confirmed against `git show HEAD:` to know which copy of the annotations was actually committed.*

**Justification:**

Twice in this session the working tree and the committed tree diverged in ways a plain `Read` could not distinguish: once when a background subagent re-applied annotations a foreground retry had already committed (duplicates only in the working tree), and once when a `git checkout --` revert restored a file whose committed state then had to be confirmed before trusting it. A working-tree read answers "what's on disk right now," the wrong question after a revert or a racing concurrent writer; only `git show HEAD:<path>` answers "what did I actually commit." The cost of getting this wrong is shipping a duplicated or stale artifact while believing the opposite. The marginal cost of the rule is one `git show` or grep over the committed blob.

### Suggestion 2: Distrust empty or truncated tool output before a destructive action — `AGENTS-MD-5fb2170cda`

- **Per-rule file**: [./2026-05-31-222/AGENTS-MD-5fb2170cda-distrust-corrupted-tool-output.md](./2026-05-31-222/AGENTS-MD-5fb2170cda-distrust-corrupted-tool-output.md)

**Proposed agent instruction:**

> **Distrust empty or truncated tool output; re-verify before a destructive action.** When a Bash or Read result comes back empty, truncated, or visibly garbled, treat the underlying state as unknown — re-run a narrowed, deterministic check — before overwriting, deleting, or reverting on the basis of it.
>
> *Grounded in: a stretch of this session where Bash returned empty/garbled output, leading to a good committed file being overwritten with an inferior reconstruction that then had to be restored from git.*

**Justification:**

Mid-session the Bash tool intermittently returned empty or truncated output. Acting on one such corrupted read, I concluded a committed consistency report was missing or thin and overwrote it with a hand-reconstruction — less thorough than the subagent's original and breaking the reference checker. The original had to be restored from git, costing two extra commits and a regression in a shipped artifact. A corrupted tool result is evidence of nothing about the file's state. The marginal cost of the rule is a single re-run of a narrowed check (`git show HEAD:<path> | head`, `wc -l`, a targeted grep) versus a destructive action on a phantom reading.

### Suggestion 3: Glob real filenames before dispatching file-targeted subagents — `AGENTS-MD-c5aaaec22b`

- **Per-rule file**: [./2026-05-31-222/AGENTS-MD-c5aaaec22b-glob-real-filenames-before-subagent-dispatch.md](./2026-05-31-222/AGENTS-MD-c5aaaec22b-glob-real-filenames-before-subagent-dispatch.md)

**Proposed agent instruction:**

> **Glob real filenames before dispatching file-targeted subagents.** Before briefing a subagent to edit files by path, resolve the actual on-disk names with a glob or `ls`; never hand a subagent assumed paths like `spec/C43.md` when the real file is `spec/C43-isolation-boundary.md`.
>
> *Grounded in: the first spec-annotation subagent in this session, which was briefed with `C<NN>.md` paths, found nothing to edit, and forced a second dispatch once the real `C<NN>-<slug>.md` filenames were discovered.*

**Justification:**

The v4 spec corpus names files `C43-isolation-boundary.md`, not `C43.md`. The first integrator subagent, briefed with the short form, silently found no matching files and returned having changed nothing — so a second subagent had to be dispatched with globbed paths, doubling the wave's cost and creating a window where two agents raced on the same files. A subagent cannot recover from a wrong path the way the lead can, because it does not know the corpus's naming convention unless told. The marginal cost is one `ls spec/C43-*.md` per target; the cost of skipping it was a wasted ~9-minute subagent run plus duplicate-edit cleanup.

### Suggestion 4: Scope a repo-wide linter to branch-touched files before calling it red — `AGENTS-MD-5729257b3b`

- **Per-rule file**: [./2026-05-31-222/AGENTS-MD-5729257b3b-scope-repo-linter-to-branch-files.md](./2026-05-31-222/AGENTS-MD-5729257b3b-scope-repo-linter-to-branch-files.md)

**Proposed agent instruction:**

> **Scope a repo-wide linter to branch-touched files before calling it red.** When a whole-repo checker reports thousands of issues, compare its result against the same checker run on the base branch (or filter its output to `git diff --name-only origin/main..HEAD`) before treating the failure as something this branch introduced.
>
> *Grounded in: `scripts/check-internal-refs.py` reporting ~4,483 issues in this session, which on inspection was a ~4,421-issue pre-existing baseline already red on `main`, not a regression from the wrap-up work.*

**Justification:**

The reference checker exited non-zero with thousands of findings, looking at first like the branch had broken something badly. Filtering to branch-touched files and re-running on `origin/main` showed ~4,421 of those issues predated the branch — almost all cosmetic `BACKTICK_PATH` suggestions the repo had already logged as a corpus-wide sweep-2 item. Only a handful of fixable bare references traced to new files, fixed in minutes. Without the baseline comparison, an agent wastes a long pass chasing a pre-existing count to zero, or wrongly blocks a merge on a check that was red before it started. Marginal cost: one extra checker run on the base branch plus a `git diff --name-only` filter.

### Suggestion 5: Spot-check subagent-authored definitions against the corpus — `AGENTS-MD-d6ad41b362`

- **Per-rule file**: [./2026-05-31-222/AGENTS-MD-d6ad41b362-spot-check-subagent-definitions.md](./2026-05-31-222/AGENTS-MD-d6ad41b362-spot-check-subagent-definitions.md)

**Proposed agent instruction:**

> **Spot-check subagent-authored definitions against the corpus source of truth.** Before shipping a subagent-authored human-facing artifact, verify each load-bearing definition in it against the spec or corpus it describes; subagents confidently invent plausible-but-wrong meanings, and a fluent wrong definition is harder to catch than a clumsy one.
>
> *Grounded in: a refresh subagent in this session describing the "digital twins" as "two copies of the factory that check each other's work," when the corpus (C44) defines twins as behavioral fakes of external services.*

**Justification:**

A subagent refreshing the plain-language guide rewrote "the twins" as two factory copies cross-checking each other — a coherent, confident, completely fabricated meaning. The actual corpus (C44 "Digital Twin (per service)" + the decisions doc) defines twins as LocalStack/VCR-style behavioral fakes of external services. The fabrication survived into a committed, user-facing guide and was caught only on a deliberate end-to-end read against ground truth. A wrong definition in an outsider-facing explainer is high-blast-radius — the whole point is to be trusted by a reader who can't check it. Marginal cost: one grep of the relevant spec per load-bearing term.
