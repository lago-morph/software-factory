## Part 1 — what happened

The task: revise [`architectures/v4/implementation-dependencies.md`](../architectures/v4/implementation-dependencies.md). Prior edits had begun clustering the 57 v4 components by the off-the-shelf product that delivers them, but two problems remained — (1) the new product view was bolted on top of the original ten-phase wave structure, which scattered one product's components across phases and ignored the natural clustering; (2) the doc was full of change-narration ("this replaces the old long pole", "you asked a sharp question") that bewilders a first-time reader. The operator asked to make products first-class, strip the change-references, use cooperative and adversarial subagents, and run a ≥3-reviewer multi-persona review loop until no factual, contradiction, or major findings remained.

### Phase 1 — grounding + locating the paradigm shift

Read the session-startup docs (`AGENTS.md`, `AGENT-ENTRY.md`, the v4 `HANDOFF.md`) and the target doc. The operator's hint — "if you look at diffs you'll find where the paradigm shifted" — was taken literally: `git log --oneline -- <file>` plus `git show` on the two most recent commits pinpointed the shift. The original commit organized by phase; two later commits added product-clustering on top without removing the phase skeleton. That diff map made the rest of the work tractable.

### Phase 2 — cooperative grounding

Dispatched two background research subagents (write-to-disk, return receipts): one to verify the product↔component mapping against the component-inventory + specs and flag discrepancies, one to extract the verbatim dependency graph and the {C53,C43} closure. These grounded the restructure in the source of truth rather than the (error-carrying) prior edits.

### Phase 3 — scope decision

Asked the operator one focused question: when products become first-class, what happens to the dependency/ordering content held in the ten phases? Answer: **fold into products** — and, crucially, "custom development is clustered into internal products that make sense to build, test, and integrate as a single unit … this may mean many single-component products that are custom." That refinement reshaped the partition: the "genuinely custom" bucket became a set of named internal products, not one row.

### Phase 4 — the restructure

Re-derived the whole document around products: an external-products table (adopt + configure), an internal-products table (custom build-test-integrate units), per-product subsections, a "backbone" (the seven-product path to safe self-build) with three rings, a "Build order across products" section carrying the dependency/parallelism/critical-path content the phases used to hold, and a top-ten-next ranking. All change-narration removed.

### Phase 5–7 — three-round adversarial review loop

Eight real-subagent reviewers across three rounds, personas rotating as feedback converged. **Round 1** (first-time-reader, fact-checker, consistency): 0 factual; one contradiction (the fence drawn parallel to the eval tier its holdout depends on), a product-count slip, a W&B license error, two broken anchors. **Round 2** (regression-verifier, skeptical architect, skim PM): regression-verifier confirmed the round-1 fixes COMPLETE; the architect found a contradiction (C20 modeled two incompatible ways) and a major omission (the fence's detect-vs-prevent caveat). The C20 fix reverted a round-1 over-simplification — folding the bead-type schema into spec intake to claim "six products" contradicted the inventory (C20→C19), so the backbone became seven products. **Round 3** (convergence-verifier, fresh-eyes onboarding engineer): convergence-verifier returned 0 findings / accept-as-is; fresh-eyes returned 0 factual / 0 contradiction / 0 major, "build from this doc: yes." Termination bar met; adopted three precision minors; converged.

### Phase 8 — merge + retrospect

Merged PR #227 (squash, `mergeable_state: clean`), verified the doc + 8 review records landed in `main`, unsubscribed from PR activity, then authored this retrospective on a fresh branch off `main`.

## Part 3 — agents-file suggestions

Proposed additions to `AGENTS.md`. Each has its own per-rule file in the sibling directory carrying a `# agent instruction` section (concatenated into `AGENTS.md` by the CI/CD assembler) and a `# justification` section (stripped by the assembler). Both are mirrored inline below.

### Suggestion 1: Locate the paradigm-shift commit before reconciling a half-applied restructure — `AGENTS-MD-f072c695ab`

- **Per-rule file**: [./2026-06-01-227/AGENTS-MD-f072c695ab-locate-paradigm-shift-commit.md](./2026-06-01-227/AGENTS-MD-f072c695ab-locate-paradigm-shift-commit.md)

**Proposed agent instruction:**

> **Locate the paradigm-shift commit before reconciling a half-applied restructure.** When asked to finish, reconcile, or fix a document whose organizing principle changed partway through its history (a newer style bolted on top of an older one), first run `git log -- <file>` and `git show` on the candidate commits to pinpoint where the paradigm shifted and what the old vs new organizing principle is, before editing. Do not start from a guess about where the inconsistency lives.
>
> *Grounded in: locating the phases-to-products shift in implementation-dependencies.md via git archaeology before restructuring.*

**Justification:** The operator's instruction was literally "if you look at diffs on the edits to the file you will find where the paradigm shifted." Acting on it — `git log` then `git show` on the two latest commits — turned a vague "the doc mixes two styles" complaint into a precise map of which structure was the keeper and which was residue. Marginal cost: two or three git commands. Cost of skipping: editing from a guess, discovering the deeper structural layer only after reworking the shallow one, and redoing the work.

### Suggestion 2: Every adversarial-review round needs a regression-verifier persona — `AGENTS-MD-53ebe3b71a`

- **Per-rule file**: [./2026-06-01-227/AGENTS-MD-53ebe3b71a-regression-verifier-per-round.md](./2026-06-01-227/AGENTS-MD-53ebe3b71a-regression-verifier-per-round.md)

**Proposed agent instruction:**

> **Every adversarial-review round needs a regression-verifier persona.** In a multi-round adversarial review loop, dispatch one reviewer per round whose sole job is to confirm the previous round's fixes are complete and introduced no new defect, reporting an explicit COMPLETE/INCOMPLETE verdict per named fix. A fix can be internally self-consistent yet inconsistent with the rest of the artifact; only a verifier that re-checks the prior fixes by name catches a half-applied correction before it ships.
>
> *Grounded in: the round-2 and round-3 regression verifiers confirming the fence/eval and C20 fixes COMPLETE.*

**Justification:** The round-1 fence/eval fix touched nine locations (two diagrams, three prose passages, three tables, one note) — exactly where a half-application hides. The round-2 verifier, briefed with the fix by name, returned "FIX-1 fence/eval: COMPLETE" with the edges it confirmed; round-3 did the same for the seven-products restructure. That is the only reason the loop could terminate with confidence. Marginal cost: one extra subagent per round. Cost of omitting: shipping a correction that fixed the reported contradiction while quietly creating another.

### Suggestion 3: A readability merge must preserve the dependency source-of-truth grouping — `AGENTS-MD-0e6fa98817`

- **Per-rule file**: [./2026-06-01-227/AGENTS-MD-0e6fa98817-readability-merge-preserves-dependencies.md](./2026-06-01-227/AGENTS-MD-0e6fa98817-readability-merge-preserves-dependencies.md)

**Proposed agent instruction:**

> **A readability merge must preserve the dependency source-of-truth grouping.** Before collapsing two items into one unit to make a document read more cleanly, check the dependency source of truth: if the items have different upstream dependencies, merging them misrepresents the graph and contradicts any section that lists them separately. Keep them separate even if it costs one more box or row.
>
> *Grounded in: folding the bead-type schema (C20, which depends on C19) into the spec-intake product to claim 'six products' contradicted the catalog and was reverted to seven.*

**Justification:** Mid-restructure, "seven products" felt like one too many, so the bead-type schema (C20) was folded into spec intake to read as six. It read better and was wrong — C20 depends on the bead store (C19), not the spec artifact — creating a component modeled two incompatible ways in one document. The architect caught it; unwinding cost a full second-round fix. Marginal cost: one dependency lookup before merging for presentation. Cost of ignoring: a contradiction a knowledgeable reader trips on immediately, eroding trust in every other count.

### Suggestion 4: Run adversarial review to an explicit zero-findings termination bar — `AGENTS-MD-189ee1f5cb`

- **Per-rule file**: [./2026-06-01-227/AGENTS-MD-189ee1f5cb-review-loop-termination-bar.md](./2026-06-01-227/AGENTS-MD-189ee1f5cb-review-loop-termination-bar.md)

**Proposed agent instruction:**

> **Run adversarial review to an explicit zero-findings termination bar.** When looping adversarial review over an artifact, fix findings and re-review until a full round returns zero factual, zero contradiction, and zero major findings; minor and polish findings do not block. State the bar up front and stop when it is met, rather than looping indefinitely or stopping after a single round.
>
> *Grounded in: the three-round review loop terminating when round 3 returned zero factual / contradiction / major findings.*

**Justification:** The operator asked to "review again in a loop until there are no factual or contradiction findings, and no other major findings." Naming that exact bar gave every round an unambiguous stop condition: round 1 had a contradiction, round 2 had a contradiction + major, round 3 returned 0/0/0 and the loop stopped. Without it, two failure modes appear — stopping after round 1 (which still had a live contradiction) or chasing cosmetic minors forever (round 3 reviewers still each raised 3–4). Marginal cost: one sentence per reviewer brief plus one orchestrator decision rule.

### Suggestion 5: State what a living document is, not how it changed — `AGENTS-MD-d0bdc2c793`

- **Per-rule file**: [./2026-06-01-227/AGENTS-MD-d0bdc2c793-state-what-document-is-not-how-it-changed.md](./2026-06-01-227/AGENTS-MD-d0bdc2c793-state-what-document-is-not-how-it-changed.md)

**Proposed agent instruction:**

> **State what a living document is, not how it changed.** In a document meant to be read fresh — a spec, build order, design doc, or README — do not narrate edit history or the prior version ('this replaces the old X', 'unchanged below', 'now leads with', 'two corrections', 'you asked'). Change-narration and conversation-anchoring bewilder a first-time reader and drift stale; state the current truth directly and let git history record how it changed.
>
> *Grounded in: removing pervasive change-narration from implementation-dependencies.md as the second of the two requested fixes.*

**Justification:** Half the task was deleting sentences that told the reader how the doc evolved rather than what it says — "This replaces the old single-line long pole," "the original view, unchanged below," "You asked a sharp question." Each made sense to the editor and was noise to a first-time reader. The operator's words: "We don't care how it changed, we care what it is … bewildering to a first time reader." The marginal cost is near zero — it is easier to state the current truth than to write the comparison. This is the document-content analogue of the existing "address user confusion directly, not via meta-honesty sections" rule.
