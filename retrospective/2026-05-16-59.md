## Part 1 — what happened

### Phase 1 — consolidate 9 auxiliary files into a single bridge file (PR #58)

The user listed nine files for cleanup: `user-next-steps.md` at the repo root, five `research/blocked-urls*.md` files, `research/fetch-from-browser.sh`, `research/next-fetch-batch.md`, and `research/unfetched-sources.md`. They asked for a single output: `research/plan-sync.md` that captures "all the information you got from cleaning up all those files that might be needed to sync up `research/PLAN.md`" — and were explicit that PLAN.md itself was NOT to be touched in this pass ("I will ask you later to update the plan, but I do NOT want you to do that now").

Approach: read each of the nine files in turn, then read PLAN.md v0.12 carefully to identify which content was already absorbed vs. which still needed a home. Estimate: ~70% of the nine files' content was already in PLAN.md, ~30% was load-bearing-but-missing. Wrote `plan-sync.md` with three layers: §1 ("what is missing from PLAN.md and probably should be added" — 8 numbered items with section-mapping recommendations), §2 ("what is ALREADY in PLAN.md" — traceability bullets), §3 ("per-file disposition"), and four verbatim Appendices A–D preserving the per-URL audit trail, the bash script body, the round-8 issue-body template, and the Path-A/B/C manual-fetch procedures.

What deviated: I had to make a call about whether to delete the originals after consolidating. User phrasing said "clean up the following files" — interpreted as delete-after-consolidate. Committed to that and noted in plan-sync.md that originals remained recoverable from git history. PR opened as draft per harness instructions.

- **Pass 2 verification** caught two more issues: (a) §1 "Open items" list named §3.5 (resolved) as a live bottleneck and omitted §3.6 (live), and (b) the §17 version-history table was now in non-chronological order (v0.10 → v0.12 → v0.13 → v0.11) — the v0.11 row had been historically appended after v0.12.

Net edits: PLAN.md grew from 440 to 495 lines (+95 inserts, −38 deletes).

## Part 3 — agents-file suggestions

See [./2026-05-16-59/AGENTS-suggestions.md](./2026-05-16-59/AGENTS-suggestions.md) for proposed additions to the project's agents file, one section per rule with exact text to paste and a persuasion argument.

Three suggestions:
1. **PRs default to ready-for-review, not draft.** Overrides the harness-default instruction in the session-start prompt; surfaced twice in one session.
2. **Multi-pass re-read for long-doc edits is non-optional.** Three rounds of drift were caught only by repeated re-reads.
3. **When the user says "consolidate" or "clean up X files into Y", default to delete-the-originals after preserving load-bearing content.** The alternative (leaving stale duplicates) is the worse failure mode.

## Part 4 — proposed ADRs

Architectural decisions made or surfaced in this session that the user may want to record as ADRs. **Titles only — no specs.** Use the `adr` skill to author any of these if you decide they're worth recording.

- **Adopt the consolidate-via-bridge-file pattern for retiring auxiliary documentation files.** — The two-PR sequence (PR1: delete N files + create bridge with appendices; PR2: fold bridge into target doc, mark bridge disposable) was used cleanly in this session and is generalizable to any "retire N stale files into one canonical doc" refactor.
- **Default PR creation mode: ready-for-review, not draft.** — The harness session-start prompt instructs "Create the pull request as a draft" but the user has now twice in one session asked to override this. Either change the harness default or record the project's contrary policy in an ADR.
- **Long-lived status docs (PLAN.md and equivalents) require multi-pass re-read after any cross-section edit.** — This session caught 6 distinct drift issues across 3 verification passes; single-pass editing would have shipped them. ADR-worthy if the team wants to bind this discipline.
