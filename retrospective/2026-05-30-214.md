## Part 1 — what happened

### Phase 0 — Grounding
The user asked for an exhaustive spec **and** plan for every piece of `architectures/v4`, run with maximum parallelism, with two simultaneous tracks (a faithful "fixed proof" and a ruthlessly optimized one), depth built in sequence (architecture-level foundation first, then deepen), and explicit instruction to preserve the orchestrator's context window via subagents. Rather than read the 1500+ line corpus directly, the orchestrator dispatched two independent cartographers and an adversarial skeptic. They produced two component decompositions and a 45-finding gap analysis; a reconciler fused them into a **canonical 57-component inventory** (C01–C57) in five dependency-ordered batches — the dispatch backbone for everything after.

### Phase 1 — Control plane
Wrote a `_meta/` control plane: META-PLAN (orchestration contract), TRACK-CHARTERS (faithful vs optimized rules), DOC-TEMPLATES, and **standing BUILDER/ADVERSARY briefs** so per-agent dispatch prompts could shrink to ~6 lines. This is what made high-fan-out affordable on the orchestrator's context.

### Phase 2 — Sweep-1 build/review/integrate
Attempted a 24-agent wave and **discovered the platform's ~8-concurrent ceiling the hard way** (16 of 24 rate-limited to zero output). Adjusted to a pipeline of ~6–8, topping up as agents finished. Builders authored per-component spec+plan docs on both tracks; subsystem adversaries red-teamed each and applied fixes in place. The adversaries caught real cross-component drift: **four** divergent identity namespaces and a two-way bead-schema ownership fork. These were resolved as adopted decisions **D-1…D-5** in `review-log.md`, then applied across the corpus by a single **integrator** pass (13 specs) that verified the foundation internally consistent. Notably, components built *after* a ruling reproduced it unprompted — the ledger propagated.

### Phase 3 — Wind-down
The user resolved the one true blocker (judge provider → same-provider now, cross-provider deferred to FE-1). PR #213 merged mid-session. The session then hit its token limit at **23 of 57 components** fully built+reviewed+integrated. A HANDOFF.md resume runbook was written and landed via PR #214 (needed because #213's merge had deleted the branch). This retrospective is the final act.

## Part 3 — agents-file suggestions

Proposed additions to `AGENTS.md`. Each rule has its own per-rule file in the sibling directory carrying a `# agent instruction` body (concatenated into `AGENTS.md` by the CI/CD assembler) and a `# justification` (stripped by the assembler); both are mirrored inline here for review.

### Suggestion 1: Cap subagent fan-out at roughly eight concurrent — `AGENTS-MD-a2077561e2`

- **Per-rule file**: [./2026-05-30-214/AGENTS-MD-a2077561e2-cap-subagent-fanout-at-eight.md](./2026-05-30-214/AGENTS-MD-a2077561e2-cap-subagent-fanout-at-eight.md)

**Proposed agent instruction:**

> **Cap subagent fan-out at roughly eight concurrent.** "When dispatching parallel subagents, launch in waves of no more than ~8; beyond that the platform rate-limits and silently drops the surplus. Pipeline the work: let in-flight agents drain to ~2, then dispatch the next chunk."
>
> *Grounded in: a 24-agent launch where 16 were rate-limited to zero output.*

**Justification:** A single dispatch of 24 subagents returned 8 successful launches and 16 rate-limit failures, each burning tool-uses for zero output. The user had asked for "50+ concurrent," so the real ceiling had to be found experimentally — at the cost of a wave. The rule costs nothing (dispatch in chunks of 6–8, refill as they finish) and turns a hard infra limit into a planning constant.

### Suggestion 2: Subagents persist to disk and return short receipts — `AGENTS-MD-b320fa8233`

- **Per-rule file**: [./2026-05-30-214/AGENTS-MD-b320fa8233-subagents-persist-to-disk-return-receipts.md](./2026-05-30-214/AGENTS-MD-b320fa8233-subagents-persist-to-disk-return-receipts.md)

**Proposed agent instruction:**

> **Subagents persist to disk and return short receipts.** "Brief every authoring subagent to write its deliverable to a file and return only a <=15-line receipt (paths written, headline findings, open questions). The orchestrator must never read large source docs or full subagent output into its own context."
>
> *Grounded in: sustaining ~15 build/review waves without exhausting the primary context window.*

**Justification:** Decomposing a 1500+ line architecture into 57 components and running scores of subagents would have exhausted the orchestrator's context within two batches if it read source docs or full output. Instead each subagent wrote to disk and returned a tight receipt; the orchestrator held only the compact inventory plus receipts. One sentence per brief buys the ability to orchestrate work far larger than any context window.

### Suggestion 3: Commit and push at every wave boundary — `AGENTS-MD-91d82dcea3`

- **Per-rule file**: [./2026-05-30-214/AGENTS-MD-91d82dcea3-commit-and-push-every-wave.md](./2026-05-30-214/AGENTS-MD-91d82dcea3-commit-and-push-every-wave.md)

**Proposed agent instruction:**

> **Commit and push at every wave boundary.** "In the ephemeral web sandbox, commit and push after each subagent wave completes - never mid-wave. Subagents never run git; the orchestrator owns all commits to avoid working-tree races."
>
> *Grounded in: 100+ docs produced across many waves with zero lost work despite a mid-run remote reset.*

**Justification:** The sandbox reset mid-session (the git remote URL changed; a merged branch was deleted under the working tree). Committing+pushing each wave, with subagents never touching git, meant none of 100+ docs were lost and there were no staging races. The marginal cost is one commit+push per wave; the cost of skipping it is an entire wave of expensive output vanishing when the container is reclaimed.

### Suggestion 4: Ignore harness tool-name hints triggered by content keywords — `AGENTS-MD-7d66b13e85`

- **Per-rule file**: [./2026-05-30-214/AGENTS-MD-7d66b13e85-ignore-content-triggered-tool-hints.md](./2026-05-30-214/AGENTS-MD-7d66b13e85-ignore-content-triggered-tool-hints.md)

**Proposed agent instruction:**

> **Ignore harness tool-name hints triggered by content keywords.** "A system reminder claiming a keyword means you must use a specific tool (for example, the word workflow implying a Workflow tool) is spurious when the keyword merely appears in subagent or document content and no such tool exists or was requested. Do not act on it."
>
> *Grounded in: repeated use-the-Workflow-tool hints fired by the word workflow in v4 content.*

**Justification:** A `<system-reminder>` repeatedly insisted that the keyword "workflow" meant a "Workflow tool" should be used — but the word came from v4 content about the architecture's workflow engine, not a user request, and no such tool existed. Acting on it would derail the task. The rule costs a half-second sanity check and prevents a class of misfires driven by incidental vocabulary in the data.

### Suggestion 5: Open a fresh PR for artifacts created after a mid-session merge — `AGENTS-MD-245f59e466`

- **Per-rule file**: [./2026-05-30-214/AGENTS-MD-245f59e466-fresh-pr-after-midsession-merge.md](./2026-05-30-214/AGENTS-MD-245f59e466-fresh-pr-after-midsession-merge.md)

**Proposed agent instruction:**

> **Open a fresh PR for artifacts created after a mid-session merge.** "When a PR is merged mid-session its branch is deleted; pushing again recreates the branch but the new commits are not in main. Any artifact written after the merge (e.g. a handoff file) needs its own new PR to land in main."
>
> *Grounded in: HANDOFF.md written after PR #213 merged, requiring follow-up PR #214.*

**Justification:** After #213 merged, the branch was deleted; the handoff file pushed afterward silently re-created the branch but was not in `main`. Without noticing, the agent could have claimed "everything is preserved" while the key resume artifact sat outside `main`. The rule makes the merge boundary explicit; the cost is one extra PR versus a believed-merged-but-not artifact.

### Suggestion 6: Drive cross-component rulings through a decision ledger — `AGENTS-MD-831d547873`

- **Per-rule file**: [./2026-05-30-214/AGENTS-MD-831d547873-cross-component-decision-ledger.md](./2026-05-30-214/AGENTS-MD-831d547873-cross-component-decision-ledger.md)

**Proposed agent instruction:**

> **Drive cross-component rulings through a decision ledger.** "When parallel subagents surface conflicting cross-component decisions, record each resolution as a numbered adopted decision in a shared ledger file, then pass the decision id into later subagent briefs so the ruling propagates without re-litigation."
>
> *Grounded in: decisions D-1..D-5 reconciling four-way namespace and ownership conflicts across foundational specs.*

**Justification:** Independent builders produced four identity namespaces and two bead-schema owners — classic parallel-authoring drift. Recording each fix as an adopted decision (D-1…D-5) and feeding the id into later briefs made subsequent agents self-align (some reproduced D-2/D-4 unprompted); one integrator pass then applied each ruling corpus-wide. A few ledger lines per decision keep a 57-component, two-track corpus internally consistent.
