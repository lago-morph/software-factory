# ADR 0033: P-25 CaMeL perimeter

- **Status**: Accepted
- **Date**: 2026-05-25
- **Deciders**: lead agent (Phase 5 Wave 5.1b parallel fanout)

## Context

Two candidates claim P-25 as a load-bearing substrate primitive: [BF-S §S-5](../../architectures/v3/tracks/brownfield-substrate-first.md) (substrate perimeter / trifecta-closure layer, production-scissors default-off) and [BF-M cycle stage 5](../../architectures/v3/tracks/brownfield-methodology-first.md) (production-adjacent boundary wrapped around the build stage). Per the [Phase-4.2 overlap analysis](../../architectures/v3/primitives/overlap.md#coverage-tier-summary-phase-5-adr-priority-signal), P-25 is in the **shared-by-2** coverage tier (4 primitives total); the [auto-005 Round 2 decision](../../architectures/v3/decisions/auto-005-phase-5-dispatch-shape.md) folds 2-candidate primitives into common ADRs with cross-references rather than per-candidate splits.

The forcing failure-mode cascade is [F12 (lethal trifecta / prompt injection)](../../architectures/v3/failure-modes-v3.md#f12--lethal-trifecta--prompt-injection) → [F33 (adversarial-prompt defeat of LLM security analysis)](../../architectures/v3/failure-modes-v3.md#f33--adversarial-prompt-defeat-of-llm-based-security-analysis) → [F44 (lethal-trifecta production-scissors default)](../../architectures/v3/failure-modes-v3.md#f44--lethal-trifecta-production-scissors-default), with [F56 (guardrail-bypass under stress)](../../architectures/v3/failure-modes-v3.md#f56--guardrail-bypass-under-stress-replit-class-incident) co-located. The corpus is explicit that prompt-level filtering cannot be hardened: the defence must shift from adversarial-string filters to a typed boundary on **dataflow**, with substrate-level enforcement to avoid [F53 voluntary-discipline fragility](../../architectures/v3/failure-modes-v3.md#f53--voluntary-discipline-fragility-kahana-fragile-dependency-class). The [P-25 buildability sketch](../../architectures/v3/primitives/P-25-camel-perimeter.md) verdicts the primitive `designed-system` with a partial research-grade flag scoped strictly to **utility-tax calibration** (deferred to Phase 8 lean-eval).

## Decision

**Build P-25 as a capability-typed perimeter implemented as a typed-boundary library wrapping the released [CaMeL reference implementation](../../architectures/v3/primitives/P-25-camel-perimeter.md#construction-path) (`google-research/camel-prompt-injection`).** The perimeter ships the Privileged-LLM / Quarantined-LLM split, a restricted-Python-AST interpreter, and the capability-propagation lattice from the paper. Envelope typing at the Python boundary uses `pydantic` + `attrs` to express the per-value `(provenance, readers, inner-source)` capability tokens; a Rust-based wrapper provides the equivalent typed envelope at the syscall boundary for native-code consumers. Tools are typed by required-capability sets; the interpreter compares the carrier token's profile to each tool's policy and raises `CapabilityError` on mismatch — no call dispatched.

**Input validation is strict at the perimeter.** Every external-origin value enters as `provenance: tool:<id>` and `readers: Public` until laundered through an explicit capability-issuance step. **Trusted operations escalate via capability tokens, not via in-band string credentials** — escalation is a typed substrate call that the interpreter records in the capability trace returned to [P-05 trajectory capture](../../architectures/v3/primitives/cluster-C1.md). [OPA-Rego](./0015-p-08-scenario-storage-with-runner-contract.md#decision) is invoked inside the interpreter at the policy-reconciliation step (reusing P-29's substrate, not reimplementing it). NORMAL vs STRICT mode is a per-work-unit-class config; under `production-adjacent` regimes the perimeter is mandatory and bypass is denied. Per-work-unit-class bypass is **configurable but substrate-logged** (the bypass cannot be set by the agent under review — F53-resistant).

## Alternatives considered

**B. Ad-hoc input validation per consumer (every tool-calling agent validates its own inputs).** *Why rejected:* this is [F53-fragile](../../architectures/v3/failure-modes-v3.md#f53--voluntary-discipline-fragility-kahana-fragile-dependency-class) by construction — it relies on every consumer remembering to validate, under time pressure, every input, every time. The corpus shows operator-voluntary discipline collapses precisely under the conditions where the perimeter matters most. It also reinvents the dataflow-tracking the CaMeL interpreter provides for free, and provides no audit substrate for capability traces.

**C. Container-isolation-only (sandboxes around builder processes, no in-process typed boundary).** *Why rejected:* container isolation is real defence-in-depth (eBPF/sandbox below the interpreter is retained for that reason) but does not give the **dataflow-tracking** that breaks the lethal trifecta. A container with production scissors inside it still loses to F12 if the prompt-injection vector triggers tool calls the sandbox is authorised to make. The typed-interpreter pattern is load-bearing because it operates on capability tokens per value, not on process boundaries; sandbox + perimeter are complementary, sandbox-alone is not sufficient. See [P-25 sketch §Prior-art alternatives](../../architectures/v3/primitives/P-25-camel-perimeter.md#construction-path).

## Consequences

**Easier:** F12 → F33 → F44 cascade is closed at the substrate by capability-typed dataflow rather than by per-agent discipline ([F53 closed](../../architectures/v3/failure-modes-v3.md#f53--voluntary-discipline-fragility-kahana-fragile-dependency-class) on this surface). Both BF-S and BF-M consume the same `CaMeL.execute(plan_ast, capability_profile, policy)` contract; F56 stress-induced guardrail-bypass is substrate-enforced (the model cannot bypass a capability check by being persuaded — the check happens outside the model). Capability traces feed P-05 uniformly.

**Harder:** The CaMeL ~7-point AgentDojo headline utility tax is real and structurally non-zero — per-deployment calibration is required and is deferred to Phase 8 lean-eval per the [P-25 sketch §Utility-tax engagement](../../architectures/v3/primitives/P-25-camel-perimeter.md#camel-utility-tax-engagement-bf-m-oq-t3). Policy authoring (per-tool required-capability sets) becomes a methodology-layer responsibility, not an agent-discipline one. Native-code consumers must marshal through the Rust envelope wrapper, adding a build-time dependency.

**Explicitly NOT promising:** (a) defence against text-to-text attacks (phishing, summary-tampering) with no dataflow component — out-of-scope per CaMeL `main.tex:167`; combine with content review. (b) Closure on ROP-analogy gadget attacks against the capability lattice; defence-in-depth (eBPF, sandbox) is the named mitigation, not stronger typing. (c) The per-deployment acceptance criterion for the utility tax — that is a Phase-5 production-adjacency-policy ADR + Phase-8 measurement, not this ADR.
