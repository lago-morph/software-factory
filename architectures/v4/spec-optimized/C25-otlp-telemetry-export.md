## 1. Purpose & responsibility

C25 is **the telemetry-export contract for the factory**: it defines *how Claude Code agents are configured to emit observability data*, *which two sinks that data flows to*, and *the named contract the rest of the factory consumes telemetry against*. It is the **first stage of the observability pipeline C25 → C26 → C27** (OTLP export → Collector → LangFuse) and simultaneously the **source of the raw-API-bodies escape hatch that C24 watches** (raw bodies → CXDB). It is an `interface` in the inventory because C25 *is* a contract surface, not a running process (DELTA-01): Claude Code emits, C26 receives, C24 consumes the inbox; C25 is the frozen agreement that ties their wires together and the env-var block C04 injects to make emission happen.

Concretely C25 owns four things:

1. **The enablement config (DELTA-01, DELTA-05).** The validated telemetry env-var block — `CLAUDE_CODE_ENABLE_TELEMETRY`, the `OTEL_*` exporter/endpoint/protocol selection, the mTLS knobs, and `OTEL_LOG_RAW_API_BODIES` — that C04 injects into every factory agent session, with frozen factory defaults (gRPC :4317, metrics+logs on, traces-beta off-by-default).
2. **The Two-Sink contract (DELTA-02, resolves G04).** An explicit declaration that telemetry fans out to **two non-converging sinks** — Sink A (structured OTLP → C26 → LangFuse) and Sink B (raw bodies → C24 → CXDB) — with the OTLP↔CXDB edge declared a permanent **anti-edge**.
3. **The raw-bodies producer contract (DELTA-03).** The producer half of the `OTEL_LOG_RAW_API_BODIES=file:<dir>` inbox: directory, isolated mount, identity, and file-readiness semantics, pinned to C24's consumer-side readiness protocol (C24 DELTA-05/OQ5).
4. **The correlation-key guarantee surface (with C28).** The contract that every emitted signal — both sinks — carries `prompt.id`/`session.id`/`user.account_uuid`/`organization.id`/`terminal.type`, so C24 can reconstruct parent chains and C26→C27 can group sessions. C28 *guarantees* the keys are emitted; C25 *configures* the surface and *names the contract* that the keys are present.

What C25 is **NOT**:
- **Not a running process / daemon.** (DELTA-01) There is no "C25 service." Emission is Claude Code's; receiving is C26's; raw-body consuming is C24's. C25 is config + contract.
- **Not the OpenTelemetry Collector (C26).** C26 *receives* the OTLP wire on :4317 and fans out to LangFuse. C25 stops at "the agent is configured to send to :4317"; C26 owns what happens on the receiving side. The C25↔C26 seam is the OTLP endpoint/protocol agreement.
- **Not the trace store (C27 / LangFuse).** C27 is two hops downstream of Sink A.
- **Not the CXDB bridge (C24).** C24 *watches* the `OTEL_LOG_RAW_API_BODIES` dir and posts to CXDB. C25 *produces/configures* that dir. The C25↔C24 seam is the inbox-directory + file-readiness contract.
- **Not the trajectory store (C21 / CXDB).** Sink B terminates at C21 *via* C24; C25 never talks to CXDB directly. The OTLP wire NEVER reaches CXDB (DELTA-02 anti-edge).
- **Not the emitter of correlation keys.** C28 (agent loop) guarantees the keys land on every signal (C28 acceptance #5); C25 configures the surface and freezes the contract that they are present. C04 owns `session.id` generation/resume.
- **Not an OTLP→CXDB translator.** v4 explicitly skips this (AI-CONTEXT §5.4 Highest impedance, §11.1/§11.3 rejected). C25 *forbids* it as an anti-edge (DELTA-02).
- **Not the anomaly/self-heal consumers** (C36/C22-typed readers). They read the *stores* (LangFuse/CXDB) C25's sinks feed; they never call C25.

## 3. Interfaces / contracts

Named-and-described (sweep 1; the concrete env-var schema with types/defaults/validation, the inbox-filename grammar shared with C24, the OTLP wire/port table, and the conformance suite land in sweep 2). C25 exposes a *configuration contract* and *two sink contracts*, not a callable API.

**The enablement config block (C25 → C04-injected, DELTA-01/DELTA-05):**
A validated, factory-default-bearing env block C04 sets on every agent `[[agent]]`:

| Var | Factory default | Purpose / contract |
|---|---|---|
| `CLAUDE_CODE_ENABLE_TELEMETRY` | `1` (DELTA-04 mandatory-on) | Master switch. `0` is a *flagged, non-default* state (re-opens F10/F22). |
| `OTEL_METRICS_EXPORTER` | `otlp` | Metrics → Sink A. |
| `OTEL_LOGS_EXPORTER` | `otlp` | Events/logs → Sink A. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://localhost:4317` (gRPC, DELTA-05) | The C25↔C26 wire. Single endpoint; per-signal split is a deployment knob, not per-agent. |
| `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` | unset (off) | Traces are *beta*; off-by-default to avoid a beta gate on the factory's load-bearing observability. A flagged opt-in. |
| `OTEL_LOG_RAW_API_BODIES` | `file:<isolated-inbox-dir>` (DELTA-03) | Sink B producer. The dir contract is shared with C24. |
| mTLS (`OTEL_EXPORTER_OTLP_CLIENT_KEY`/`_CERTIFICATE`; HTTP: `CLAUDE_CODE_CLIENT_CERT`/`_KEY`) | unset for localhost; **required-and-specified** for non-localhost C26 | Wire confidentiality when the Collector is not co-located. |
| `OTEL_METRIC_EXPORT_INTERVAL` / `OTEL_LOGS_EXPORT_INTERVAL` | 60s / 5s (Claude Code defaults) | Bounds Sink-A freshness; also bounds Sink-B body-arrival latency C24 sizes against. |

Pre: C04 owns `session.id`; C01 owns the inbox mount. Post: the agent subprocess emits both sinks; signals carry correlation keys (C28-guaranteed).

**Sink A — structured OTLP (C25 contract → C26):**
- Wire: OTLP/gRPC on `:4317` (factory default, DELTA-05) carrying **metrics** (session count, LoC, PRs, commits, costs, token usage, edit decisions, active time) and **events/logs** (user prompts, tool results, API requests/errors, tool decisions, permission changes, auth, MCP connections, plugins, skills) — and, *if and only if* the beta flag is set, **traces** (prompt→API→tool spans). Receiver = C26. **Invariant (DELTA-02 anti-edge):** this wire NEVER reaches CXDB.
- Pre: C26 is listening on the agreed endpoint/protocol. Post: structured signals land in C26 for fan-out to LangFuse. Failure of C26 to listen ⇒ bounded local drop, agent unaffected (DELTA-04).

**Sink B — raw API bodies (C25 producer contract → C24):**
- `OTEL_LOG_RAW_API_BODIES=file:<dir>` dumps *untruncated* request/response JSON to `<dir>`. Each dumped file is conversation-shaped and correlation-attributed (`session.id` etc. present per C28). **Producer-side readiness (DELTA-03, pinned to C24 DELTA-05/OQ5):** C25 owns *which dir*, *which isolated mount*, *under whose identity*, and the *file-completion signalling* (whether the exporter writes atomically via rename or stream-appends — the open question C24-OQ5 names; C25 is the spec that must *resolve* it for the consumer). Receiver = C24's `BodyWatcher`.
- Pre: C01 inbox mount exists with C43/C01 isolation; only the agent identity writes, only C24 identity reads. Post: complete body files appear for C24 to ingest. **Invariant (DELTA-02 anti-edge):** these bodies go to CXDB *via C24 only* — never via the OTLP wire.

**Invariants (frozen):**
- **Two-Sink, non-converging (DELTA-02, resolves G04):** exactly two sinks; OTLP-wire (Sink A) and CXDB-store (Sink B) are NEVER connected to each other. OTLP→CXDB is a declared anti-edge.
- **Correlation-keys-present (with C28):** every signal in both sinks carries `prompt.id`/`session.id`/`user.account_uuid`/`organization.id`/`terminal.type`. (C28 emits them; C25 contracts that they are present so C24 can parent-chain and C26→C27 can group sessions.)
- **Off-the-hot-path / fail-safe (DELTA-04):** telemetry export failure (Collector down, inbox unwritable) MUST NOT block, stall, or crash the agent loop. Export is async/buffered with bounded drop. Sink/store liveness is never an agent-run gate.
- **Mandatory-on (DELTA-04):** the factory default is instrumented; telemetry-off is a flagged exception, never silent.
- **Single factory wire (DELTA-05):** one endpoint/protocol default (gRPC :4317) for the C25↔C26 seam; protocol selection is a deployment knob, not a per-agent choice.
- **Raw-bodies isolation (DELTA-03):** the inbox is a secrets-bearing surface under C01/C43 filesystem isolation; write=agent identity, read=C24 identity.

## 4. Data model / state

C25 **owns no runtime state** (DELTA-01) — it is a configuration contract, not a process. Its "state" is declarative config and the *shape of the data crossing its two seams*.

- **Owned (declarative config):** the env-var block above, living in `city.toml`/C03 (`[[agent]] env = {…}`, `[[service]] name = "otel_collector"` endpoint, the inbox-dir path, the telemetry/beta feature flags). Version-pinned with the pack. This is the canonical "how is the factory instrumented" record.
- **Sink-A wire shape (not stored by C25):** OTLP metrics/logs/(beta)traces as Claude Code emits them — the OTLP protobuf/gRPC schema is Claude Code's + OTel's, not C25's to define. C25 *selects* which signals (metrics+logs on, traces beta-gated) and *where* (:4317 → C26). Persistence is C27's (LangFuse).
- **Sink-B inbox shape (the C25↔C24 contract surface):** a directory of untruncated request/response JSON files, conversation-shaped, correlation-attributed. C25 owns the *producer* contract (dir, mount, identity, readiness); C24 owns the *consumer* state (spool/cursor/quarantine — C24 §4). The files are the seam; neither side "owns" them as canonical state (the canonical trajectory is C21's, after C24 lands it).
- **Correlation attributes (the join keys):** `prompt.id`, `session.id`, `user.account_uuid`, `organization.id`, `terminal.type` — present on every signal in both sinks. `session.id` is the load-bearing one (C24's parent-chain key, AI-CONTEXT §5.4; owned/generated by C04).
- **Consistency model:** C25 holds no linearization authority. Sink A is best-effort/at-least-once with bounded drop (DELTA-04); Sink B's delivery guarantees are C24's (ack-before-release, C24 DELTA-03). Export *intervals* (60s metrics / 5s logs) bound freshness on both sinks but are not a consistency contract — a session that ends mid-interval still flushes per Claude Code's exporter semantics (sweep-2 verification, ties C24-OQ5).
- **Storage layout:** none beyond the `city.toml` config and the C01-provided inbox mount. No new datastore (mirrors v4's "no Postgres/Redis/Kafka" posture for the bridge path).

## 5. Behavior

Key flows (sweep-1 prose; sweep-2 = Mermaid sequence + the two-sink fan-out diagram):

- **Session start / instrumentation (the enablement flow):** C04 starts an agent session and injects the C25 env block (AI-CONTEXT §13.2). Claude Code initialises its OTLP exporter (gRPC :4317 → C26) and, if `OTEL_LOG_RAW_API_BODIES` is set, opens the raw-body dump to the isolated inbox. From this point the subprocess emits both sinks autonomously; C25 has no further runtime role.
- **Sink A — structured emission (the C25→C26→C27 pipeline):** during the agent loop, Claude Code batches metrics (60s) and events/logs (5s) and exports them over OTLP/gRPC to C26. C26 receives and fans out to LangFuse (C27) for trace browsing + session/prompt versioning. Each signal carries correlation keys so C27 can group by `session.id`. **Anti-edge held:** C26 fans out to LangFuse only — never to CXDB.
- **Sink B — raw-body emission (the C25→C24→C21 escape hatch):** in parallel, Claude Code dumps each untruncated request/response body to the inbox dir as a complete file (readiness per DELTA-03/C24-DELTA-05). C24's `BodyWatcher` picks up complete files and posts them to CXDB as parent-chained turns (C24 §5). The two sinks run independently from the same emitter; neither blocks the other.
- **Collector-down (Sink A degraded, DELTA-04):** C26 is unreachable → Claude Code's OTLP exporter buffers and, past its bound, drops, with no agent-loop impact. Metrics/logs freshness degrades (a flagged observability gap, re-opening F22 detection until recovery) but the run completes. Sink B (raw bodies → C24 → CXDB) is *unaffected* — the durable trajectory still lands. This is the G33-adjacent partial-failure story for the observability subsystem: the two sinks fail independently, and the *durable* one (Sink B, via C24's ack-before-release) is the one self-heal/replay depend on.
- **Inbox-unwritable (Sink B degraded, DELTA-04):** the inbox mount is full/unmounted → Claude Code's raw-body dump fails → again, no agent-loop crash (bounded/best-effort), but trajectory freshness degrades and `Health()` on C24 surfaces a stalled inbox. Sink A (structured) is unaffected. Operator alarm via C24's `inbox_depth`/`bridge-lag` (C24 §3).
- **Telemetry disabled (flagged exception, DELTA-04):** if `CLAUDE_CODE_ENABLE_TELEMETRY=0` for a given agent (e.g. a throwaway diagnostic), the run produces *no* observability for the self-heal loop and *no* trajectory for replay — explicitly flagged as an attribution/observability hole, never the default, never silent.
- **mTLS / non-localhost Collector (DELTA-05):** when C26 is not co-located, the mTLS env vars are *required and specified*; a mismatched/absent cert is a configuration failure surfaced at session start, not a silent plaintext-or-drop.

## 7. Cross-cutting

- **Security (load-bearing, DELTA-03):** the raw-bodies escape hatch dumps *untruncated* request/response JSON — secrets, full prompts, holdout/scenario content. C25 owns the producer-side bound: isolated C01 mount, identity-scoped write/read, C43 lethal-trifecta boundary. mTLS specified for non-localhost Sink-A wire (DELTA-05). The OTLP wire carries structured (truncated) signals — lower sensitivity than the raw bodies, but still attribution-bearing; mTLS protects it cross-host. Anti-edge (DELTA-02) also has a security dimension: keeping OTLP and CXDB separate keeps the high-sensitivity raw-body path on a single audited bridge (C24) rather than smeared across the Collector fan-out. In-flight body confidentiality/tamper-evidence before CXDB landing is shared with C24-OQ4.
- **Cost/scale:** C25 adds *no* runtime process and no new store — it is config, so its marginal cost is the export overhead Claude Code already bears plus the inbox disk. Sink-A volume is bounded by export intervals (60s/5s) and the C26 receive ceiling; Sink-B volume is bounded by raw-body size × request rate and the C01 inbox retention (sized jointly with C24's spool, C24 §7). The traces-beta-off default keeps the highest-volume signal (per-span tracing) off the load-bearing path until promoted.
- **Observability (of itself):** C25 has no `Health()` of its own (no process). Its health is *observed through its consumers*: Sink-A liveness via C26's receive metrics; Sink-B liveness via C24's `inbox_depth`/`bridge-lag`/`last_ack_ts`. A degraded sink is the bounded-degradation signal — C36 can read either as a numeric anomaly. The meta-point: C25 is the component that makes *everything else* observable.
- **Ops:** the C25 contract is pure configuration — a version-pinned env block in `city.toml`/C03 plus the C01 inbox mount + C26 `[[service]]` endpoint declaration (AI-CONTEXT §13.1/§13.2). Deploy contract: C04 injects the block on every agent; C01 provisions the isolated inbox; C26 listens on the agreed wire. "Verify events flow" (README §539) is the smoke-test acceptance. No daemon to supervise (DELTA-01). The doc pointer `code.claude.com/docs/en/monitoring-usage.md` (AI-CONTEXT §657) is the upstream source for the exact emitted-signal catalog and the exporter's file-write semantics that sweep-2 must verify (ties C24-OQ5).

## 8. Acceptance criteria & test strategy

1. **Two-Sink non-convergence (DELTA-02, G04):** trace the dataflow graph of a live factory — structured signals reach C26→LangFuse, raw bodies reach C24→CXDB, and there exists **no** path from the OTLP wire to CXDB nor from the raw-body dir to LangFuse. The OTLP→CXDB anti-edge is mechanically absent (assert no Collector exporter targets CXDB). **This is the G04 resolution test.**
2. **Verify-events-flow smoke test (README §539):** with the C25 block injected, a one-prompt Claude Code session produces (a) metrics+log events received by C26, and (b) at least one complete raw-body file in the inbox carrying all five correlation attributes.
3. **Correlation-key presence (with C28 #5):** every signal on both sinks carries `prompt.id`/`session.id`/`user.account_uuid`/`organization.id`/`terminal.type`; `session.id` from a resumed session matches the prior session (C04 resume), enabling C24 parent-chaining and C27 session grouping.
4. **Fail-safe under Collector-down (DELTA-04):** kill C26 mid-run → agent loop completes unaffected (turn latency independent of C26 state); OTLP export buffers then drops within bound; Sink B (raw bodies → C24 → CXDB) lands the full trajectory regardless. Joint with C24 acceptance #9 (off-hot-path) and C26.
5. **Fail-safe under inbox-unwritable (DELTA-04, DELTA-03):** make the inbox unwritable/full mid-run → agent loop completes unaffected; the failure is visible via C24 health, not an agent crash; Sink A unaffected.
6. **Raw-bodies isolation (DELTA-03, security):** the inbox is writable only by the agent identity and readable only by C24's identity under C01/C43 isolation; a non-agent process cannot read the secrets-bearing bodies. Holdout content in a body never crosses to an implementer-readable partition.
7. **File-readiness / no-torn-files (DELTA-03, resolves C24-OQ5 producer side):** under load, C24 never observes a mid-write body file — the producer-side completion mechanism (atomic rename / completion signal) is verified against Claude Code's actual exporter behavior (sweep-2 repo/doc inspection per AI-CONTEXT §657).
8. **Single-wire default (DELTA-05):** all factory agents export to the one frozen endpoint/protocol (gRPC :4317); a deliberately mismatched endpoint is a config-time failure, not a silent runtime drop; non-localhost C26 requires the specified mTLS or fails to start.
9. **Mandatory-on default (DELTA-04):** a default-configured agent is instrumented (telemetry on, both sinks); telemetry-off requires an explicit flag and is recorded as a flagged exception, not silently permitted.
10. **Traces-beta gating:** traces are emitted *only* when `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`; the load-bearing metrics+logs path does not depend on the beta gate.
