## Part 4 — proposed ADRs

Architectural decisions made in this session that you might want to record formally. **Titles only — no specs.** Author any of these via the `adr` skill if you decide they're worth recording.

- **`/reference-only/` is the canonical directory for processed primary sources** — Distinct from the transient `research/manual/` drop zone. The split is now established in PLAN.md §2 and the `reference-only/README.md`. Worth formalizing so a future session doesn't reinvent the directory.
- **Audit-pass commits are preferred over `git commit --amend` for iterative bug fixes within a PR** — Each audit pass landed as a discrete commit (`852db97`, `8eee478`, `20da79f`, `a7ec210`, `d827316`, `411a0ae`). The reviewer can see the audit trail; bisect across them; reviewers reading PR #34 can see exactly what each pass caught. Amending would have erased that.
- **Cherry-pick + restore-from-history is the recovery pattern when commits' parent files were moved or deleted on the target branch** — Demonstrated this session by `git show <hash>^:research/manual/<file> > reference-only/<new-name>` before cherry-picking sub-30, which then resolved cleanly as a rename/delete conflict.
- **Even in "approximate" sections (cost envelopes, time estimates), claims must trace to a source — fabricated numbers are out of scope** — The `$15-25 in Anthropic API calls per the run report` claim survived four audits before I caught it; it had no source. The cost of allowing fabricated numbers in approximate sections is exactly the cost of the audit passes that don't trust them.
- **After major section restructure, every `§N` and `§N.M` cross-reference must be re-resolved against the new structure before commit** — v0.8's rewrite renumbered ten sections; v0.9 found stale references to `§6` (was different content), `§17` (was Round 5 catalog in v0.7), `§18` (didn't exist), `§§1–4 of v0.1` (Round 1 predates v0.1), `§5.1`/`§5.2`/`§10.2`/`§10.4`/`§11.12`/`§14.4` (all v0.7-numbered subsections that no longer exist in v0.9). Auditing for these is mechanical — `grep -oE '§[0-9]+(\.[0-9]+)?'` then verify each against the current headings.
