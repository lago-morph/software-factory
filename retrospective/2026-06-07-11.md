## Part 1 — what happened

The session picked up a verified-live Dockerized Gas City prototype and had two
deliverables from `docs/HANDOFF.md`: (1) a one-line doc fix to `gc session nudge`,
and (2) the real feature — make `gc bd create --rig rigN …` get worked with **no
manual nudge and no manual sling**, verify it live against the shipped config with
a real subscription token, and update the docs.

### Phase 1 — orientation and branch reconciliation

Read HANDOFF + `AGENTS.md`/`AGENT-ENTRY.md`. Immediately hit a discrepancy worth
recording: the HANDOFF (and the kickoff prompt) named branch
`claude/software-factory-v4-setup-vTSqG`, but the harness directive and the actual
checked-out branch were `claude/stoic-ptolemy-Hvsiv`, which already equalled
`origin/main`. Trusting git over the stale handoff name avoided pushing to a
non-existent branch. (→ agents-rule.)

### Phase 2 — research the mechanism from the gascity source

Cloned `gastownhall/gascity` at the pinned tag `v1.2.1` and read the order
subsystem. Key findings that shaped the design: orders support an `exec` trigger
that the controller runs **directly** (no agent, no LLM, no token spend) on a
`cooldown`; molecule step-beads are typed `step` (not `task`) and carry
`gc.step_ref`; a slung bead's root gets `gc.routed_to` set. This gave a precise,
safe filter for "user task bead vs formula scaffolding," and confirmed the
HANDOFF's hint that a direct-sling order was the cleanest of the three approaches.

### Phase 3 — build the verify image and probe the real environment

Built a CA-trusting `Dockerfile.verify` (sandbox TLS-inspection CA trusted in
both stages) — gc 1.2.1 / bd 1.0.4 / dolt 2.1.0 / claude 2.1.168, matching the
pinned set. Before writing the order's script I ran a throwaway `_probe-env`
order: it showed the exec runs with `cwd=/workspace/city`, `PACK_DIR` pointing at
the city dir (not the source pack), `GC_RIG=""`, and — usefully — `RIG1_NAME`/
`RIG2_NAME` and the managed-Dolt `GC_DOLT_*` already exported. A second probe
(`_probe-route`) confirmed the list-filter + `gc sling` logic worked from the
city-scope exec env and that `sh` (dash), not bash, runs the exec (`set -o
pipefail` errored). (→ skill + agents context.)

### Phase 4 — tokenless proof of the deterministic half

Recognized the verification splits into a free controller-side half and a paid
agent half. Iterated the free half to convergence: the `route-rig-tasks` cooldown
order auto-routed a plain `gc bd create` to `rig1/gastown.polecat` in ~55s with
zero manual action, molecule step-beads were correctly excluded, and the order was
idempotent. All for $0. (→ skill.)

### Phase 5 — one paid live run, via a subagent

length), and dispatched a single background subagent to run the irreducible paid
half against the **shipped** `docker compose` stack. Result: a plain
`gc bd create --rig rig1` auto-routed at t+69s → `in_progress` at t+194s → polecat
committed `7a691f9` on a worktree branch → refinery merged it into `rig1` main →
bead `closed` (~t+10m), unattended; the `gc session nudge … "msg"` override
returned exit 0. The subagent tore the stack down to stop spend.

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its
own per-rule file in the sibling directory at

### Suggestion 1: Reconcile the working branch from git, not just the handoff doc — `AGENTS-MD-12cfc897d6`

- **Per-rule file**: [./2026-06-07-11/AGENTS-MD-12cfc897d6-reconcile-branch.md](./2026-06-07-11/AGENTS-MD-12cfc897d6-reconcile-branch.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Reconcile the working branch from git, not just the handoff doc.** When a handoff or pickup doc names a branch and the harness names a different one, do not trust either on faith: run `git branch --show-current`, `git branch -a`, and compare the candidate branch to `origin/main` before the first commit. The checked-out branch and the origin state are authoritative; a handoff doc's branch name is often stale from the session that wrote it.
>
> *Grounded in: the HANDOFF named `claude/software-factory-v4-setup-vTSqG` while the actual branch was `claude/stoic-ptolemy-Hvsiv`, which already equalled `origin/main`.*

**Justification** (verbatim from the per-rule file's `# justification` section):

A pickup brief and the harness disagreed on the branch name in the first minute of this session. The handoff said `claude/software-factory-v4-setup-vTSqG`; the real checked-out branch was `claude/stoic-ptolemy-Hvsiv`, already equal to `origin/main`. Had the agent trusted the handoff, the first `git push -u origin claude/software-factory-v4-setup-vTSqG` would have created a stray branch divorced from the real work, and every PR would have targeted the wrong head. The check is three read-only git commands costing seconds; the failure it prevents is a confusing tangle of branches that the operator has to clean up. The asymmetry is overwhelming, and handoff docs go stale on exactly this field because the branch is often regenerated per session.

### Suggestion 2: HTML-safe placeholders in PR and issue bodies — `AGENTS-MD-62f6cdc77d`

- **Per-rule file**: [./2026-06-07-11/AGENTS-MD-62f6cdc77d-html-safe-placeholders.md](./2026-06-07-11/AGENTS-MD-62f6cdc77d-html-safe-placeholders.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **HTML-safe placeholders in PR and issue bodies.** Do not put `<angle-bracket>` placeholders inside inline code in a PR or issue body: GitHub renders the body through an HTML sanitizer that silently strips them, even inside backticks. Use uppercase word placeholders (`ID-OR-ALIAS`, `MESSAGE`) or escape as `&lt;...&gt;`.
>
> *Grounded in: PR #9's body lost its `<id-or-alias> <message...>` text to HTML stripping and had to be re-edited.*

**Justification** (verbatim from the per-rule file's `# justification` section):

PR #9's description documented a CLI signature as `` `gc session nudge <id-or-alias> <message...>` ``. When the body rendered, GitHub's HTML sanitizer ate the `<id-or-alias>` and `<message...>` tokens — even inside the backticks — leaving the nonsensical "takes ` `". The whole point of that PR was to teach a command signature, so the stripped body actively misinformed reviewers. The fix was a second `update_pull_request` call rewriting every placeholder to an HTML-safe form. The marginal cost of getting it right the first time is zero (write `ID-OR-ALIAS` instead of `<id-or-alias>`); the cost of getting it wrong is a re-edit plus, if unnoticed, a permanently garbled record of the exact thing the PR was trying to convey.

### Suggestion 3: Isolate overlapping doc-edit tasks with selective staging — `AGENTS-MD-f108f2e5fc`

- **Per-rule file**: [./2026-06-07-11/AGENTS-MD-f108f2e5fc-isolate-overlapping-doc-tasks.md](./2026-06-07-11/AGENTS-MD-f108f2e5fc-isolate-overlapping-doc-tasks.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Isolate overlapping doc-edit tasks with selective staging.** When two tasks edit the same lines (for example a bug-fix and a later restructure of the same section), ship them as separate sequential PRs: complete and merge the smaller fix first, then `git stash` or selectively `git add` the second task's changes so each PR diff is reviewable in isolation. Do not let the second task's changes contaminate the first commit, and rebase the second onto the merged main before opening its PR.
>
> *Grounded in: Task #1 (nudge quoting) and Task #2 (autonomous-flow rewrite) both edited the same README and GETTING-STARTED nudge lines; stashing Task #2 kept PR #9 a clean two-file diff.*

**Justification** (verbatim from the per-rule file's `# justification` section):

This session had two deliverables that touched the *same lines*: Task #1 fixed the `gc session nudge` invocation, and Task #2 then rewrote those very sections into the autonomous flow. Worked naively in one branch, the two would have collapsed into one indistinguishable diff — the small, independently-verifiable doc fix buried inside a large feature change. Stashing Task #2's code (`git stash push -u entrypoint.sh pack/orders/`) kept PR #9 a clean two-file diff that merged on its own merit; after the merge, `reset --hard origin/main` + `stash pop` rebased Task #2 onto the new main so PR #10 showed only its own changes. The marginal cost is a couple of stash/reset commands; the payoff is two reviewable PRs instead of one muddy one, and the ability to land the verified fix even if the feature had hit a snag.
