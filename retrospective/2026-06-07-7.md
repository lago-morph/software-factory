## Part 1 — what happened

### Phase 1 — Windows slowness (PR #2)

The operator reported the bead store was "extremely slow" on a Windows laptop. The cause was that runtime state lived on a Docker Desktop **host bind mount** (`./workspace`): Dolt's many small reads/writes and its file locking crawl on the translated host filesystem (drvfs/9p over the WSL2 VM). The fix switched `/workspace` to a **named volume**. Two companion changes shipped alongside — `GC_BEADS_FORCE_FALLBACK=1` (intended to skip gc's native-store retry) and a pinned `DOLT_VERSION`. The first of these turned out to be a mistake corrected in PR #3.

### Phase 2 — gc status 3s timeout (PR #3)

After the volume fix, the symptom persisted: `gc status` logged `native_store_unavailable gate=force_fallback` and "loading session snapshot timed out after 3s." The cause was the `GC_BEADS_FORCE_FALLBACK=1` from PR #2: it forced every snapshot read through a `bd` subprocess, which blew gc's 3s budget on the WSL2 VM — even though `gc bd list` itself was fast. The fix was to **drop force_fallback** so gc uses its in-process native store on the now-fast volume. An important nuance the operator raised: the "native store" is NOT an exclusive embedded DB; it is an in-process Go client to the **same** managed Dolt server, and agents share that one server.

### Phase 3 — native_store_unavailable / bd_context (PR #4)

The `native_store_unavailable` warning reproduced on **Linux** too, ruling out Windows and gc-version as causes. Live-booting the real stack and running the failing preflight showed that `bd context` resolves a scope via its **git repo root**, and `/workspace/city` was not a git repo (`not a git repository`), so gc's `bd_context_agreement` preflight failed → fallback + warning. The data plane had always been healthy. The fix git-inits the city directory in the entrypoint. PR #4 also pinned the gascity-matched set from v1.2.1's `deps.env`: gc **v1.2.1** (the Dockerfile had floated on `main` and stamped 1.1.1) and dolt **2.1.0**.

### Phase 4 — documentation testing (PR #5)

The operator's directive: "you have to test documentation." Every command in README + GETTING-STARTED was run against the live container, surfacing **5 doc bugs**: (a) `gc bd` from the rig dir fails — it must run from the city dir with `--rig`; (b) the sling target `rig1/polecat` did not exist (it was `rig1/claude` at that point); (c) tmux session names need translation (`gc session list` shows `gastown.mayor`, tmux uses `gastown__mayor`) — docs switched to `gc session peek/attach <id>`; (d) `gc events --follow` needs the supervisor API, which is not running in standalone; (e) the run-3 `jq` pipeline failed silently. All were fixed and each correction re-verified verbatim.

### Phase 5 — live-token diagnosis of "the bead disappears" (PR #6)

With a real token, an explicitly-slung task ran end-to-end and produced a real commit. The reported "disappears" was a **scope mismatch**: a `gc bd create --rig` bead lives in the rig scope, but plain `gc bd list` shows the city scope, so the bead looked gone; and the mayor did not auto-dispatch it. At this point the docs were corrected to a human-driven "you sling" flow — which turned out to be a half-truth, corrected in PR #7.

### Phase 6 — native dispatch root cause + fix (PR #7)

The operator clarified that "100% human-guided" meant the *rest of the v4 backbone isn't built yet*, NOT "disable Gas City's native features." Investigating why native dispatch didn't work showed the gastown **rig roles (witness/refinery/polecat) never expanded**, because `[[rigs]]` had no pack import: `[defaults.rig.imports.gastown]` is only a **template that `gc rig add` consumes** at registration, and the prototype declares rigs **statically** and never runs `gc rig add`. The fix gives each `[[rigs]]` its own `[rigs.imports.gastown]`. Verified live with a real token: `gc agent list` shows `rigN/gastown.{witness,refinery,polecat}`, and the **native pipeline runs end-to-end** — mayor routes → polecat pool auto-scales 0→1 → polecat commits on a branch → refinery merges into the rig → bead closes (real commit `542f2ef` in rig1 main). Behavioral note: the mayor **triages** and won't blindly sling every open bead (gastown design); a `gc session nudge` or an explicit `gc sling rigN/gastown.polecat` routes a specific bead. Docs were corrected to the real native flow and the right worker name.

### Cross-cutting process lessons

The operator hammered these throughout:

- **Execute documentation.** Five doc bugs were invisible until each command was run.
- **Test the SHIPPED config, not a proxy.** The Windows slowness was missed because verification used `docker run` + named volume while the shipped file used `docker-compose` + bind mount.
- **Reasoned-from-source ≠ verified.** `force_fallback` was shipped from code-reading and introduced the 3s-timeout regression.
- **Handle live credentials without printing them.** The token was loaded into an env-file from the token file/FD and verified with `grep -c`, never printed.
- **Use subagents for the long live tests** so the orchestrator's context stayed lean.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory with exactly two sections: `# agent instruction` (verbatim, assembled into `AGENTS.md`) and `# justification` (stripped by the assembler). Part 3 mirrors both inline.

### Suggestion 1: Execute documentation before publishing it — `AGENTS-MD-c78b670a12`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-c78b670a12-execute-documentation-before-publishing-it.md](./2026-06-07-7/AGENTS-MD-c78b670a12-execute-documentation-before-publishing-it.md)

**Proposed agent instruction:**

> **Execute documentation before publishing it.** When you write or edit user-facing documentation that contains runnable commands, execute every command against the real running system and reconcile the docs to observed behavior before declaring them done; do not ship commands you only reasoned about.
>
> *Grounded in: five tutorial commands shipped wrong, all caught only by running them against the live container.*

**Justification:** Running every README and GETTING-STARTED command against the live container surfaced five doc bugs that were invisible on the page (wrong dir, non-existent target, name-translation gap, service-not-running, silent `jq` failure). The cost of not having the rule is a tutorial that fails for the first reader who follows it; the marginal cost is one pass of pasting each command into the already-running system.

### Suggestion 2: Verify the shipped artifact and config, not a proxy — `AGENTS-MD-36202f144e`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-36202f144e-verify-the-shipped-artifact-and-config-not-a-proxy.md](./2026-06-07-7/AGENTS-MD-36202f144e-verify-the-shipped-artifact-and-config-not-a-proxy.md)

**Proposed agent instruction:**

> **Verify the shipped artifact and config, not a proxy.** Verify a packaged deliverable by running the exact shipped artifact and configuration — the real compose file, entrypoint, and volume/network settings — on a target-equivalent platform, not a hand-rolled approximation that is easier to run.
>
> *Grounded in: verifying with `docker run` + a named volume while shipping `docker-compose` + a bind mount hid a Windows-only performance failure.*

**Justification:** The proxy verification (`docker run` + named volume) passed precisely because it swapped out the one property — volume type — where the bug lived; the shipped compose used a bind mount that crawled on Docker Desktop. The cost is shipping a deliverable that fails on the operator's machine while all internal checks are green; the marginal cost is booting the real compose file on the closest-available target platform.

### Suggestion 3: Reasoned-from-source is not verified — `AGENTS-MD-a924b58a5c`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-a924b58a5c-reasoned-from-source-is-not-verified.md](./2026-06-07-7/AGENTS-MD-a924b58a5c-reasoned-from-source-is-not-verified.md)

**Proposed agent instruction:**

> **Reasoned-from-source is not verified.** A change derived from reading source code is a hypothesis, not a verified fix; label it as unverified and run it against the real system before shipping it or claiming it works.
>
> *Grounded in: `GC_BEADS_FORCE_FALLBACK` shipped from code-reading and introduced the gc-status 3s-timeout regression.*

**Justification:** `GC_BEADS_FORCE_FALLBACK=1` was shipped on the strength of reading gc's source and was plausible but wrong — it forced snapshot reads through a `bd` subprocess and blew gc's 3s budget, a regression PR #3 had to reverse. The cost is shipping regressions that look like fixes; the marginal cost is one live run before claiming the change works.

### Suggestion 4: Use named volumes, not host bind mounts, for database-like state on Docker Desktop — `AGENTS-MD-926f858f5e`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-926f858f5e-use-named-volumes-not-host-bind-mounts-for-database-like-state-on-docker-desktop.md](./2026-06-07-7/AGENTS-MD-926f858f5e-use-named-volumes-not-host-bind-mounts-for-database-like-state-on-docker-desktop.md)

**Proposed agent instruction:**

> **Use named volumes, not host bind mounts, for database-like state on Docker Desktop.** Put database or DB-like runtime state in a named Docker volume, not a host bind mount, when the target may be Docker Desktop (Windows/macOS); the translated host filesystem is pathologically slow for the many small reads/writes and file locking such state generates.
>
> *Grounded in: Dolt crawled on a `./workspace` host bind mount and ran fast on a named volume.*

**Justification:** Dolt's small-read/write + locking pattern is the worst case for Docker Desktop's bind-mount translation layer; the operator hit an "extremely slow" store, and a named volume fixed it. The cost is a deliverable that is unusably slow on the most common dev platform; the marginal cost is one line in the compose file.

### Suggestion 5: git-init a scope that a tool resolves context from via its git root — `AGENTS-MD-41bef1fabc`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-41bef1fabc-git-init-a-scope-that-a-tool-resolves-context-from-via-its-git-root.md](./2026-06-07-7/AGENTS-MD-41bef1fabc-git-init-a-scope-that-a-tool-resolves-context-from-via-its-git-root.md)

**Proposed agent instruction:**

> **git-init a scope that a tool resolves context from via its git root.** If a tool (e.g. `bd`) resolves a working scope by walking up to a git repository root, ensure that scope directory is actually a git repo; a non-git scope fails the tool's context/preflight check even when the underlying data layer is healthy.
>
> *Grounded in: `/workspace/city` not being a git repo broke `bd context` and produced native_store_unavailable.*

**Justification:** `bd context` resolves scope via the git root; `/workspace/city` wasn't a git repo, so gc's preflight failed despite a healthy data plane — a deceptive failure that points at the store. The cost is debugging the wrong layer; the marginal cost is a one-line `git init` in the entrypoint.

### Suggestion 6: `[defaults.rig.imports]` is a `gc rig add` template, not an apply-to-all — `AGENTS-MD-abb64f4d71`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-abb64f4d71-gc-defaults-rig-imports-is-a-gc-rig-add-template-not-apply-to-all.md](./2026-06-07-7/AGENTS-MD-abb64f4d71-gc-defaults-rig-imports-is-a-gc-rig-add-template-not-apply-to-all.md)

**Proposed agent instruction:**

> **`[defaults.rig.imports]` is a `gc rig add` template, not an apply-to-all.** In Gas City, `[defaults.rig.imports]` is only copied into a rig by `gc rig add` at registration time; for rigs declared statically (in `city.toml`/`site.toml` without running `gc rig add`), give each `[[rigs]]` its own `[rigs.imports.<pack>]` or its rig-scoped agents will never expand.
>
> *Grounded in: gastown witness/refinery/polecat roles never appeared until per-rig imports were added.*

**Justification:** Native dispatch silently did nothing because the rig roles never expanded — `[defaults.rig.imports]` is a `gc rig add` template, and the prototype declares rigs statically. The cost is a system that boots clean, reports no error, and never routes work; the marginal cost is one import block per static rig.

### Suggestion 7: Pin the matched dependency set from the upstream's deps.env, not latest — `AGENTS-MD-b30e54baaa`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-b30e54baaa-pin-the-matched-dependency-set-from-the-upstreams-deps-env-not-latest.md](./2026-06-07-7/AGENTS-MD-b30e54baaa-pin-the-matched-dependency-set-from-the-upstreams-deps-env-not-latest.md)

**Proposed agent instruction:**

> **Pin the matched dependency set from the upstream's deps.env, not latest.** When building an image around an upstream tool that publishes a pinned dependency manifest (e.g. gascity's `deps.env`), pin your image to that matched set — the tool plus its companion binaries — at a release tag, not `main`/`latest`, to stay reproducible and avoid version skew.
>
> *Grounded in: floating on gascity `main` stamped gc 1.1.1, and `dolt latest` had once removed a flag the image relied on.*

**Justification:** The Dockerfile floated on `main` and stamped gc 1.1.1 instead of the intended v1.2.1; `dolt latest` had previously removed `sql-server --user`. The cost is a non-reproducible image that can break overnight; the marginal cost is reading one upstream manifest and pinning to a release tag.

### Suggestion 8: Handle live credentials without printing them — `AGENTS-MD-5b260a7909`

- **Per-rule file**: [./2026-06-07-7/AGENTS-MD-5b260a7909-handle-live-credentials-without-printing-them.md](./2026-06-07-7/AGENTS-MD-5b260a7909-handle-live-credentials-without-printing-them.md)

**Proposed agent instruction:**

> **Handle live credentials without printing them.** When a task requires a real token or credential, load it by reading the source file or FD directly into an env-file or env var, and verify only with non-revealing checks (e.g. `grep -c`); never echo, `cat`, or otherwise emit the secret into logs or transcripts.
>
> *Grounded in: the live-token runs built `.env` from the token file and verified with `grep -c`, never printing the token.*

**Justification:** Three live-token runs never printed the token: `.env` was built from the token file/FD and presence verified with `grep -c`. The cost of a leak is catastrophic and irreversible; the marginal cost of the safe pattern is zero.
