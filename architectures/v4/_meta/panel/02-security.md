## 1. Verdict

**`right-idea-but-change-X-before-building`** — the architecture names the right security goals (boundary-typed blast-radius, holdout integrity, attribution-by-default, honest residual register), but its two highest-risk properties both rest on a single unverified substrate fact, and the second-highest-risk mode (objective drift at P3b) has no mechanism — only a human checklist at a review cadence that is not yet defined.

## 2. Where v4 is sound (from my lens)

- **Attribution is genuinely substrate-native (F14).** Gas City's `created_by` on every bead and event is the strongest single security property in the corpus. It is not an add-on and cannot be accidentally omitted. Any post-hoc audit starts with a complete, attributable trail.
- **Deterministic-typing-as-primary-guard is the right philosophical bet (F33/F51).** Deciding boundary class by rule (CaMeL pattern, C43) rather than by LLM judgment eliminates a whole class of adversarial defeat. A probabilistic guard on a deterministic exfiltration path fails eventually; a deterministic guard does not.
- **Twins-by-default / production-scissors is the right default-deny posture (F44).** Requiring explicit per-pack opt-in to reach production — rather than requiring explicit opt-out — is the correct safe-fail orientation. Most harm comes from accidental production reach, and the scissors rule closes that class by construction once twins exist.
- **Honest residual register (C57) is architecturally rare and genuinely valuable.** The "no bare Addressed" invariant — every unbuilt mechanism must carry its exposure-window caveat — prevents the common failure mode where a coverage claim is true at spec time but false at deployment time. The G31 caveat traveling explicitly to C57 is exactly right.
- **D-20 (fence pulled to P2 precondition) is the correct call.** Requiring C43's boundary-typing half before the factory runs unattended closes the most dangerous exposure window without waiting for twins. This is the single highest-leverage sequencing decision in the plan.

## 3. Where v4 is weakest / riskiest (from my lens)

- **CRITICAL — The fence (C43) is a declaration, not a control, until G11 is resolved (D-23 / OQ-C43-1 ≡ OQ-C34-1).** C43's "boundary-typing half" pulled forward to P2 by D-20 consists of: a config declaration that a surface is `twin`-typed, plus the twin-by-default routing rule. But C43 explicitly drops the capability-grant enforcement layer (C02-04 DROPPED), drops spawn-time OS isolation (C04-05 DROPPED), and drops OPA (C42-06 DROPPED). The fence is a policy intent encoded in `city.toml`. Whether the Gas City pack loader *rejects* a production-defaulted config at load time, or merely *permits it with a later detect*, is the unresolved D-23 substrate fact. If `gc` is detect-not-prevent, then D-20's "fence pulled forward" is a declaration pulled forward — the blast-radius window is not actually closed, only documented. In the moment of a prompt-injection at P2 (factory running unattended, no twins yet), a declaration-only fence offers no resistance. The entire lethal-trifecta defense (F12/F44/F56 "Addressed") collapses to audit-log evidence of the breach.

- **CRITICAL — Holdout integrity is detect-after-the-fact with no model-family fallback (D-1 / G21).** C34 enforces the holdout invariant with filesystem permissions plus an after-the-fact audit. Per D-1, the judge runs on the same provider/family as the coder; cross-family judging is deferred to FE-1. This means the *sole* guarantee that the implementer did not train-against its own scenarios is: (a) a rig config declaration, (b) filesystem perms, and (c) C34's post-hoc log scan. Against a broad-tool-access Claude Code subprocess, (a) and (b) are disciplinary — a Bash tool call can read files that filesystem perms would block if the process runs as the wrong OS user. Whether Gas City actually prevents the read at tool-call time is again the unresolved D-23 fact. If `gc` is detect-not-prevent, then the coder *can* read the test set in the same tool-call it writes code, and the only record is in the audit log. A same-family judge cannot detect this from the trajectory alone. This is a single-layer, detect-only holdout boundary for a load-bearing integrity property — exactly the shape of a security guarantee that looks solid on paper and fails silently in production.

- **HIGH — P3b self-modification with F54 objective-drift mitigated only by a human checklist (D-21).** The factory modifies its own components at P3b. The objective-drift audit mechanism (F54) is registered unbuilt. D-21 mitigates with "a cheap periodic human checkpoint at each batched review point." Three problems: (1) the review cadence is not specified — "batched" at what interval?; (2) self-modification between checkpoints is unobserved; (3) at P3b the factory is already running unattended at scale (P2 precedes P3b), meaning the checkpoint frequency is the only brake on drift accumulation. The C57 register honestly marks F54 unbuilt, but honest registration is not a control. A factory that rewrites its own prompts, tuning packs, and fix-task schemas between human reviews can drift substantially before the next checkpoint. The D-21 decision defers the real detector to before L5, but P3b with self-modification is already within the dangerous zone.

- **MEDIUM — G37 plaintext secrets until "first real credential" (D-25).** Production scissors in `city.toml` reach real external systems; those endpoints need credentials. D-25 defers secrets management to "at first real credential." The risk is that in practice "first real credential" is recognized late — after a production scissors declaration is already in a config under git review, after an API token is stored in an env var visible in process-listing, after a credential has been committed in a test run. Secrets-management debt compounds fastest precisely when the system is first touching real production, which is the moment the fence matters most.

## 4. Changes worth making BEFORE implementation

- **Resolve D-23 (prevent-vs-detect) as Sweep-2 first action, and gate D-20's fence on the result.** D-23 correctly identifies this as the highest-leverage spike. But the implication must be made binding: if the spike finds that `gc` is detect-not-prevent, then C43 is not a fence — it is a logging policy — and D-20's "fence pulled to P2 precondition" must be re-evaluated before the factory runs unattended. The architectural response to a detect-only substrate is not to proceed with the current design; it is to add a compensating prevent layer (OPA, seccomp, or namespace isolation) or to descope the autonomy claim. **This is a go/no-go gate, not a noted caveat.** Cheap: one focused `gc` binary test, one week; high leverage.

- **Specify the D-21 human-checkpoint cadence as a hard ceiling tied to P3b entry, not a vague commitment.** "Periodic" and "batched" are not controls. Before the factory self-modifies a single component, define: the maximum interval between drift audits (wall-clock or number-of-self-modification-events, whichever is shorter), the specific artifact a reviewer inspects (the diff of what was modified vs the original spec intent), and who is responsible. Without this, the D-21 mitigation is a process intention, not a control. Cost: one day of design work; prevents silent multi-cycle drift.

- **Require C34's holdout audit to capture Bash-level reads, not just tool-invocation events, before P2.** The audit's soundness depends on the read-trail completeness (OQ-C34-2). A Claude Code subprocess can read scenario files via Bash `cat` without triggering a formal tool-call event in the Gas City bead log. If the audit only scans bead/OTLP events, not OS-level filesystem reads, it has blind spots that an adversarial (or merely misbehaving) agent can traverse silently. Confirm that the read-trail source captures filesystem access at the process level before treating C34 as an audit boundary. Cost: one spike against the OTLP raw bodies + Gas City event trail; medium effort.

## 5. What you'd verify first (highest-leverage unknowns)

- **D-23 spike: does `gc` prevent an out-of-partition tool call, or permit-with-log?** Stand up a real `gc` instance with C42's rig config, give the implementer rig a Bash tool, and attempt to `cat` a file in the `scenarios` partition. Observe whether the attempt is rejected (prevention) or succeeds and logged (detection). This single test answers OQ-C42-1, OQ-C34-1, and OQ-C43-1 simultaneously, and re-grades five "Addressed" failure modes (F28, F12, F44, F56, F51). No other spike has comparable leverage.

- **Read-trail completeness for C34's audit: do OTLP raw bodies + Gas City events capture every way a subprocess can read scenario bytes?** The concern is that `OTEL_LOG_RAW_API_BODIES` captures API request/response JSON, not OS-level file reads. A `cat scenarios/foo.md` in a Bash tool call produces a file read at the OS level; whether that path appears in the OTLP stream or only in the Bash output (which becomes an API response body) determines whether C34's audit can detect it. Verify against a real tool-call trace.

- **Objective-drift signal: what specifically would a human reviewer inspect at each D-21 checkpoint?** The audit needs a concrete artifact — e.g., a diff of the self-modified prompt template against its signed original, or a comparison of the meta-metric definition against the operator's stated intent at P2 entry. Without a named artifact, "human checkpoint" means the reviewer reads whatever the factory surfaced, which is adversarial to the factory's own drift direction. Define the artifact before the first P3b self-modification.

## 6. One-paragraph bottom line

v4's security architecture is philosophically correct — deterministic boundary typing, attribution-native substrate, honest residual register, production-scissors default-deny — but the entire lethal-trifecta defense and the holdout boundary both pivot on a single unverified fact: whether Gas City prevents out-of-partition access at tool-call time, or only logs it. D-23 identifies this as the highest-leverage spike, but the current design treats a detect-only outcome as a noted caveat rather than an architectural trigger. In the moment a prompt injection arrives at P2 (unattended factory, no twins yet, declaration-only fence), a detect-only C43 offers no resistance — the blast radius is open and the audit trail is evidence collected after the fact. The same gap undermines C34's holdout integrity in a factory where the judge runs on the same provider as the coder. These are not theoretical: they are the exact conditions during the P2–P3b window that D-20 was designed to close. D-20 closes the window only if the fence actually prevents. The recommended change is to make D-23's spike a go/no-go gate on D-20's precondition claim — not a research item to note in the register.
