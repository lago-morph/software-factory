# Brownfield track — legacy-ingestion-first

## §0 Axis declaration and defense

**Sub-axis.** *Code-archaeology is the primary organizing principle.* The factory's first move on any new brownfield codebase is a dedicated **ingestion phase** that produces a durable, machine- and human-readable model of what is already there — structure, conventions, test patterns, hot paths, debt clusters, idioms, latent invariants, runtime traces — before any per-cycle methodology runs. Every downstream choice (work-unit shape, substrate primitive set, gate definitions, regime classification, scenario library) is *derived from the ingestion artifact*, not assumed in advance.

**Why this axis, not substrate-first or methodology-first.** UC4 names the brownfield mandate as *"analyzing what is there and growing it"* — that is the *defining* characteristic, not a side condition. The other two brownfield tracks (substrate-first, methodology-first) inherit a generic substrate or generic loop and *apply* it to a codebase. This track inverts: ingestion fidelity *constrains* the substrate's primitive set and *parameterises* the methodology's gates. The corpus directly supports the inversion: CTR-G4 (StrongDM "code as opaque weights" vs. UC4 "code-archaeological") and F20 (maintenance-vs-greenfield asymmetry, brownfield-critical) both say that brownfield's load-bearing fact is the *existing* code, not the *new* code; nothing the factory does is intelligible without first having read what is there.

**Anticipating Phase-3 adversarial passes.**

- *"Ingestion is just a one-time bootstrap; it doesn't deserve to be the organising axis."* Rebuttal: F20 (brownfield-critical), F34 (cross-layer drift, brownfield-critical), F35 (federation-as-family drift, brownfield-high), F54 (goal subversion, brownfield-critical), F58 (runtime/design-time compliance split, brownfield-high) all describe failures that recur every cycle whenever the factory's *model of the codebase* drifts from the codebase itself. Ingestion is not one-shot — it is a continuously-maintained substrate artifact (call it the **codebase model**), refreshed per cycle. The axis is "the codebase model is the primary substrate primitive," which is exactly what no other brownfield track centres.
- *"This is just substrate-first dressed up."* Rebuttal: substrate-first builds generic substrate primitives (sandbox, judge router, watchdog) and treats the codebase as an input to them. Ingestion-first builds *codebase-specific* primitives — derived per-instance — and treats generic substrate as a host for them. The Phase-4 boundary line falls in a different place: scenario storage, judge prompts, gate thresholds, and watchdog triage rules are all *parameterised by* the codebase model in this track; they are *fixed* in substrate-first.
- *"Why doesn't greenfield need this?"* Rebuttal: it might (the cold-start tracks ask exactly that question, per brief §5). But greenfield has *no* existing code to ingest — its analogue is corpus/domain ingestion, which is a different problem. The asymmetry UC4 names is real (CTR-G1).
- *"Ingestion at this scale is the F21 trap."* Rebuttal acknowledged: F21 (context-window exhaustion) is rated **brownfield-critical** precisely because brownfield ingestion saturates context fastest. The track's answer is that ingestion produces a *persisted, indexed, queryable artifact* (the codebase model), not a single mega-context. Per-cycle agents query the model; they do not re-ingest each cycle. This is the *whole point* of treating ingestion as substrate, not methodology.

## §1 Architecture sketch

The architecture has three loops over a single durable artifact.

**Durable artifact: the Codebase Model.** A versioned, queryable, multi-view representation of the existing codebase. Views include: (a) structural — modules, dependencies, call graphs, schema; (b) conventional — idiom register, lint conventions, test patterns; (c) historical — commit cadence per area, churn hotspots, attribution; (d) runtime — production traces, error fingerprints, performance hot paths where telemetry exists; (e) invariant — extracted from tests, types, runtime assertions, schema constraints; (f) debt — TODOs, deprecation markers, known-bad regions, dependency staleness. The model is *built* by the ingestion loop, *queried* by the work loop, *refreshed* by the maintenance loop. It is the primary substrate primitive of this architecture.

**Loop 1: Ingestion (deep, slow, run once per codebase + refresh on declared triggers).** A dedicated multi-agent ingestion phase whose deliverable is the codebase model. Inputs: the repository, git history, CI logs, runtime telemetry, existing tests, existing docs, AGENTS.md/CLAUDE.md scaffolds if present. The ingestion phase is the brownfield analogue of greenfield cold-start (brief §5) — it has the same load-bearing status (per CTR-G3, the corpus does not establish that the two are symmetric; this track treats them as *parallel* without claiming identity). Ingestion runs to completion before the work loop dispatches its first cycle.

**Loop 2: Work (per-cycle, methodology-shaped, queries the codebase model).** The work-unit-class taxonomy (per D2) is *derived from the codebase model*, not pre-decided. A codebase with a heavy issue tracker and stable architecture surfaces *issue-from-queue* work units (Atelier-style; OQ-B4); a codebase with active spec-driven refactoring surfaces *change-request-against-spec* (Refinery-style); a codebase whose model shows accumulating debt and no issue queue surfaces *codebase-evolution proposals*. The methodology layer is thin: it dispatches the right unit shape for the codebase model's profile, runs the cycle, gates the output against scenarios derived from the model.

**Loop 3: Maintenance (continuous, low-cadence).** The codebase model drifts: code changes, runtime patterns shift, conventions evolve as agents themselves modify the codebase. A maintenance loop re-runs ingestion deltas, reconciles model with reality, and refreshes invariants. This is the brownfield-specific defence against F34 (cross-layer drift), F55 (behavioural drift / self-reference loop), F57 (design-authority erosion).

**Scenarios are inherited from the codebase model, not authored out-of-tree.** This is the explicit challenge to D-2 (per the brief's own fragile-default flag). Existing test suites, production traces, incident replays, runtime invariants, and integration patterns ARE the scenario set. New scenarios are *derived* from gaps in the model (regions with low test coverage, runtime patterns no test exercises, invariants extracted from code but not enforced anywhere). The model itself records derivation provenance so holdout discipline (D-4) can be enforced *within* the inherited set: the substrate marks subsets of the model as held-out, and ingestion-aware judges enforce the partition.

**Regime classification is derived from the model, per work-unit-class.** A regression-fix against a high-coverage, low-churn module flows to L4-lights-out; an architectural change in a low-coverage, high-churn area flows to L3-augmented with human re-entry per OQ-B3. The model-driven classifier is the substrate primitive that resolves the §2.1 lights-out / L5 / regime tension *for this mandate*.

**Substrate-vs-methodology layer placement.** The codebase model, the ingestion engine, the model-query interface, the scenario-derivation primitive, the regime classifier, and the held-out partition enforcement are **substrate** (they are codebase-specific instances of substrate primitives, not methodology choices). The work-unit decomposer, the per-cycle gate selection, and the per-cycle agent topology are **methodology**. This places the boundary differently than substrate-first or methodology-first tracks — Phase-4 must adjudicate.

## §2 How this addresses each load-bearing concern

**§2.1 lights-out / L5 tension (mandatory).** The vocabulary mapping test (per glossary §0 and CTR-A4) is performed *per work-unit-class against the codebase model*, not globally. Lights-out is operationalised as: the factory operates without human in the per-cycle inner loop for work units the model-driven classifier marks as automation-eligible. Eligibility is a function of (a) codebase model's test coverage and invariant density for the touched region; (b) runtime telemetry density (more telemetry → more out-of-distribution signal → higher F1/F27/F46 resistance, per the brownfield severity reductions in the F-catalog); (c) historical churn cadence (high churn → operator's mental model already stale → degrade to L4 with sample audit); (d) Caremark/RSI exposure of the region (per F43, F54, F58). This is brief §2.1 option (c) plus (b): *regime classification + lights-out over a defined surface*. Jaymin's empirical bars (CTR-A1, CTR-A3, CTR-E3) are not adopted wholesale (per OQ-B6); the codebase-model-derived classifier is the bar source, with Jaymin's thresholds as one of several inputs to the eligibility function.

**UC4 (working hypothesis).** This track *operationalises* UC4's brownfield half — "analyzing what is there and growing it" is exactly the ingestion + maintenance loop. The track explicitly does NOT attempt to extend to greenfield (the unified-mandate tracks do that). UC4 is treated as falsifiable: if the codebase model's substrate primitive set turned out to be a strict superset of what a greenfield architecture needs (e.g., if greenfield's "ingest the problem domain" is structurally similar), UC4's "different solutions" claim weakens. This track does not pre-judge; it surfaces the question for Phase 3.

**OQ-B1 (mapping test).** Performed per work-unit-class as above; the vocabulary mapping holds for some classes and dissolves for others. Concretely: for *regression-fix* against well-covered modules, "lights-out" maps cleanly to L4 (operator out of per-cycle loop, sample audit) and is *not* L5 (Jaymin's anti-pattern claim does not bite because the out-of-distribution signal density is high, per the brownfield severity reductions on F1/F27/F46). For *post-mvp-evolution* against high-churn under-covered areas, the mapping is *adversarial*: "lights-out" in UC1's sense would require L5 because the per-cycle signal density is low, but the codebase model itself classifies these as ineligible — so the architecture honours UC1's lights-out *as a regime selector*, not a universal posture.

**OQ-B2 (boundary).** This track's boundary draw is explicitly different: the codebase model, ingestion engine, scenario-derivation, and regime classifier are substrate. Methodology is thin (work-unit dispatch + gate selection + agent topology). Phase 4 adjudicates against substrate-first and methodology-first.

**OQ-B3 (re-entry).** The model-driven classifier names the trigger conditions: model-detected anomaly (invariant violation in held-out region; production-trace pattern with no scenario; debt-cluster touched by a non-debt-targeting cycle), Caremark/RSI exposure escalation (F43, F54), or watchdog (Patrol-tier per D-6) escalation. The handback protocol is substrate-level: the model snapshot at re-entry time, the cycle's trajectory, the detected anomaly, and the proposed remediation are bundled into a human-review packet. Per CTR-A3, the handback explicitly does not assume Willison's "review is morally required" *per-cycle*; it triggers per-anomaly.

**OQ-B4 (unit of work).** *Determined by the codebase model, not pre-decided.* This is the most direct architectural answer to OQ-B4 in this track: the right unit shape for a given codebase is a function of what the codebase contains. Atelier-issue / Refinery-change-request / codebase-evolution-proposal are all available; the model picks. This is consistent with Phase-1's `brownfield-primary` re-tag of report 3 (Compound Engineering presupposes an issue queue, which presupposes a brownfield codebase) and with F20.

**OQ-B6 (empirical bars).** Not Jaymin's thresholds wholesale (per CTR-A1 / CTR-A5 / CTR-E3). The bars are model-derived: per work-unit-class, the eligibility function uses codebase-specific coverage / telemetry / churn metrics plus a small set of corpus-derived defaults (Jaymin K=5 and prompt-paraphrase as one input; Husain/Shankar binary-judge alignment as another, per followup/07; Anthropic same-model-Auto-Review precedent per report 23 §3.5 as a third). The eligibility function itself is auditable, not opaque.

**OQ-B8 (provider properties).** Ingestion phase has provider-property requirements distinct from work phase: long-context for whole-file structural analysis, vision for diagram/screenshot ingestion, tool-calling latency lower bound for repository traversal. Work phase has the usual requirements. The router abstraction (CTR-C4) is contested per Attractor's "per-provider profiles, do not unify" — this track sides partially with Attractor for the *ingestion* role (provider-aligned tools work best on whole-codebase reads) and partially with OpenHands routing for the *work* role.

**OQ-B9 (methodology evolution).** Methodology evolution is partly a substrate concern *here* because the codebase model itself evolves and the methodology must follow. The work-unit dispatcher's rules are model-parameterised; as the model changes, the dispatcher's behaviour changes. This is not Klaassen-style self-improving prompts (CTR-C3); it is substrate-driven methodology parameterisation.

**Load-bearing F-modes addressed by ingestion-first design.**

- **F20** (maintenance-vs-greenfield asymmetry, brownfield-critical): directly addressed; the ingestion + maintenance loops *are* the answer to F20.
- **F21** (context-window exhaustion, brownfield-critical): addressed by treating the codebase model as a persisted indexed artifact queried per-cycle, not re-loaded.
- **F34** (cross-layer drift, brownfield-critical): the maintenance loop reconciles fast-layer changes against slow-layer invariants in the model.
- **F12 / F33 / F44** (Lethal Trifecta cascade, brownfield-critical): the model's `production-access-surface` view explicitly maps where production scissors live; substrate enforces production-scissors-off (F44) per region.
- **F30 / F43 / F54** (governance, RSI, goal subversion; brownfield-critical / high): the model tags Caremark/RSI-exposed regions; cycles touching those regions are routed to elevated regime per the classifier.
- **F46 / F48 / F61** (single-model review blindspot, tacit collusion, context fragmentation): the model's invariants and runtime traces are the cross-model independent signal (per Phase-4 placement of judges); the partial mitigation of F1/F27/F46/F48 specifically credited to brownfield (out-of-distribution ground truth, per F-catalog §7 force 1) is *realised* by this architecture, not merely available.
- **F56** (guardrail-bypass under stress, Replit-class, brownfield-critical): the model's `production-access-surface` view + substrate-enforced production-scissors-off makes the Replit failure shape structurally not-available, rather than instruction-shaped (per CTR-B6 / D-2 / F53 voluntary-discipline fragility).
- **F59** (premature decomposition, greenfield-high / brownfield-medium): partial answer — the model's discovered structure parameterises decomposition rather than forcing it before discovery; brownfield's existing structure provides the discovery the F59 mechanism complains is missing.

**Load-bearing F-modes this track does NOT meaningfully address.**

- **F25** (design starvation): brownfield issue queues mitigate per the F-catalog rating (medium); not a focus.
- **F40** (last-mile drift): partially helped by inherited release infrastructure but not architecturally addressed; an open question.
- **F47** (visible-metric drift / Goodhart on tokens): orthogonal to ingestion-first axis; left to substrate/operator policy.

## §4 defaults: accepted vs challenged (all 7 marked)

- **D-1. Specs are the durable, version-controlled, human-curated artifact.** *Challenged (partial).* The durable, version-controlled artifact for the brownfield mandate is the **codebase model** (derived from the codebase, refreshed per cycle), not a human-authored spec. Specs exist for *change requests*, but they are derived from the model and re-anchored to it. Brier (followup [`12`](../../research/followup/12-brier-pace-layers.md), pace-layer-3-not-1) and CTR-B3 / CTR-B7 weaken D-1's claim that the spec is *the* primary artifact; for this track the model is the primary artifact and specs are layer-on-top.
- **D-2. Scenarios live outside the codebase as a holdout set.** *Challenged.* The brief itself flags D-2 fragile for brownfield. This track explicitly inverts: scenarios are *inherited from the codebase model* (tests, runtime traces, incident replays, derived invariants). Holdout discipline (D-4) is preserved via in-model partition enforcement. Corpus support: CTR-B5 WEAK-3 sharpening (StrongDM's own "Tokens are the fuel" enumeration already places scenario-equivalents inside the running system); CTR-G2.
- **D-3. Agent = Model + Harness.** *Challenged (partial).* The codebase model is a substrate primitive that does not decompose into either "model" or "harness." Ingestion-phase agents are graph-shaped (per CTR-F3's reframing: substrate supports both shapes). The D-3 vocabulary is workable for the work-loop's per-cycle agents but is incomplete for the ingestion phase. Corpus support: CTR-C1 + CTR-C10 (report [`37`](../../research/37-academic-llm-agent-collusion.md) natural-language-of-prompt as missing axis).
- **D-4. Holdout discipline (acceptance criteria withheld from builder agents) is substrate-enforced.** *Accepted with justification.* In this track, holdout is enforced *within* the inherited scenario set via model partitions. The substrate enforces the partition; methodology cannot opt out. Corpus support: F28; Round-2 C13.
- **D-5. Hard cost ceilings are non-optional in CI.** *Accepted with justification.* Ingestion phase has higher cost ceiling (one-time, deep) than work-loop cycles; both are enforced. The 10× variance in CTR-E1 (Cherny $100K vs. noosphr $500/day) and the CaMeL utility-tax measurement (CTR-E6, ~7-point) are reasons the ceiling itself is per-phase, not flat.
- **D-6. Tiered watchdog (Daemon / Triage / Patrol) is a substrate primitive.** *Accepted with justification.* The watchdog's *Triage* tier is parameterised by the codebase model (a "stalled" agent in low-coverage area triggers earlier than in high-coverage area). The *Patrol* tier checks model drift against codebase reality. Corpus support: Round-2 C14; F22, F23.
- **D-7. Trajectory capture is cheap and production-tested.** *Accepted with justification.* Trajectories from ingestion *become* part of the codebase model (how the model was built is itself queryable, supporting F14 attribution). OpenHands V1 measurement context (report [`11`](../../research/11-openhands-substrate-audit.md) §6) is treated as evidence the cost scales to ingestion-phase volumes.

## §5 Cold-start

**Not applicable to this track in the greenfield sense.** This track is brownfield-only (mandate-scope: brownfield); greenfield cold-start (brief §5) is mandatory only for greenfield tracks and unified tracks.

**However, brownfield has its own day-0 problem:** *legacy ingestion is the brownfield analogue of cold-start* (per CTR-G3). The ingestion loop IS the answer. Per Historian M5 the cold-start required-reading subset (reports [`25`](../../research/25-requirements-engineering-foundations.md), [`26`](../../research/26-prompt-underspecification-academic.md), [`30`](../../research/30-cognitive-escrow.md), [`31`](../../research/31-caremark-rsi-board-exposure.md), [`followup/10`](../../research/followup/10-governance.md)) was scoped to greenfield, but several of these reports are *also* load-bearing for brownfield ingestion: report 25 (GtWR-derived invariant-extraction discipline applies to ingesting existing specs/comments); report 30 (cognitive escrow applies to operator review of ingestion artifact); reports 31 + followup 10 (Caremark/RSI/AILCCP exposure of the existing codebase must be classified during ingestion so the work loop's regime classifier has the input). This is one of the open questions raised by this track for Phase 3: should ingestion get its own dedicated-section discipline parallel to greenfield cold-start?

## §6 What this track is NOT trying to be

- **Not a unified architecture.** Brownfield-only. The 3 unified-mandate tracks explore whether one architecture covers both; this track does not attempt to extend to greenfield.
- **Not a substrate-first track.** Substrate primitives are derived from the per-codebase model; this is a different boundary placement than substrate-first.
- **Not a methodology-first track.** Methodology is thin and model-parameterised; this is a different boundary placement than methodology-first.
- **Not comprehensive on regime / threshold-bars.** OQ-B6 is addressed through the model-driven eligibility function, not through a wholesale empirical-bar declaration. Other tracks may go deeper on the Jaymin / Husain-Shankar / Anthropic threshold corpus.
- **Not a refutation of Compound Engineering.** Compound Engineering's queue-and-skills shape is one of the available work-unit forms (per OQ-B4); the model picks it for codebases whose profile matches.
- **Not a Gas-City-vs-OpenHands substrate selection.** Either could host this architecture; the codebase-model primitive is the load-bearing addition either way. CTR-C5 left open.
- **Not a metaphor-debate (Brier).** This track is named "factory" but the architecture's central artifact is a *model of the existing system*; whether the right metaphor is factory, refinery, or archaeology lab is left to Phase 3.

## §7 Open questions surfaced by this track

1. **Ingestion-as-substrate vs ingestion-as-methodology.** This track places ingestion at the substrate layer. Phase 4 must decide. If substrate, then a shared substrate primitive ("codebase model") must be provided cross-architecture; if methodology, then per-architecture ingestion is acceptable and the substrate provides only model-storage primitives.
2. **Symmetry with greenfield cold-start (CTR-G3 surfaced; not resolved here).** Should ingestion get the same dedicated-section discipline that greenfield cold-start enjoys (brief §5)? If yes, brief §5 expands to cover both; if no, the asymmetry needs corpus-grounded justification.
3. **Model staleness vs. cycle latency tradeoff.** The maintenance loop's cadence is a tunable. Too slow → F34 (cross-layer drift) bites; too fast → cost ceiling pressure (D-5) bites. Open: what's the empirical anchor for cadence?
4. **Per-region vs. per-codebase regime classification.** This track lets the eligibility function classify per code region. Phase 3 must check: does this fragment governance (F43 board-visibility gap) by making the "what regime is the factory at" answer a function of which region is being touched?
5. **Ingestion provider-profile vs. work provider-profile (OQ-B8).** This track splits the provider-property requirements by phase. Does the corpus support that split, or is it a lead-agent invention?
6. **The codebase model as attack surface (F54 goal subversion).** Kahana's framing (report [`31`](../../research/31-caremark-rsi-board-exposure.md) §1) applies: an adversary who can poison the codebase model can drift the factory's objectives across cycles without tripping any single guard. The architecture needs a model-integrity primitive that this track gestures at but does not specify.
7. **Federation-as-Family Drift (F35) at the model level.** If multiple brownfield factories share a model-schema family, F35 applies to the model schemas themselves. Open: is model-schema variability governance a separate ADR?
8. **CaMeL utility-tax (CTR-E6) applied to the model.** A typed-interpreter boundary around model queries would close certain F12 paths but at measurable cost. Open: where does the boundary sit?
