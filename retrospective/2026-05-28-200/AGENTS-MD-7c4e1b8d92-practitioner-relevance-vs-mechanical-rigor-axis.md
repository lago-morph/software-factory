# agent instruction

**Practitioner-relevance is a distinct verdict axis from mechanical-falsifier-rigor in benchmark / lean-eval design.** When a brief commits to a falsifying-outcome discipline with a mechanical rubric (e.g., the falsification-designer's 4-item check: metric / artifact-state / threshold / §3-vs-YAML consistency), the brief MUST ALSO commit to a **practitioner-relevance** verdict axis — i.e., whether a domain practitioner who builds software for a living would agree the falsifier's metric maps to a software-quality outcome they care about. A falsifier can pass the mechanical rubric (by measuring a substrate-emitted distribution / confidence / count) while being **practitioner-thin** (the metric is rigorous but the practitioner cannot tell whether a "pass" means the methodology actually works). Both axes are needed; the mechanical axis is necessary but not sufficient. The brief's downstream consumer (a simulator-harness, an evaluator, a reviewer) MUST be given a two-tier verdict report: **mechanical pass cleanly** vs **practitioner pass cleanly**. A candidate that achieves only mechanical-pass-cleanly is a **partial witness** for whatever the falsifier targets; one that achieves both is a strong witness.

*Grounded in: Phase-8 auto-008 + Wave-8.1.b domain-practitioner audit. Falsification-designer audit returned 10/10 PASS on the 4-item mechanical rubric. Domain-practitioner audit returned 3 accept-as-is + 7 accept-with-named-amendments + 0 reject — load-bearing cross-cutting finding: 3 unified-attempts (U-A, U-B, D7-U-1) are mechanically-sound but practitioner-thin (measure substrate-emitted distributions/confidences/counts rather than software-quality outcomes). The Wave-8.2 cross-candidate evaluator-brief absorbed this finding via §4 practitioner-relevance weighting + a DEC-1.a falsification strength gradient (strong / mechanical-only / not-falsified). Without the two-tier discipline, a mechanically-passing-but-practitioner-thin unified-attempt would be reported as a clean DEC-1.a falsifier when in fact its evidence is substrate-self-test-shaped rather than methodology-quality-shaped.*

# justification

The mechanical-rigor axis (does the falsifier name a metric + artifact + threshold + maintain §3-vs-YAML consistency?) is easy to check programmatically and catches a clean class of defects: vague falsifiers ("the evaluator judges the methodology inadequate"), inconsistent statements (§3 says one thing, YAML says another), implicit metrics. But mechanical rigor is necessary-not-sufficient because:

- A falsifier can name a metric (e.g., `LayerInferenceConfidence`) that is internal to the substrate being tested. A pass means the substrate's own self-report says "I'm fine"; a fail means the substrate's own self-report says "I'm not fine". Both are mechanically rigorous; neither is practitioner-readable.
- A falsifier can name an artifact location (e.g., `solutions/audit/fc-ledger/*.jsonl`) that is meaningful to the methodology authors but opaque to a domain practitioner. The practitioner cannot tell whether the contents represent a meaningful pass or fail.
- A falsifier can name a numeric threshold (e.g., `MCC ≤0.55`) that is statistically meaningful but methodologically arbitrary — `MCC=0.6` might be no more practitioner-meaningful than `MCC=0.5`.

The practitioner-relevance axis catches these cases by asking: would a practitioner who builds software for a living, with no methodology-specific training, agree the metric-as-measured maps to "the methodology actually works"? Audit operationalization: a dedicated domain-practitioner subagent reviews each falsifier with high/medium/low practitioner-relevance verdicts; the lead-agent aggregation builds the two-tier report.

The rule applies to any benchmark/lean-eval/evaluation design — not just to multi-mandate / unified-attempt briefs. Phase-8 surfaced the discipline in the unified-attempt context because the DEC-1.a falsification was the load-bearing pressure-test, but the principle generalizes: any benchmark whose verdict matters to a downstream consumer should be evaluated on both axes.

Operational discipline: add a domain-practitioner subagent (or equivalent) to the bias-guard set for any benchmark/lean-eval design dispatch. Output: per-candidate practitioner-relevance verdict. Aggregation: two-tier report (mechanical / practitioner). Downstream report: strength gradient (strong = both / mechanical-only / not-passing).
