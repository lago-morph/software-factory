## Part 3 — agents-file suggestions

Seven proposed `AGENTS.md` rules; each has a per-rule file in the sibling dir (with `# agent instruction` + `# justification`). Mirrored inline:

### Suggestion 1: Four-axis coverage ledger for multi-component authoring runs — `AGENTS-MD-557513e54b`

- **Per-rule file**: [./2026-05-31-220/AGENTS-MD-557513e54b-four-axis-coverage-ledger.md](./2026-05-31-220/AGENTS-MD-557513e54b-four-axis-coverage-ledger.md)

> **Four-axis coverage ledger for multi-component authoring runs.** When a run authors or reviews many components/artifacts that each owe multiple passes, maintain a coverage ledger with one row per component and columns {Built, Reviewed, Incorporated, iNtegrated}, and treat the run as done only when every row is checked on every axis. Mark an axis done only when its evidence exists on disk (a `.review.md` for Reviewed; every finding applied-or-deferred-with-reason for Incorporated).
>
> *Grounded in: the v4 Sweep-1 run, where the ledger surfaced 11 built-but-never-reviewed components and guaranteed all 57 closed on all four axes.*

The operator's entering worry was "do not miss any that weren't reviewed." A flat to-do list can't distinguish built-but-unreviewed from reviewed-but-not-incorporated; the four-axis ledger made each visible and surfaced 11 components of silent review debt at stand-up. Cost: one small table updated per wave. Absence: exactly the silent debt the operator feared.

### Suggestion 2: Per-batch build-review-integrate, not build-all-then-review — `AGENTS-MD-62c3f73209`

- **Per-rule file**: [./2026-05-31-220/AGENTS-MD-62c3f73209-per-batch-build-review-integrate.md](./2026-05-31-220/AGENTS-MD-62c3f73209-per-batch-build-review-integrate.md)

> **Per-batch build-review-integrate, not build-all-then-review.** In a long unattended authoring run that may be cut off at any token-window boundary, close each batch fully (build -> adversary-review -> integrator) before opening the next, rather than building everything and reviewing later. This keeps completed batches fully closed and minimizes the unreviewed surface at any cutoff instant.
>
> *Grounded in: the v4 Sweep-1 run's per-batch cadence.*

Build-all-then-review under truncation risks "34 built, 0 reviewed" at cutoff — the worst state. Per-batch closure means only one batch is ever partial. Cost: more, smaller waves. Benefit: graceful degradation under truncation.

### Suggestion 3: Sibling-seam cross-check when reviewing parallel-built components — `AGENTS-MD-2c958df117`

- **Per-rule file**: [./2026-05-31-220/AGENTS-MD-2c958df117-sibling-seam-cross-check.md](./2026-05-31-220/AGENTS-MD-2c958df117-sibling-seam-cross-check.md)

> **Sibling-seam cross-check when reviewing parallel-built components.** When two components were built in parallel against a shared seam (each unaware of the other's final spec), brief each one's adversary reviewer to read the sibling's spec and verify the seam is described consistently from both sides. A single-component review cannot catch a seam mismatch; the cross-read can.
>
> *Grounded in: the v4 run, where the C14<->C15 DOT-surface seam and the C26<->C27 signal-set seam were mismatched and only the cross-read caught them.*

Parallel builders write their side of an interface blind to the other's final wording; the mismatch lives *between* the docs, invisible from inside either. C14 ("fail-loud on loops") vs C15 (needs a loop marker) and C26 (pipes metrics+logs+traces) vs C27 (traces-only) were both caught only by the cross-read. Cost: one extra file-read per reviewer.

### Suggestion 4: Restart interrupted async subagents after a session or sandbox rotation — `AGENTS-MD-a13d4f606d`

- **Per-rule file**: [./2026-05-31-220/AGENTS-MD-a13d4f606d-restart-interrupted-async-subagents.md](./2026-05-31-220/AGENTS-MD-a13d4f606d-restart-interrupted-async-subagents.md)

> **Restart interrupted async subagents after a session or sandbox rotation.** When an async subagent was dispatched but its completion never arrived and the session/sandbox has since rotated (e.g. the task-namespace path UUID changed), treat that subagent as dead: verify its deliverable is absent on disk, then re-dispatch it. Do not assume a pre-rotation background job survives the rotation.
>
> *Grounded in: the v4 run, where a C52 adversary launched before an interrupt never landed and was re-dispatched after the task-namespace UUID changed.*

Background subagents are tied to the launching container; nothing announces an orphan. C52's adversary launched before an interrupt; on resume the namespace UUID had changed and its review was absent. Treating it as "still running" would have hung the wave forever. Check: a `ls` + namespace-change awareness.

### Suggestion 5: Record risk-tolerance cross-component calls as provisional rulings plus morning-review — `AGENTS-MD-19e20132a2`

- **Per-rule file**: [./2026-05-31-220/AGENTS-MD-19e20132a2-provisional-ruling-morning-review.md](./2026-05-31-220/AGENTS-MD-19e20132a2-provisional-ruling-morning-review.md)

> **Record risk-tolerance cross-component calls as provisional rulings plus morning-review.** When a cross-component decision turns on operator risk-tolerance (e.g. a security or sequencing trade-off) rather than something derivable from the corpus or prior decisions, record it as a PROVISIONAL ledger ruling carrying the recommended resolution AND surface it as an explicit morning-review item for operator confirmation -- neither silently settling it nor freezing the run.
>
> *Grounded in: the v4 run's D-18 provisional C43 isolation pull-forward.*

D-18 (whether the factory may scale unattended + self-modify before its lethal-trifecta bound lands) is the operator's risk call, not the agent's. Freezing would violate the unattended mandate; silently choosing would usurp a risk decision. Provisional-ruling + morning-review does both right, in one isolated revertible commit.

### Suggestion 6: Spec known-hard or unsolved gaps honestly under a scope bar — `AGENTS-MD-e511bf4ddd`

- **Per-rule file**: [./2026-05-31-220/AGENTS-MD-e511bf4ddd-honest-unsolved-gaps.md](./2026-05-31-220/AGENTS-MD-e511bf4ddd-honest-unsolved-gaps.md)

> **Spec known-hard or unsolved gaps honestly under a scope bar.** When a component addresses a gap the source material flags as hard or unsolved, spec it honestly: partition what is tractable now from what is deferred, claim no more capability than is actually delivered, and register an unbuilt or partial item as exactly that. Never let a keep-it-minimal or is-it-addressed bar pressure a false 'addressed'.
>
> *Grounded in: the v4 run -- C49 framed the unsolved counterfactual-replay (G19) as deterministic-now vs deferred-LLM, and the C57 register kept F54 objective-drift marked UNBUILT rather than over-claimed.*

An "is it addressed?" bar quietly incentivizes overstating coverage — the most dangerous spec error because it hides risk. C49 partitioned tractable vs deferred (no reproduction claim for the LLM slice); C57 kept F54 UNBUILT. Cost: a less impressive coverage table. Benefit: real residual risks stay visible on a self-modifying system.

### Suggestion 7: Verify critical artifacts in HEAD independently of a subagent's git self-report — `AGENTS-MD-f724da5fef`

- **Per-rule file**: [./2026-05-31-220/AGENTS-MD-f724da5fef-verify-artifacts-in-head.md](./2026-05-31-220/AGENTS-MD-f724da5fef-verify-artifacts-in-head.md)

> **Verify critical artifacts in HEAD independently of a subagent's git self-report.** When a subagent reports it cannot see its own output via `git status` (or any sandbox/index quirk), do not trust that self-report either way -- the orchestrator independently verifies the artifact is on disk and in the committed tree (`git ls-tree -r HEAD --name-only | grep <path>`) before declaring it saved.
>
> *Grounded in: the v4 run, where the C57 capstone builder reported an empty `git status` but the files were present and already committed by a prior checkpoint.*

Subagents are briefed never to run git, so their repo-state view is partial; the C57 builder mis-read an empty `git status` as a quirk. The orchestrator owns git and is the only authoritative answer to "is this committed?" — one `git ls-tree` resolved it. Prevents both false-loss panic and false-save complacency at the capstone.
