## Part 1 — what happened

### Phase 1 — Extract §2.4 of the architecture comparison doc verbatim into a new canonical file

Issue #111 asked to split a 35-line out-of-date "Failure mode coverage" matrix out of `architectures/00-comparison.md` into its own file and to update the skill that proposes failure modes so the new file becomes the canonical index. The extraction phase was mechanically faithful: read the source file, use `sed -n '79,113p'` to extract the byte range, write the destination, and `diff` the extracted range against the new file's tail to confirm byte-identical copy. The verbatim-by-tool discipline came from the issue's explicit "Use tools for this to ensure is verbatim" — and saved time later when later commits would have to renumber sections without disturbing the cell content.

The harder half of Phase 1 was finding "the skill that tells you to determine and extract failure modes." There was no single such skill; failure-mode discovery is part of the `research-pipeline` stage-5 content-processing flow, where research reports propose candidate F-modes. I extended that doc with a "Failure-mode discovery and registration" procedure: pick the next free integer, grep for collisions, renumber the loser, propagate the renumber, register in the new canonical file in the same commit. The renumber-propagation step came from the worked F36/F37 collision documented in `research/PLAN.md` §3.6.

### Phase 2 — Three rounds of reviewer feedback reshape the location and the link discipline

Three PR review comments arrived in sequence, each shifting the structural shape:

1. *"Should be in architecture dir not repo root. Also modify anywhere else this assumption was used."* — relocated `failure-modes.md` → `architectures/failure-modes.md` and updated all eight references in the comparison-doc pointer, SKILL.md hard rule, and stage-5 procedure section.
2. *"This file changes a lot. Give a link to the file in a specific commit. Also when you reference another file in this repo make sure it is a correct clickable hyperlink."* — converted every bare-text in-repo reference to a clickable markdown link with `test -f`-verified relative paths, and pinned the churn-prone `research/PLAN.md` §3.6 worked-example reference to a GitHub permalink at commit `58216ff#L83-L97` (with a live-file link alongside for current-state navigation).
3. *"It is very important that whenever any of the other files in /architecture are modified, the assessment of failure mode vs architecture be updated... only the column for that alternative. I suggest a strict schema for this table, and mechanical tools to change only one column so you aren't tempted to 'adjust' a different column when you weren't asked to."* — built a markdown-table linter parsing §2.4 + diff-correspondence enforcement + a CI workflow as a hard fail. AskUserQuestion clarified shape: "lightest" (no JSON canonical / no mutator CLI, just markdown lint + CI gate) and "hard fail" (PR blocked until reconciled, label `failure-mode-only` as the escape hatch).

### Phase 3 — User reshapes the entire artifact: the gate becomes a self-installing skill, and the CI signal becomes a PR review

The fifth user message was the largest pivot: *"Make sure all required files are stored in the skill resources directory, and the skill will detect it isn't installed and self install if needed... Do not change any files outside of the skills directory, and especially not agents. You should create a separate skill, and in any skill that updates failure modes in architecture or the reports, this skill should be cross referenced. If the ci triggers, then the agent should detect, and determine if the change was a major change that would affect the failure modes. If not can you override ci gate? Can the ci result be a review on the pr that you can check and either fix the edit or go ahead and ignore review with a comment on the pr why it was ignored."*

This required three substantial restructures applied at once:

- **Revert all outside-skill edits from prior commits.** `AGENTS.md` had gained an "Architecture documents" rule (commit `22ee8d4`), `architectures/failure-modes.md` had gained a "Schema and update discipline" section, and `stage-5-content-processing.md` had a "Interaction with the architecture-table CI gate" subsection. All three were reverted via `git checkout 80962b3 -- <files>`. The new content moved into `SKILL.md` of the new skill.
- **Build a new self-installing skill** at `.claude/skills/architecture-failure-mode-gate/`, modeled on the existing `self-bootstrapping-skill` pattern + `research-pipeline`'s `install-workflows.py`. The linter and workflow template both live inside `resources/_workflows/` and `scripts/`; install.py renders `__SKILL_PATH__` and copies to `.github/workflows/`. The pre-flight check has three exit codes (0 / 1 / 2) so the agent's auto-recovery branches correctly: drift is auto-fixed via `--force` (no user prompt); skill defects (missing internal files) surface to the user.
- **Convert the CI workflow's signal mode.** Instead of failing the check on lint failure, the workflow posts a `REQUEST_CHANGES` PR review carrying the lint errors + the override procedure, and exits 0. On the next run where lint passes, it dismisses any prior bot-authored REQUEST_CHANGES review via `gh api -X PUT /reviews/$ID/dismissals`. The skill's "Handling the gate review" section spells out the agent's response: investigate the diff, decide if material; if material, fix the column; if not, dismiss the review with a justification comment that becomes the audit trail.

### Phase 4 — Reinforce the no-prompt pre-flight

The sixth user message arrived after the PR's last commit: *"Make sure that the skill knows to run install.py. It must not be a manual step they have to remember to do."* This was a reinforcement of the no-prompt contract, not a new feature. Two changes landed in commit `891eef3`:

- The frontmatter `description` now LEADS with the install command itself ("FIRST ACTION on every invocation, before reading anything else in this SKILL.md or doing any work — run `python .../install.py --check`; if exit code is 1, immediately run the same script with `--force`"). The trigger list comes after. This makes the install command physically the first thing any agent sees when deciding to use the skill.
- The SKILL.md body's pre-flight is now positioned ABOVE the intro paragraph, behind a "⚠ STOP — run the pre-flight before reading anything else" header. The no-prompt contract is restated twice (in the exit-code table and as a standalone paragraph) with the rationale: every prompt to the user is a place the install gets skipped, and skipped installs are the exact failure mode this skill exists to prevent.

Install.py was also tightened: `--check` now verifies that the skill's own files (SKILL.md, lint script, install script, workflow template) are intact, with a distinct exit code 2 for "skill-installation defect" vs exit 1 for "workflow drift". Verified all three exit codes by simulating each scenario (delete lint script → exit 2; delete installed workflow → exit 1; everything intact → exit 0).

The PR merged shortly after this commit landed.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory at `./2026-05-21-113/AGENTS-MD-<hash>-<kebab-name>.md` — the per-rule file contains exactly two sections: `# agent instruction` (the verbatim rule text the CI/CD assembler concatenates into `AGENTS.md`) and `# justification` (the persuasion text the assembler strips out). This Part 3 mirrors that content inline so the retrospective reviewer has every proposed rule + its justification in one place at review-decision time.

### Suggestion 1: Verify-verbatim when moving content between files — `AGENTS-MD-b2472f0bdd`

- **Per-rule file**: [./2026-05-21-113/AGENTS-MD-b2472f0bdd-verify-verbatim-on-move.md](./2026-05-21-113/AGENTS-MD-b2472f0bdd-verify-verbatim-on-move.md)

**Proposed agent instruction**:

> **Verify-verbatim when moving content between files.** When you relocate a block of text from one file to another and the goal is byte-identical preservation (a section move, a quote extraction, an artifact split), extract the source range with `sed -n 'A,Bp'` (or equivalent line-bounded tool) and immediately verify with `diff <(sed -n 'A,Bp' source) <newfile-tail>` so any silent corruption is caught before the move is committed. Do not trust Edit / Write tools alone to preserve content verbatim.
>
> *Grounded in: PR #113 §2.4 extraction from `architectures/00-comparison.md` into `architectures/failure-modes.md`.*

**Justification**: Issue #111 explicitly said "Use tools for this to ensure is verbatim." The discipline cost less than 60 seconds (one extra `diff` command). The marginal benefit is asymmetric: a silent byte-drift (a curly quote sneaking in, a tab→space conversion, a trailing whitespace edit) is invisible at code-review time and propagates into every downstream consumer of the moved content. PR #113's audit-trail commit messages and the §2.4 row-by-row diff hold up to inspection precisely because the extraction was tool-driven and verified. Adopting the rule trades one shell pipeline for forever-eliminating that class of silent corruption on file moves.

### Suggestion 2: Audit prior commits when the user introduces a mid-PR scope constraint — `AGENTS-MD-47f0b307b9`

- **Per-rule file**: [./2026-05-21-113/AGENTS-MD-47f0b307b9-audit-prior-commits-on-scope-change.md](./2026-05-21-113/AGENTS-MD-47f0b307b9-audit-prior-commits-on-scope-change.md)

**Proposed agent instruction**:

> **Audit prior commits when the user introduces a mid-PR scope constraint.** When a reviewer adds a new constraint partway through a PR ("don't touch X", "keep everything in directory Y", "don't change AGENTS"), do not just comply going forward — walk every commit already on the branch, identify any change that now violates the new constraint, and revert it in a follow-up commit. The reviewer's constraint applies to the whole PR, not just future commits.
>
> *Grounded in: PR #113 — user mid-PR direction to keep all gate machinery inside the skill directory required reverting `AGENTS.md` and `architectures/failure-modes.md` edits from earlier commits `22ee8d4` and `80962b3`.*

**Justification**: When user feedback arrives at commit five of a PR, the natural inclination is "OK, future commits will respect this." But the user is judging the PR as a whole — they will see the existing edits to AGENTS.md and the schema section in failure-modes.md when they next review the diff. Leaving them in produces a PR that visibly contradicts the user's constraint, forcing a second review round. The cost of compliance is one `git checkout <pre-violation-sha> -- <file>` per violated file (here: three files, four lines of shell). The cost of non-compliance is at minimum one wasted review round, at maximum a merge that lands the violations into main. The asymmetry is large enough that "audit then comply" should be the default response to mid-PR scope constraints.

### Suggestion 3: Use GitHub permalinks when referencing churn-prone files — `AGENTS-MD-acf21ff623`

- **Per-rule file**: [./2026-05-21-113/AGENTS-MD-acf21ff623-permalink-churn-prone-references.md](./2026-05-21-113/AGENTS-MD-acf21ff623-permalink-churn-prone-references.md)

**Proposed agent instruction**:

> **Use GitHub permalinks when referencing churn-prone files.** When citing a specific line range or section of a file whose section numbers or line positions drift (`research/PLAN.md`, `INDEX.md`, status docs, anything regenerated by a workflow), link to a GitHub permalink pinned at a specific commit SHA (`https://github.com/<owner>/<repo>/blob/<sha>/<path>#L<start>-L<end>`) instead of a live relative link. Keep a separate live link alongside for current-state navigation, but make the permalink the citation of record so the reference does not silently rot.
>
> *Grounded in: PR #113 reference to `research/PLAN.md` §3.6 worked F36/F37-collision example.*

**Justification**: The reviewer flagged the bare-`research/PLAN.md §3.6` reference because that file changes a lot — drains add round-summary bullets, plan reorganizations renumber sections. A future reader following the link could find `§3.6` is now about something else entirely. Pinning the citation to commit `58216ff#L83-L97` costs four extra characters of typing per reference (the SHA prefix) and one `git log -1 -- <file>` lookup; the benefit is a permanent reference that survives arbitrary file reorganization. The live link alongside still gives readers the current-state version. Adopt for any reference whose target is a file that gets regenerated, regularly amended, or carries section numbers that re-flow.

### Suggestion 4: Self-installing skills use three exit codes from `install.py --check` — `AGENTS-MD-42cee721cd`

- **Per-rule file**: [./2026-05-21-113/AGENTS-MD-42cee721cd-self-installing-three-exit-codes.md](./2026-05-21-113/AGENTS-MD-42cee721cd-self-installing-three-exit-codes.md)

**Proposed agent instruction**:

> **Self-installing skills use three exit codes from `install.py --check`.** A self-bootstrapping skill's check script must distinguish three outcomes with distinct exit codes so the agent's auto-recovery branches correctly: `0` means installed and in sync (proceed); `1` means workflow / artifact missing or drifted (auto-fix with `--force`, no user prompt); `2` means a skill-internal file is missing (skill installation defect — re-copy the skill, do NOT auto-fix). Two exit codes (pass/fail) conflate recoverable drift with unrecoverable skill damage and make the auto-fix policy unsafe.
>
> *Grounded in: `architecture-failure-mode-gate` install.py refinement in PR #113 commit `891eef3`.*

**Justification**: The existing `self-bootstrapping-skill` pattern documented two exit codes (success / failure) plus a passing mention of "exit 2 if template missing from the skill itself." PR #113 made the exit-2 case concrete and tested all three (delete lint script → exit 2; delete installed workflow → exit 1; everything intact → exit 0). The reason this needs to be enforced as a project-wide rule: if the agent's pre-flight maps "exit 1" to "auto-fix with `--force`" and the install.py also returns 1 for skill-internal damage, the agent will repeatedly try to `--force`-install in a broken state, producing confusing error logs without ever surfacing the actual skill-defect cause. Three exit codes carry distinct recovery semantics; conflating two of them is the source of the failure mode. Marginal cost: ~6 lines of Python per install script. Marginal benefit: agents auto-recover correctly without operator intervention.

### Suggestion 5: Lead self-installing skill descriptions with the install command — `AGENTS-MD-bfb7c7722c`

- **Per-rule file**: [./2026-05-21-113/AGENTS-MD-bfb7c7722c-skill-description-leads-with-install.md](./2026-05-21-113/AGENTS-MD-bfb7c7722c-skill-description-leads-with-install.md)

**Proposed agent instruction**:

> **Lead self-installing skill descriptions with the install command.** For any skill that ships derived artifacts requiring local installation, the frontmatter `description` field must lead with the install command itself — not a summary, not the trigger list. The trigger list goes AFTER. The reasoning: the description is what an agent sees when deciding whether to use the skill, and the install must happen before any other action; placing the install command in the first sentence makes it physically impossible to invoke the skill without seeing the install. The SKILL.md body must mirror this by placing the pre-flight section above the intro paragraph behind a STOP header.
>
> *Grounded in: PR #113 — user direction "the skill must not be a manual step they have to remember" required moving the install command to the top of both the description and SKILL.md.*

**Justification**: The original `architecture-failure-mode-gate` SKILL.md had its pre-flight at section position 2 (after the intro paragraph), which is where the existing `research-pipeline` and `self-bootstrapping-skill` examples place it too. The user judged that insufficient — burying the pre-flight even one section below the H1 was enough that "agents skip pre-flights when they're buried below the interesting content." The fix is to make the install command the first content the agent sees in BOTH surfaces: the frontmatter description and the SKILL.md body. The marginal cost is reordering two paragraphs. The benefit is removing the entire failure mode of "agent forgets to run the install" — and the user's explicit reason for asking is that they have repeatedly seen this failure mode in this repo.

### Suggestion 6: Test git-diff-driven logic via unit tests, not sandboxed commits — `AGENTS-MD-3ff89265e8`

- **Per-rule file**: [./2026-05-21-113/AGENTS-MD-3ff89265e8-test-git-diff-logic-via-unit-tests.md](./2026-05-21-113/AGENTS-MD-3ff89265e8-test-git-diff-logic-via-unit-tests.md)

**Proposed agent instruction**:

> **Test git-diff-driven logic via unit tests, not sandboxed commits.** When validating a script that consumes `git diff <base>...HEAD` output, do not attempt to test it by creating commits inside a temporary `git worktree add` or `cp -r .git /tmp/...` setup — commit signing in the Claude Code sandbox is bound to the main working tree and fails with `"missing source"` inside copies. Instead, factor the diff-consuming logic into a pure function (e.g., `changed_columns(old_text, new_text)`) and unit-test it with synthetic before/after strings. The unit test is faster, deterministic, and survives the sandbox's commit-signing constraints.
>
> *Grounded in: PR #113 lint-failure-modes.py verification — git worktree commits failed; Python unit tests with synthetic table strings worked.*

**Justification**: I tried twice to validate the lint logic by creating a sandbox via `git worktree add /tmp/...` and `cp -r .git /tmp/...`, and both attempts failed at the `git commit` step with `signing server returned status 400 ... missing source`. The signing endpoint is bound to the main working tree's path and refuses to sign commits from any copy. The recovery — factoring `changed_columns(old_text, new_text)` into a pure function and writing seven synthetic test cases (no-op, single-col change, multi-col change, header rename, row add, row delete, mixed) — took ~3 minutes and produced more thorough coverage than the commit-based test ever would have. Adopting this rule saves the next agent five-to-ten minutes of fruitless sandbox experimentation and produces a strictly better test suite. The marginal cost is "design the function to be testable in isolation," which is good code architecture regardless.
