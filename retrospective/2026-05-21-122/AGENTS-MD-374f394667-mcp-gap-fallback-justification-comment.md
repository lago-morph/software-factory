# agent instruction

**MCP gap fallback: justification comment + surface to user.** When a documented skill action depends on an MCP tool capability the actual exposed tool surface does not support — `pull_request_review_write` lacking a `dismiss` method, no `gh` CLI in the environment, an endpoint the skill assumes that does not exist — the agent must (a) post a structured justification comment on the affected PR or issue containing the phrase "Dismissing `<gate-name>`: `<reason>`" (or equivalent verb for non-dismiss cases) as the audit trail, (b) explicitly surface the tooling gap to the user in chat naming the specific MCP method that is missing, and (c) NOT silently skip the action and NOT fabricate an alternative action that is "close enough." The justification comment must be detailed enough that a maintainer can take the manual action (e.g., click-dismiss in the GitHub UI) without re-doing the analysis.

*Grounded in: PR #122 — failure-mode-gate bot left a `CHANGES_REQUESTED` review for non-material link edits; `mcp__github__pull_request_review_write` exposes only `resolve_thread`/`unresolve_thread`, no `dismiss` for full PR reviews; `gh` CLI not available in this environment.*

# justification

Skills are written against the GitHub API in the abstract; the actual MCP tool surface this harness exposes is a moving subset. When a skill says "use `mcp__github__pull_request_review_write method=dismiss`" and that method is not in the actual MCP, the agent has three failure modes available — silent skip ("the gate is wrong, I'll just ignore it"), fabricate ("post a `COMMENT` review and pretend that's a dismissal"), or freeze ("I cannot do this; user, do it yourself"). None of those are right. The correct move is fourth: produce the closest available artifact that preserves the audit-trail intent (a structured justification comment on the affected thread), surface the gap to the user explicitly so they can either take the manual action or file a ticket against the MCP, and document what the agent did NOT do.

In PR #122 the bot's review was a known non-material false positive (Lineage line link conversions touched no failure-mode coverage). The skill's documented `dismiss` path was unavailable. The recovery posted a structured "Dismissing failure-mode gate review: ..." comment with the full diffs inline and a `cc the human reviewer` ping. Cost of the rule: one extra comment per gap encounter (small). Cost of skipping: the audit trail vanishes ("why did this bot review get auto-ignored?"), the rule gets soft-disabled by precedent, and the gap stays invisible to the maintainer. Asymmetric.
