# Cluster C2 — Observation & control (P-05, P-06, P-07)

Cluster scope per the [primitive index](./index.md#cluster-c2--observation--control): the three substrate primitives that observe the cycle as it runs and arbitrate read access to what is observed. Sketches below are produced under the [refined two-part rule](../phase-3.4-decisions-resolved.md#refined-two-part-rule-for-accepting-a-substrate-primitive) and the [Round-2 cluster-subagent constraints](../decisions/auto-001-phase-3.5-dispatch-shape.md#amendments-to-the-dispatch-brief-that-will-be-sent-to-subagents). **Per the cluster-subagent rules, no same-vs-distinct verdicts are rendered on primitives that look similar across candidates (e.g., P-05's GF-S/BF-M plain trajectory vs. U-C distance-keyed trajectory) — that judgment is deferred to Phase 4.2.** Each primitive's section restates its contract, names at least one concrete tool/library with an integration sentence, cites the specific corpus problem that motivates it, and renders a buildability verdict.

---

## P-05 Trajectory capture

**Contract restatement.** P-05 is per-event append-only persistence of the agent's step/tool-use trace. Every tool call, model invocation, judge call, guard decision, and operator action must persist as a content-addressed event *before* it returns to the caller — so that crash-resume is replay from the last persisted event and post-hoc forensic reconstruction across cycle boundaries is possible. The persistence has to be sub-millisecond per event (writes are on the agent's hot path), append-only (no mutation of prior events), and content-addressed (event ID is a hash, not a sequence number, so cross-cycle references are stable). Reads are by event-ID, by cycle-ID, by time-window, and — for the U-C distance-keyed variant — by distance tuple appended at write time.

**Construction path.** OpenHands V1's event-sourced runtime is the named prior-art reference and the construction pattern. The OpenHands V1 substrate measures sub-ms per-event persist and ~7.4ms median crash-recovery cost across a cycle ([report 11 §6](../../../research/11-openhands-substrate-audit.md), cited as evidence-of-feasibility per [GF-S §1.S3](../tracks/greenfield-substrate-first.md)). The integration is direct: model the trajectory store as a per-cycle append-only log file (or a single LMDB table keyed by event hash) with a writer interface that wraps every tool/model/judge call; the wrapper computes the SHA-256 of the event payload, writes `{event_id, parent_event_id, cycle_id, kind, payload, ts}` to the log, fsyncs, and only then returns control to the caller. Crash-resume reads the log tail to find the last persisted event and rehydrates the agent state from there. For the U-C variant, the writer additionally appends the distance tuple computed by P-32 at write time ([U-C §1.5](../tracks/unified-C.md)); for BF-M (D-7) the same writer feeds the PR-body trajectory pointer at stage 8 ([BF-M §4 D-7](../tracks/brownfield-methodology-first.md)). Alternative substrates that satisfy the contract: LMDB or SQLite WAL mode for the per-cycle log; S3 or an IPFS-style content-addressed object store for cross-cycle archival.

**Corpus-why citation.** The motivating corpus problem is [F14 forensic-reconstruction widening](../failure-modes-v3.md) and [F55 behavioural drift](../failure-modes-v3.md). [GF-S §1.S3](../tracks/greenfield-substrate-first.md) makes the load-bearing case: "when a greenfield architecture changes its own structure mid-flight (UC4 spec-malleability), the trajectory is the only persistent artifact that records *which cycle of which spec-version produced which output*. Without it, the architecture's history rewrites silently as the spec moves." Trajectory is also the substrate input that Patrol (P-06 tier-3) reads for cross-cycle drift detection ([F8 stale-knowledge inversion](../failure-modes-v3.md), [F54 goal subversion](../failure-modes-v3.md)) and that the BF-M PR-creator (P-04) attaches as the trajectory pointer for [F14 attribution](../tracks/brownfield-methodology-first.md).

**Research-grade-uncertainty flag.** None. Construction is well-understood; OpenHands V1 has shipped the measurements.

**Buildability verdict.** `commodity`.

## P-06 Watchdog tiers (Daemon / Triage / Patrol)

**Contract restatement.** P-06 is a three-tier escalation chain that observes the running factory at three different cadences and scopes. **Daemon** is substrate-resident, runs at seconds cadence, and watches process-level signals: heartbeat liveness, resource caps, sandbox-boundary violations. Detects process death and stuck-but-not-dead conditions. **Triage** is substrate-resident but invokes an AI judge at seconds-to-minutes cadence to answer the per-cycle question "is this agent stalled or thinking?" — the structural detector for [F22 (zombie agents) and F23 (stalled-vs-thinking)](../failure-modes-v3.md). **Patrol** runs at hours cadence over the cross-cycle distribution of trajectories: it asks "is the population of cycles drifting?" and escalates to a human when it detects [F55 behavioural drift](../failure-modes-v3.md), [F57 design-authority erosion](../failure-modes-v3.md), [F8 stale-knowledge inversion](../failure-modes-v3.md), or — in the U-C and D7-U-1 variants — [F47 Goodhart gaming of the dispatcher](../failure-modes-v3.md). Each tier's escalation surface is typed (an event on the coordination medium); higher tiers consume lower-tier output.

**Construction path.** No single off-the-shelf tool covers all three tiers, but each tier maps onto well-understood patterns. **Daemon tier**: a systemd-style supervisor process or a Kubernetes liveness/readiness probe pair; concretely, a per-cycle sidecar process polling `/proc/<pid>/stat` plus the trajectory log's last-event timestamp at 1Hz, with cgroup-enforced resource caps wrapping the agent process. **Triage tier**: a substrate-resident LLM judge invoked at a fixed cadence (or on Daemon-tier signal) with a typed prompt taking `{recent_trajectory_window, current_tool_invocation, elapsed_since_last_event}` and emitting a typed verdict `{stalled, thinking, escalate}`; the cross-family routing requirement is inherited from P-14 (judge router). **Patrol tier**: a cron-style batch job (Airflow / Prefect / a simple `systemd.timer`) running at hours cadence that reads the trajectory store (P-05) across many cycles and applies deterministic distribution checks (KL-divergence of action distributions, monotone-trend tests on judge-agreement rates, signed-rank tests on cycle-cost distributions) — Patrol's heavy lifting is *statistical*, not LLM-based, exactly because it is checking for drift that LLM-based detectors would themselves be subject to.

**Corpus-why citation.** The construction is anchored by [GF-S §1.S5](../tracks/greenfield-substrate-first.md), [GF-M D-6](../tracks/greenfield-methodology-first.md), and [BF-M §4 D-6](../tracks/brownfield-methodology-first.md), all of which accept-with-justification the Daemon/Triage/Patrol decomposition from [Round-2 C14](../../../archive/synthesis-v1-v2/13-round-2-synthesis.md) and the [brief glossary §0](../00-brief-v3.md). The Patrol-tier's load-bearing justification is the cross-cycle drift cluster: [F34 cross-layer drift](../failure-modes-v3.md), [F55](../failure-modes-v3.md), [F57](../failure-modes-v3.md), and the brownfield F43 RSI-board-visibility surface ([report 31 §1](../../../research/31-caremark-rsi-board-exposure.md)). The Triage-tier's specific corpus motivation is the F22/F23 cluster — "is this agent stalled or thinking?" is the question no Daemon-tier substrate check can answer without semantic understanding of what the agent is doing.

**Research-grade-uncertainty flag.** None. Each tier maps onto a mature engineering pattern (process supervision; LLM-as-judge with typed I/O; statistical drift detection on time-series logs).

**Buildability verdict.** `commodity`. The composition discipline — that the three tiers have to exist *together* and escalate up the chain — is the design content, but each tier individually is uncontroversial.

## P-07 Telemetry ingestor (per-role read filters)

**Contract restatement.** P-07 ingests production telemetry — OpenTelemetry traces, metrics, log streams, error fingerprints, per-module latency / error-rate aggregates, hot-path identifiers — and exposes them as a queryable surface to agent tools. The substrate-distinguishing requirement is **per-role read filters**: the same telemetry corpus is the brownfield system's *scenario holdout* ([CTR-B5 / CTR-G2](../contradictions.md) inversion of D-2), so the substrate must partition reads by agent role. The **builder** role must not see telemetry slices that have been carved off as held-out acceptance scenarios; the **V&V** (acceptance) role reads the holdout slice; the **comprehension / archaeological-brief** role reads non-holdout slices freely. Partition is enforced at the read API, not by file-system convention, and is auditable per query (every read records the role, the requested slice, and the allowed-vs-denied verdict to P-05 trajectory and P-24 attribution).

The per-role read filter is the non-trivial part. Without it, P-07 is a commodity telemetry pipeline; with it, P-07 is the substrate-level enforcement of [D-4 holdout discipline](../tracks/brownfield-substrate-first.md) generalized from filesystem partitioning to attribute-based access control over a continuous data stream. [BF-S §S-3](../tracks/brownfield-substrate-first.md) states this load-bearing-ly: "The substrate exposes these as *queryable* by agent tools but *partitioned by role* — builder agents cannot read holdout telemetry; only the V&V agent role can. This is substrate-enforced holdout discipline (D-4) generalized to telemetry-as-scenario."

**Construction path.** The named tool is **OpenTelemetry collectors with attribute-based access control**, composed with **OpenPolicyAgent (OPA)** or **Cedar** as the role-filter policy engine. Integration sentence: deploy an OpenTelemetry Collector pipeline whose `attributes` processor tags every incoming span/metric with a holdout-partition attribute computed at ingest time (e.g., `holdout.bucket = hash(trace_id) % 100 < 20 ? "holdout" : "training"`), then expose reads through a thin query proxy (a FastAPI service in front of the OTel backend — Jaeger, Tempo, or Prometheus depending on signal type) whose every query is rewritten by an OPA policy bundle that filters out spans/metrics whose `holdout.bucket` is held-out for the calling role. The role identity is carried in the agent's bearer token (a substrate-issued JWT per cycle naming the role); the OPA policy reads `{role: "builder"|"vv"|"comprehension", holdout.bucket: "training"|"holdout"}` and emits an `allow`/`deny` per row. Every allow/deny is logged to P-05 with the cycle ID. The held-out partition itself is declared at substrate-init time (a `holdout-policy.yaml` checked into the deployment repo, signed at deploy) and is immutable for the lifetime of the cycle — exactly the [F28 holdout leakage](../failure-modes-v3.md) discipline the substrate is supposed to enforce.

Alternative construction paths that meet the contract: a **Hyperdrive-style** query gateway in front of a managed observability backend, with the role filter as a SQL-rewriting layer (the OPA policy emits a `WHERE` clause appended to every PromQL or TraceQL query); a CaMeL-class typed perimeter (P-25) wrapping all telemetry reads with capability tokens that name the allowed partitions, which is the BF-S architectural framing where P-07 reads flow through the P-25 perimeter. Both alternatives preserve the substrate-enforcement-not-methodology-convention property.

**Corpus-why citation.** Three specific corpus problems motivate P-07's existence and shape:

1. **[F28 holdout leakage](../failure-modes-v3.md)** — the load-bearing motivation for the per-role filter discipline. Brownfield's "scenarios live in the running system" inversion ([CTR-B5 / CTR-G2](../contradictions.md)) makes filesystem-partition holdout enforcement impossible; the substrate must instead enforce holdout at the read API, which is exactly what the per-role filter does. [BF-S §4 D-4 expanded](../tracks/brownfield-substrate-first.md) makes this the substrate-defining argument.
2. **[F55 behavioural drift / self-reference](../failure-modes-v3.md)** — production telemetry is the out-of-distribution ground truth that breaks self-reference loops. The BF-S F-mode table lists F55 as `high` severity with "S-3 (production telemetry as out-of-distribution ground truth)" as the mitigation ([BF-S §2.8](../tracks/brownfield-substrate-first.md)).
3. **[F58 runtime/design-time compliance split](../failure-modes-v3.md)** — for RSI-board-visibility ([report 31](../../../research/31-caremark-rsi-board-exposure.md)) the substrate has to provide runtime compliance evidence that the methodology can attach to outputs. P-07's audited query log (every read tagged with role + cycle ID) *is* that evidence stream.

Plus the BF-L Codebase Model's runtime view: P-07 is one of the six views BF-L's P-26 composes ([BF-L §1.5 view (d)](../tracks/brownfield-legacy-ingestion-first.md)), so its construction is also a precondition for BF-L's load-bearing primitive.

**Research-grade-uncertainty flag.** None — the per-role filter discipline has prior art (OPA, Cedar, AWS IAM resource policies, ABAC literature broadly) and OpenTelemetry's attribute-processor pipeline is mature. There is no missing primitive that has to be invented.

**Buildability verdict.** `designed-system`. The plain telemetry-ingestor half is commodity (OpenTelemetry Collector + a backend is a configuration exercise); the per-role read-filter half is non-trivial design content — partition-policy declaration, signed-at-deploy immutability, OPA-policy authoring for the role taxonomy, audited query log integration into P-05 and P-24, role-identity carriage in JWT, perimeter wrapping per the P-25 path. The cluster brief flagged this primitive as the one whose buildability verdict might land at `designed-system` rather than `commodity`; that's where this sketch lands. Note: the [registry buildability-scope column](./index.md#cluster-c2--observation--control) marks P-07 as `commodity (per-role filter is the non-trivial part — see notes)`, which this sketch sharpens to `designed-system` on the strength of the filter discipline being load-bearing for [F28 holdout leakage](../failure-modes-v3.md) enforcement in the brownfield mandate. The reclassification is surfaced for Phase-3.5.5 lead-agent re-check.

## Cluster coda (commodity-cluster note, no same-vs-distinct verdicts)

The three primitives in C2 form a natural pipeline: P-05 writes the per-event substrate-of-record, P-06 reads it at three cadences to detect liveness / cycle-anomaly / cross-cycle drift, and P-07 ingests an external telemetry stream that Patrol (P-06 tier-3) can compare against the trajectory-derived distributions. Two of the three are commodity in construction (P-05, P-06); one lands at `designed-system` because the per-role read-filter discipline is the load-bearing brownfield-holdout-enforcement primitive. Per the [Round-2 cluster-subagent rules](../decisions/auto-001-phase-3.5-dispatch-shape.md#amendments-to-the-dispatch-brief-that-will-be-sent-to-subagents), this coda renders no judgment on whether the U-C distance-keyed trajectory variant, the GF-S/BF-M plain trajectory, and any other claiming-candidate's trajectory primitive collapse to one P-05 or remain distinct — that is Phase-4.2 work.
